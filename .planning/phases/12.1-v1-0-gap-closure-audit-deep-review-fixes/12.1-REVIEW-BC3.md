## Warnings

### WR-BC3-1: Two shape rules are still quadratic, yet the header and DIAGNOSTICS.md now claim every rule is linear

**File:** `.pi/lib/secret-patterns.ts:3`, `:25`, `:29`; `docs/DIAGNOSTICS.md:263-264`

**Issue:** The new header says "Every quantifier is bounded or runs over a class disjoint from what follows it, so each start position costs O(1)". DIAGNOSTICS.md says "Every rule is length-bounded, so the redactor stays linear on hostile input". Both claims are false for two rules in `SHAPE_PATTERNS`:

- **JWT** `eyJ[A-Za-z0-9_-]{8,}\.…`: from each `eyJ` the regex scans the whole dotless run before it fails. A run that repeats `eyJ` therefore costs O(n²).
- **curl** `(?<keep>(?<![\w-])(?:-u|--user)[ =]+)[^\s:'"]+:…`: `[ =]+` overlaps the value class, which contains `=`, and every `-u=` restarts the scan.

Measured on node 24 with the exact regexes:

| Input | Time |
|---|---|
| `"eyJ".repeat(n)`, 20 KB | 920 ms |
| `"eyJ".repeat(n)`, 80 KB | 14,974 ms |
| `"-u=".repeat(n)`, 80 KB | 744 ms |
| `" -u " + "=".repeat(80000)` | 2,232 ms |

`redactDeep` calls `redactString`, which applies `SECRET_PATTERNS`, and that includes these shape rules. It runs synchronously in `before_provider_request` (`diagnostics/wire.ts:169`) on every request for as long as the string stays in the 40-message tail. It also runs on the reviewer contract.

A base64url blob or a crafted fixture in a work repo, read once, stalls every following turn by seconds. This is the same class of problem as WR-BC2-6. Only the name rule was fixed.

**Fix:**
- Anchor the JWT start so that each run has a single start position: `/(?<![A-Za-z0-9_-])eyJ[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]*/g`.
- For curl, make the separator and the value disjoint, and bound the value: `/(?<keep>(?<![\w-])(?:-u|--user)(?: +|=))[^\s:'"=][^\s:'"]{0,256}:[^\s'"]{1,256}/g`.
- Add `"eyJ".repeat(100_000)` and `"-u=".repeat(70_000)` to the existing "linear-time" test, with the same 100 ms bound.
- Rewrite both claims so they are true.

### WR-BC3-2: The bounded name rule lets long credentials into the logs: quoted values over 512 characters in full, unquoted ones as a tail

**File:** `.pi/lib/secret-patterns.ts:38`

**Issue:** In the value alternatives `"[^"\n]{0,512}"` and `'[^'\n]{0,512}'`, the closing quote must appear within 512 characters, or the alternative fails. The unquoted branch `[^\s"'&;]` cannot start at a quote, so the whole match fails. The unquoted branch stops after 512 characters and leaves the rest in clear. The `[ \t]{0,16}` spacing also no longer crosses a newline, which the old `\s*` did.

Verified results:
- `password: "<600 chars>"`: unchanged, so the value is not masked at all.
- `"client_secret": "<600 chars>"`: unchanged.
- `TOKEN=<600 chars>`: `TOKEN=[redacted:512 chars]` followed by the last 88 characters in clear.
- `password:\n  hunter2`: unchanged.

Before this iteration, the unbounded rule masked all four. Long values are realistic in exactly the files the wire log captures:
- STS and SSO `SessionToken`/`accessToken` JSON values often exceed 512 characters;
- `aws_session_token=` in `~/.aws/credentials` does as well.

The wire dump lands in the working tree of a public repo, and `.gitignore` is only the second control there (`redact.ts:2-3`).

**Fix:** Linearity does not need the value bound. Only a match that fails can cause a rescan, and a value branch with nothing after it never fails. Keep `{0,40}` on the key suffix and drop the value bound:

```ts
/(?<keep>(?:password|passwd|secret|token|api[_-]?key|access[_-]?key|authorization|credential)[A-Za-z0-9_-]{0,40}["']?[ \t]{0,16}[=:][ \t]{0,16})(?!\[(?:redacted|REDACTED)\b)(?:"[^"\n]*"?|'[^'\n]*'?|[^\s"'&;]+)/gi
```

With the closing quote optional, a match never fails after `[=:]`. Every failure therefore happens within the bounded 40-character suffix, and the rule stays O(n). Add fixtures for a 600-character quoted value, a 600-character unquoted value and a 200 KB time bound.

### WR-BC3-3: `onlyCommitsSince` rejects every signed commit when `log.showSignature` is set, and allows no clock tolerance

**File:** `.pi/extensions/workflows/evidence.ts:61-69`

**Issue:** `git log --format=%P|%at|%ct` honours `log.showSignature=true` from the user's gitconfig. Signature verification output then goes to **stdout**, ahead of each formatted row. This was verified in the scratchpad with an SSH-signed commit:

```
Good "git" signature for a@b with ED25519 key SHA256:…
dbfc3f38…|1791891656|1791891656
```

The signature line passes the `trim() !== ""` filter. `row.split("|")` turns it into `parents = 'Good "git" signature …'`, whose `split(" ").length` is not 1, so `every` returns false. The run then rejects with "not a new commit … made during this run".

Every `/quick` and `/execute` run by a user who signs commits and sets `log.showSignature` is falsely rejected. That combination is common where signing is mandated, which is typical of enterprise GitLab, and the user works on GitLab. GPG users are affected the same way.

There are two smaller false-reject paths:
- The floor is the arm second, with zero tolerance. A system clock stepped backwards mid-run (an NTP correction or a VM or hibernate resume, on runs that last minutes to hours) rejects legitimate commits.
- A `GIT_AUTHOR_DATE` or `GIT_COMMITTER_DATE` exported in the shell does the same.

**Fix:**

```ts
spawnSync("git", ["-c", "log.showSignature=false", "rev-list", "--no-commit-header", "--format=%P|%at|%ct", `${baseSha}..${headSha}`], …)
```

Alternatively, add `--no-show-signature` to `git log`. Then parse strictly with `/^([0-9a-f]{40,64}(?: [0-9a-f]{40,64})*)?\|(\d+)\|(\d+)$/`, fail closed on any other line, and also reject an empty parent list (a root commit). Allow a small tolerance, for example `armedAtMs - 120_000`, and document it.

Add a test that sets `-c log.showSignature=true` on a repo with a signed commit. An SSH key from `ssh-keygen` needs no GPG.

### WR-BC3-4: Pinning the raw task line includes the checkbox, so ticking a finished task refuses `/execute` and `/review`

**File:** `.pi/extensions/execute/ledger.ts:126`; `.pi/extensions/execute/index.ts:102-103`; `.pi/extensions/review/index.ts:77-78`

**Issue:** `tasksOf` stores `line: t.rawLine`, and `rawLine` is the whole PLAN line including `- [ ] `. `TASK_LINE_PATTERN` (`plan-schema.ts:18`) accepts `[ xX]`. A ticked task is still a valid task, but its line no longer matches the pin. Afterwards:
- `pinMismatch` refuses the next `/execute` with "PLAN.md's tasks (text, …) changed";
- `/review` refuses as well.

Ticking is the natural thing for both the user and a cheap model to do. In degraded mode, the brief is literally `Do this task yourself: - [ ] T002 …` (`execute/index.ts:134`). `.pi/work/` is git-excluded, so the drift check never sees the edit, and the only signal is the refusal on the next run. Iteration 2's pin (`id`, `path`, `verificationCommand`) was immune to this. This is a false refusal of legitimate work, recoverable only through `--repin` (see WR-BC3-5).

**Fix:** Pin the line without its checkbox, `line: t.rawLine.replace(/^- \[[ xX]\] /, "")`, or pin `verb` plus the remainder. Existing ledgers then refuse once and are re-pinned. Add a test that ticks T001 and checks that `/execute` proceeds to T002.

### WR-BC3-5: `--repin` asks the user to approve a SPEC change it cannot show, and "restore it" points at a copy that does not exist

**File:** `.pi/extensions/execute/index.ts:80`, `:84`, `:103`; `.pi/extensions/execute/ledger.ts:129-131`

**Issue:** The pin keeps only `specHash`, so the confirm can say no more than `SPEC.md: CHANGED since the pin`. The pinned SPEC text is not stored anywhere:
- the ledger holds only the hash;
- `ensureHarnessIgnored` adds `**/.pi/work/` to `info/exclude`, so git has no copy either.

WR-BC2-4's threat is a model that rewrites SPEC requirement text mid-run. Against that threat, the only human control is an approval of a change the user cannot see. The refusal text, "restore it, or accept the change with … --repin, which shows both", is also wrong for SPEC on both counts: there is nothing to restore from, and `--repin` does not show both versions.

For tasks, the confirm prints the full pinned and current lists one after the other, with no marking of what changed. On a 20-task plan the one rewritten line is easy to miss.

**Fix:**
- Store the gated SPEC `requirementsBody` in the `base` and `pin` rows (or the whole SPEC.md). The ledger sits in the git common dir, so its size is not a concern.
- Render a line diff in the confirm: only the changed task lines and SPEC lines, as `-`/`+`.
- Change the refusal text to "accept it with /execute <slug> --repin, which shows what changed".

### IN-BC3-3: `--repin` and `--rebase-base` run before the in-flight check, and Pi runs commands mid-stream

**File:** `.pi/extensions/execute/index.ts:81-97` (the check is at `:109`)

Pi 1.1.0 executes extension commands immediately, even while the agent is streaming (`agent-session.js:1524-1532`). Both flags return before `isRunArmed() || !ctx.isIdle()`. A user can therefore re-pin while the executor is still editing PLAN.md. The executor's mid-run rewrite is then accepted behind one confirm, and with `--rebase-base` the drift base moves to an uncommitted-for HEAD. Both paths are user-approved, so this is INFO. Moving the `IN_FLIGHT` check above both branches costs one line.

### IN-BC3-4: `/mode`'s "re-run /<mode> to re-pin" advice can be permanently wrong

**Status (2026-10-13):** fixed in cf5c5db - the planner pin and `/mode` choose with one registry-aware picker, so the re-pin advice shows only when re-running the mode command would change the pin.

**File:** `.pi/extensions/routing/index.ts:235-240`; `.pi/extensions/routing/agent-overrides.ts:88-99`

The two sides use different pickers:
- `routed` comes from `pickConfiguredCandidate`: the first candidate that is in the registry **and has configured auth**.
- The pin comes from `agentOverridesFor`: the first candidate that passes the guard on a fixture, with no auth check.

When the first planner candidate has no key on this machine, the two differ. `/mode` then reports the mismatch and tells the user to re-run the mode command, which writes the same pin again. Either share one picker or reword the advice to name the cause.

### IN-BC3-5: Pin-expiry edges and an unproven ROUTING.md claim

**File:** `.pi/extensions/routing/agent-overrides.ts:164-166`, `:334`; `docs/ROUTING.md` (the "cheaper direction" sentences)

- An owner `at` in the future (the clock stepped back after a pin) gives a negative `now - o.at`, so the owner never expires until the clock catches up. Treat `o.at > now + 60_000` as expired.
- ROUTING.md twice says an early restore "moves its planner to the cheaper default, never to a dearer one". The restore writes the user's own pre-pin value, which can be any model. Reword it to "the user's own override".

### IN-BC3-6: Fresh-commit residuals that WORKFLOWS.md section 4 does not list

**File:** `docs/WORKFLOWS.md` ("Only commits the run made count")

These also pass `onlyCommitsSince` with stock flags, not with forged dates:
- `git rebase --ignore-date` / `--reset-author-date` of a fetched branch;
- `git merge --squash other` (one parent, fresh dates, someone else's content);
- `git commit -C <sha> --reset-author`;

The drift check and the reviewer remain the defences, as the doc says. List these residuals there.
