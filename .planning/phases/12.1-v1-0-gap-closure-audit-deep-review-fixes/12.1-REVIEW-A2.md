## Critical Issues

### CR-A2-1: Piping a guarded command into an interpreter still works through `/dev/stdin` or an inline shell that re-reads stdin

**Location:**
- `.pi/extensions/safety/shell.ts:681-689` (`interpreterScript`)
- `shell.ts:561-573` (`runnerTexts`)
- `shell.ts:694-707` (`runsGeneratedScript`)

**Defect:**
- `interpreterScript` treats any path-shaped operand as a script file. `/dev/stdin`, `/dev/fd/0` and `/proc/self/fd/0` are path-shaped, so a piped interpreter given one is never "fed by pipe".
- An inline form (`sh -c sh`, `bash -c 'bash -s'`) returns `undefined`, the "code is an argument" case. Its inner shell still reads the pipe.
- In both cases `runnerTexts` sees only the runner's own segment, where no guarded verb appears.

**Reproduced (allowed on `feat` and `main`):**
- `echo 'git push origin feat:main' | bash /dev/stdin`
- `echo 'git push origin feat:main' | sh /dev/fd/0`
- `echo 'git push origin feat:main' | sh /proc/self/fd/0`
- `echo 'git push origin feat:main' | python3 /dev/stdin`
- `echo 'git push origin feat:main' | sh -c sh`
- `echo 'git push origin feat:main' | bash -c 'bash -s'`

**Fix:**
- In `interpreterScript`, map a stdin alias to `"-"`. Match it with `/^\/(dev\/(stdin|fd\/0)|proc\/self\/fd\/0)$/`.
- For a piped command, refuse when a guarded verb appears in any **other** segment of the same pipeline and the piped command is any `STDIN_INTERPRETERS` member, whatever its operand. This is the cross-segment taint iteration 1 proposed.

```ts
const pipelineMentionsVerb = mentionsGuardedVerb(extracted.filter((e) => !scan.piped.has(e.node)).flatMap((e) => segmentTexts(e.invocation)));
if (scan.piped.has(node) && STDIN_INTERPRETERS.has(executable) && pipelineMentionsVerb) return true;
```

### CR-A2-2: Write-then-run is not detected when the script file name has no dot or slash

**Location:**
- `.pi/extensions/safety/shell.ts:686-688`: a bare word becomes `"-"`
- `shell.ts:702-705`: `"-"` is excluded from the written-file match

**Defect:**
- The `bash -o pipefail` heuristic turns any bare-word operand into stdin.
- The written-file comparison then skips `"-"`, so a script written and run in one command escapes when its name has no `.` or `/`.
- `docs/SAFETY.md:50-52` says this form is refused.

**Reproduced (allowed on `feat` and `main`):**
- `echo 'git push origin feat:main' > p; sh p`
- `echo 'terraform apply -auto-approve' > p && bash -e p`
- `echo 'git push origin feat:main' | tee p && sh p`
- `echo 'git push origin feat:main' > p.sh; cp p.sh q; sh q`

**Fix:** keep the raw first non-option operand separately, and compare it against `written` whatever its shape:
```ts
const operand = invocation.args.find((a) => !a.startsWith("-"));
const runs = [script, operand, sourced, ...];
```

### CR-A2-3: `xargs` in front of a wrapper runs the piped guarded command

**Location:**
- `.pi/extensions/safety/shell.ts:561-573`: for xargs, `runnerTexts` inspects only xargs's own words
- `shell.ts:700`: refused only when an interpreter follows

**Defect:** xargs appends stdin words to its command, so `xargs env` runs `env git push origin HEAD:main`. Any wrapper in `WRAPPER_GRAMMARS` works, as does xargs's own option parsing.

**Reproduced (allowed on `feat` and `main`):**
- `echo git push origin HEAD:main | xargs env`
- `echo git push origin HEAD:main | xargs nice`
- `echo git push origin HEAD:main | xargs timeout 60`
- `echo terraform apply -auto-approve | xargs command`
- `echo git push origin HEAD:main | xargs -0 sudo`

**Fix:** when xargs or parallel is piped, resolve wrappers over its command words with `resolveWrappers`. Then refuse if:
- nothing is left (the wrapper runs the stdin words), or
- what is left is a guarded verb or interpreter, or
- any other segment of the pipeline mentions a guarded verb.

### CR-A2-4: Programs that take a command string as an option are not shell runners

**Location:** `.pi/extensions/safety/shell.ts:30-34` (`SHELL_RUNNERS`)

**Defect:**
- The guarded verb is fully visible in the arguments.
- `runnerTexts` returns `undefined` for these programs, so nothing inspects those arguments.
- None of them is in the Known bypasses table.

**Reproduced (allowed on `feat` and `main`):**
- `awk 'BEGIN{system("git push origin feat:main")}'` (also `gawk`)
- `sed -n '1e git push origin feat:main' package.json` (the GNU `e` command)
- `tar -cf /dev/null --to-command='git push origin feat:main' x`
- `rsync -e 'git push origin feat:main #' a b:c`
- `bat --paging=always --pager='git push origin feat:main' README.md`
- `less '+!git push origin feat:main' README.md`
- `vim -c '!git push origin feat:main' -c q`
- `make --eval='x:;git push origin feat:main' x`
- `sort --compress-program='git push origin feat:main' x`

`awk` and `sed` are everyday tools for a coding agent, so a cheap model reaches this form without any intent to evade.

**Fix:** add the following to `SHELL_RUNNERS` and `COMMAND_TEXT_RUNNERS` (whole segment text), so a guarded verb anywhere in their arguments refuses:
- `awk gawk mawk nawk busybox-awk`
- `tar` (only with `--to-command`, `-I`, `--use-compress-program`, `--checkpoint-action`; an unconditional entry would refuse `tar` with a guarded word in a file name)
- `rsync`, `bat`, `less`, `more`, `man`, `vi`, `vim`, `nvim`, `emacs`, `make`, `gdb`
- `sort` (only with `--compress-program`)
- `sed` (any script containing an `e` command, or simply any guarded verb in its arguments)

### CR-A2-5: A root-relative MSYS spelling defeats every home-anchored read rule and the search-root check

**Location:** `.pi/extensions/safety/paths.ts:158-165`: `rewriteMsysDrivePrefix` runs before the cwd join and before `collapseSegments`

**Defect:**
- `/./c/Users/x` and `/tmp/../c/Users/x` do not match `^/[A-Za-z](/|$)` at rewrite time.
- They collapse afterwards to `/c/Users/x` with root `/`, which never equals the drive root `C:` that `home` uses.
- A relative path after `cd /` is joined to `/` after the rewrite, with the same result.
- In Git Bash every one of these spellings is `C:\Users\...`.

**Reproduced (allowed on `feat` and `main`):**
- `cat /./c/Users/tester/.ssh/id_rsa`
- `cat /tmp/../c/Users/tester/.ssh/id_rsa`
- `cat /./c/Users/tester/.pi/agent/auth.json`
- `cp /./c/Users/tester/.ssh/id_rsa k && cat k`
- `cd /tmp/.. && cat c/Users/tester/.ssh/id_rsa`
- `cd / && cat c/Users/tester/.ssh/id_rsa`
- `grep -r PRIVATE /./c/Users/tester` (CR-A-4 reopened)

The `read` and `grep` tools are also allowed for `/./c/...`. On Windows, Node and rg resolve that path to `C:\c\...`, so only bash is exploitable.

**Fix:** apply the MSYS drive rewrite **after** joining and collapsing, and apply it to the collapsed root-`/` form:
```ts
const rooted = isAbsolutePath(slashNormalized) ? slashNormalized : joinWithCwd(ctx.cwd, slashNormalized);
return collapseSegments(rewriteMsysDrivePrefix(collapseSegments(rooted)));
```
Add corpus rows for `/./c/...`, `/tmp/../c/...` and `cd / && cat c/...`.

### CR-A2-6: The `cd` model ignores `CDPATH` and the `pushd` stack

**Location:** `.pi/extensions/safety/shell.ts:518-524`

**Defect:**
- **`CDPATH`.** A relative `cd` target that does not start with `./` or `../` is resolved through `CDPATH` by bash. The guard resolves it against the previous directory.
- **`pushd +N` and `pushd -N`.** These rotate the directory stack. `+1` does not start with `-`, so it is taken as a literal directory named `+1`.
- **Bare `pushd`.** It swaps the top two stack entries, but the code models it as `cd ~`.

**Reproduced (allowed on `feat` and `main`):**
- `CDPATH=~ cd .ssh && cat id_rsa`
- `export CDPATH=~; cd .ssh; cat id_rsa`
- `pushd ~ && pushd /c/repo && pushd +1 && cat .ssh/id_rsa`
- `pushd ~/.. && pushd /c/repo && pushd && cat tester/.ssh/id_rsa`

**Fix:**
- Treat as unknown (`known: false`):
  - a `pushd` target starting with `+` or `-`
  - a bare `pushd`
  - any `cd`/`pushd` whose literal target does not start with `/`, `~`, `./`, `../` or a drive, when `CDPATH` is assigned or exported anywhere in the script, or when it carries a `CDPATH=` prefix
- Better, treat every such relative `cd` as unknown unless it starts with `./` or `../`, because an inherited `CDPATH` cannot be seen.
- Once the target is unknown, the existing relative-path refusal applies.

## Warnings

### WR-A2-1: Protected branches can still be moved or committed to through a name or a switch the guard does not model (WR-A-4 variants)

**Location:**
- `.pi/extensions/safety/git.ts:260-279` (`protectedRefWrite` has no `worktree` or `rebase` case)
- `git.ts:282-288` (`switchTarget`)
- `git.ts:161-166` (`worktree` is an unconditional read)

**Reproduced:**

| Command | `feat` | `main` |
|---|---|---|
| `git worktree add -B main ../wt feat` (resets `main` to `feat`) | allow | **allow** |
| `git switch --track origin/main && git commit -am x` (creates local `main` and switches to it) | allow | block |
| `git checkout -t origin/main && git commit -am x` | allow | block |
| `git checkout @{-1} && git commit -am x` (`@{-1}` may be `main`) | allow | block |
| `git rebase feat main` (switches to `main`, then rewrites it) | allow | block |
| `git rebase --onto feat HEAD~1 main` | allow | block |

**Reasoned, not probed with real git:** `git worktree add ../wt main && cd ../wt && git commit -am x` on `feat`. The commit's dir is `../wt`, which does not exist when the command is evaluated. `currentBranch` therefore returns `DETACHED_HEAD`, and the commit lands on `main` through the shared refs.

**Fix:**
- In `protectedRefWrite`:
  - `worktree add` with `-b`/`-B` naming a protected branch blocks.
  - `worktree add <path> <protected>` followed by any later write in the same command sets `switched`.
  - `rebase` with a second positional, or `--onto` with a final positional, that names a protected branch blocks.
- In `switchTarget`:
  - `--track`/`-t <remote>/<b>` yields `<b>`.
  - `@{-N}` and any `@{...}` form yield `"-"`.

### WR-A2-2: git subcommands, interpreters and xargs write detonation targets and guard code without path classification

**Location:**
- `.pi/extensions/safety/policy.ts:373`: only `writeOperands` and redirects are write-classified
- `shell.ts:627-662`

**Reproduced (allowed on `feat`):**
- `git checkout feat -- .gitlab-ci.yml`
- `git restore --source=HEAD~3 .pi/extensions/safety`
- `git apply x.patch`
- `python -c "open('.git/hooks/pre-commit','w').write('x')"`
- `rg -l TODO | xargs sed -i 's/TODO/DONE/'`

**Why it matters:** CR-A-7 made extension-code writes `ask`. In this checkout, `git restore`/`git checkout <old> -- .pi/extensions/safety` rolls the guard back to an earlier, weaker revision. The user-scope stub then loads that revision in every repository on the machine at the next start. Interpreter writes are not in the Known bypasses table.

**Fix:**
- For `git checkout <tree-ish> -- <paths>`, `git restore`, `git apply` (without `--check`) and `git am`, classify each pathspec operand with `classifyPathWrite`. For `apply`/`am`, which name no paths, treat them as `ask` when the project has `.pi/extensions`.
- Run xargs's command words through `writeOperands` as a sed/tee/cp destination guess, or refuse `xargs` with a writer.
- Publish "an interpreter's own file writes" as a Known bypasses row next to EV-210.
- Longer term, have the stub pin a content hash of the guard.

### WR-A2-3: A full run still creates two delivery paths when a git package is already configured

**Location:** `bin/bootstrap.sh:1153-1155`; the check is at `:945`

**Defect:**
- `report_delivery_paths` fails only when `git.length > 0 && stub` exists.
- `run_full` calls it **before** `install_safety_extension`. On a machine whose only delivery path is the user-level git package, the check passes because there is no stub yet. The next line then writes the stub.
- The result is the two diverging copies the check exists to prevent. The second run fails, by which time the machine is already in that state.

**Fix:** in `run_full`, fail when any user-level git package of this repo is configured, because the stub is about to be written. Pass a flag:
```sh
KYPI_DP_WILL_WRITE_STUB=1 report_delivery_paths   # and in the node: const stub = existsSync(...) || process.env.KYPI_DP_WILL_WRITE_STUB === "1";
```

### WR-A2-4: Any relative argument after `cd "$VAR"` is refused, including words that are not paths

**Location:** `.pi/extensions/safety/policy.ts:348-351`; `shell.ts:521`

**Reproduced (blocked on both heads):**
- `cd "$D" && npm test`
- `cd "$HOME/projects/x" && npm test`

`echo done` after an unknown `cd` is blocked too. The check counts every non-flag word as a path, so `test`, `run` and `build` are refused.

**Why it matters:** this is an accepted false positive in REVIEW-FIX-A, but it lands on one of the most common shapes a model writes in a multi-package repo. The likely learned response is `cd` plus an absolute path, or abandoning the `cd`, which is no safer.

**Fix:**
- Expand `$HOME`/`${HOME}` prefixes in `cd` targets (the canonicaliser already understands them).
- For a target that is still unknown, classify relative arguments against the session cwd **and** home, as iteration 1 proposed, instead of refusing outright. Refuse only an argument that names an existing sensitive path in either location, or keep the refusal only for read-capable executables (`cat`, `less`, `cp`, `tar`, `grep`, ...).

### WR-A2-5: On a protected HEAD the model cannot branch off or stash

**Location:** `.pi/extensions/safety/git.ts:147-172` (the read table), `:601-607` (unclassified blocks)

**Reproduced (blocked on `main`):**
- `git checkout -b feat2`
- `git switch -c feat2`, which follows by inspection, because neither `checkout` nor `switch` is in either table
- `git stash`
- `git checkout HEAD~1 -- file.ts`

**Defect:** "create a feature branch first" is exactly the recovery a cheap model should take when it finds itself on `main`, and it is refused. The block message ("add a read-table fixture") tells the model nothing actionable.

**Fix:** add read-table rows for:
- `checkout -b|-B <new>` and `switch -c|-C <new>` whose new name is not protected (`protectedRefWrite` already refuses a protected name)
- `stash` / `stash push` (stash does not move the branch)

The block reason should also name the remedy ("create a branch: git switch -c <name>").

### WR-A2-6: `xargs <interpreter> <script-or-flag>` is refused as `generated-script`

**Location:** `.pi/extensions/safety/shell.ts:700-701`

**Reproduced (blocked on both heads):**
- `find . -name '*.py' | xargs python -m py_compile`
- `git diff --name-only | xargs node scripts/lint.mjs`
- `ls *.sh | xargs -n1 bash -n`

**Defect:** xargs passes stdin words as **arguments**, so `xargs node scripts/lint.mjs` runs a named script file over a file list. The rule refuses any interpreter name after xargs.

**Fix:** apply `interpreterScript` to the xargs tail, `{ executable: tail[0], args: tail.slice(1) }`. Refuse only when it returns `"-"` (no script) or when its inline flag is the last word (`xargs sh -c`, where the first stdin word becomes the code). Combine this with CR-A2-3.

### WR-A2-7: `cp .env.example .env` is refused as a secret read

**Location:** `.pi/extensions/safety/policy.ts:356-366`: every argument, write destinations included, goes through `classifyPathRead`

**Reproduced (blocked on both heads):** `cp .env.example .env`, the canonical first step of almost every project's setup. By contrast, `echo 'API_URL=x' >> .env` is allowed.

**Fix:** exclude the operands `writeOperands(invocation)` returns from `reads` when the executable is `cp`/`mv`/`install`/`ln`/`tee`/`touch`. They are still write-classified by `classifyShellWrites`. A `.env` write is not a secret read.

### WR-A2-8: Plan mode admits `bat --pager <program>`

**Location:** `.pi/extensions/plan-mode/read-only.ts:16-19` (`bat` is in `ALWAYS_READ_ONLY`)

**Defect:** `bat --paging=always --pager='<cmd>' file` runs `<cmd>` as its pager. The same goes for `BAT_PAGER`/`PAGER`, but an assignment prefix in plan mode is a separate question. Plan mode is meant to be a read-only boundary. CR-A2-4 shows the safety layer also allows it.

**Confidence:** medium. This comes from the bat documentation, not execution; bat may skip the pager when stdout is not a TTY, but `--paging=always` forces it.

**Fix:** move `bat` to `ARGUMENT_RULES` and deny `--pager` (and `--pager=`) and `--paging=always`. Also reconsider `printenv` in `ALWAYS_READ_ONLY`: the safety layer already blocks it, and it should not appear on a list named "read-only" as if it were harmless.
