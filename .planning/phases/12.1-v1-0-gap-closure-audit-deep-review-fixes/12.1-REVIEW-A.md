# Phase 12.1: Code Review Report, Part A (Safety)

**Reviewed:** 2026-10-13
**Depth:** deep
**Files Reviewed:** 28
**Status:** issues_found

## Summary

Method: I read every file in scope. pi-subagents 0.76.1 (`~/.pi/agent/npm/node_modules/pi-subagents`) and Pi 1.1.0 (`node_modules/@earendil-works/pi-coding-agent/dist`) were checked at the seams. Every reproduction marked "Reproduced" came from one probe script. The probe imported the real `evaluate()` from `.pi/extensions/safety/policy.ts`, using `node` 24's built-in type stripping, and ran in the foreground. Its facts were cwd `C:/repo`, home `C:/Users/tester`, protected `main`/`master`, push-protected `+staging`, and `remote.origin.url` configured. Each case ran twice, with `currentBranchFor` returning `feat` and then `main`. No vitest run was made.

The C-1..C-3 fixes hold for the forms they name: brace expansion, `-c alias.*`, `send-pack`, `trap`/`source`, and `git-push` executables. The C-4 fix also holds. pi-subagents binds in-process children with `mode: "print"` (`child-session.js:444-445`), so `canConfirm` refuses there. Resume reuses the persisted required-extension snapshot (`async-resume.js:312-314`).

Three problems remain:
- **Push and infra bypasses still exist, and they need no obfuscation.** Piping a literal command into `sh` works, and so do git's own command-running options. On `main`, `git rebase <upstream>` is classified as a read.
- **The secret-read layer has four ways around it.** Paths are resolved against the session cwd, never the `cd`/`env -C` cwd. Recursive bash searches from `~` are not root-checked. Directory 8.3 names exist on this machine. Bash writes are never path-classified, so every "detonation target" is writable through `>`, `cp` or `tee`.
- **The guard can be disabled.** It does not protect its own source or extension directories. The user-scope stub fails open when the import throws.

## Critical

### CR-A-1: Piping a literal guarded command into a shell is allowed on every branch

**Location:**
- `.pi/extensions/safety/shell.ts:509-521` (`runnerTexts`)
- `shell.ts:533-542` (`findShellRunnerDenial`, `carriesVerbAcrossSegments`)

**Defect:**
- A shell runner with no script operand reads its script from stdin. `runnerTexts` then examines only the runner's own segment text (`sh`), never the pipeline segment that produces the script.
- `carriesVerbAcrossSegments` taints other segments only for `trap alias hash enable fc source .`, not for `sh`/`bash`/`python`, which read stdin.
- So the guarded verb is fully visible in the parsed command, and the guard still allows it. This is not EV-41, which relies on a base64 payload.

**Reproduced (allowed on both `feat` and `main`):**
- `echo 'git push origin feat:main' | sh`
- `echo 'terraform apply -auto-approve' | bash`
- `printf 'aws s3 rm s3://b --recursive' | sh`
- `echo 'git push origin feat:main' > x.sh; sh x.sh` (written and run in one command)

**Fix:**
- When any invocation is a `SHELL_RUNNERS` member whose script comes from stdin (no operand, `-`, or `-s`), refuse if `mentionsGuardedVerb` matches any invocation's text in the same command, the way `carriesVerbAcrossSegments` does.
- Apply the same cross-segment taint when a runner's script operand is a file that an earlier segment of the same command writes.
- Add both forms to the corpus as `BLOCKED` rows on `feat`.

### CR-A-2: git's own command-running options and subcommands bypass the push guard; `rebase <upstream>` on `main` is classified as a read

**Location:**
- `.pi/extensions/safety/git.ts:150-180`: the read table, including the `rebase` row at `:171-174`
- `git.ts:183-190`: `GIT_KNOWN_SUBCOMMANDS`
- `git.ts:529-531`: any known subcommand is allowed on a non-protected HEAD

**Defect:**
- The C-2 fix allow-lists subcommand names, but not the options that make those subcommands run a program. Plan mode already knows these options (`read-only.ts:227` `GIT_EXECUTING_OR_WRITING_FLAGS`, `:240` `-O`), but the safety layer does not reuse that list.
- The `rebase` read row is wrong. `git rebase <upstream>` rebases the **checked-out** branch onto `<upstream>`. Only `git rebase <upstream> <branch>` switches first, and then it rewrites `<branch>`. So `git rebase origin/main` on `main` rewrites `main`, and `--exec` runs arbitrary commands there.

**Reproduced:**

| Command | `feat` | `main` |
|---|---|---|
| `git submodule foreach 'git push origin HEAD:main'` | allow | block |
| `git bisect run sh -c 'git push origin HEAD:main'` | allow | block |
| `git rebase --exec 'git push origin HEAD:main' feat` | allow | **allow** |
| `git fetch --upload-pack='sh -c x' origin` | allow | **allow** (arbitrary program) |
| `git grep -O'sh -c x' needle` | allow | block |
| `git ls-remote --upload-pack='sh x.sh' .` | allow | block |
| `git clone --upload-pack='sh x' x y` | allow | block |
| `git log --output=/c/Users/tester/.bashrc` | allow | **allow** (writes `~/.bashrc` outside the project; `--format` controls the content) |

**Fix:**
- Before the branch check, refuse on every branch:
  - `--upload-pack`, `--receive-pack`, `--exec`, `-x`, `--output`, `--ext-diff`, `-O`/`--open-files-in-pager` (bundled too)
  - `submodule foreach`
  - `bisect run`
  - `rebase --exec`/`-x` and `-i` (whose todo `exec` lines run commands)
- Put the shared list in one module that both `git.ts` and `read-only.ts` import.
- Move `rebase` with a positional argument out of the read table. Every rebase form rewrites a branch, so it belongs in the write table.

### CR-A-3: Path arguments ignore `cd`, `pushd` and `env -C`, so secrets are readable by relative path

**Location:**
- `.pi/extensions/safety/policy.ts:95-96` (`canonicalOf` always resolves against `facts.cwd`)
- `policy.ts:247-256`
- `policy.ts:281-284`: redirect targets have the same problem

**Defect:**
- `CanonicalInvocation.cwdOverride` and `afterCd` are computed (`shell.ts:465-474`), but only the git branch lookup uses them.
- A relative argument after `cd ~` is resolved under the project. The home-anchored rules (`home-ssh`, `home-aws`, `git-credentials`, `docker-config`, `pi-auth`) therefore never match.
- A literal `cd ~` is not itself blocked, because `~` alone matches no read pattern.

**Reproduced (allowed on both branches):**
- `cd ~ && cat .ssh/id_rsa`
- `env -C /c/Users/tester cat .pi/agent/auth.json`

`cd ~ && cat .aws/sso/cache/*.json` follows the same path. The glob is judged by its directory, `C:/repo/.aws/sso/cache`, which matches nothing. A model debugging SSO could plausibly type this.

**Fix:**
- Resolve each argument and redirect target against `foldDirectories([facts.cwd, invocation.cwdOverride ?? "."])`.
- When `afterCd === "unknown"`, refuse any relative argument, or classify it against both the session cwd and `home`.
- Add corpus rows for `cd ~ &&`, `pushd ~ &&` and `env -C ~`.

### CR-A-4: A recursive bash search rooted at or above `$HOME` is never root-checked

**Location:**
- `.pi/extensions/safety/policy.ts:247-256`: bash args go through `classifyPathRead` only
- `policy.ts:324-337`: `isSensitiveSearchRoot` is wired only for the `grep`/`find`/`ls` tools

**Defect:** a bash argument naming `~` or one of its ancestors is a recursive root for `grep -r`, `rg`, `find`, `tar` and `cp -r`. It passes `classifyPathRead` because the directory itself matches no file pattern.

**Reproduced (allowed on both branches):**
- `grep -r PRIVATE ~`
- `rg --hidden -uu aws_secret_access_key ~`
- `grep -r token C:/Users`

Each of these prints the contents of `~/.ssh/id_*` and `~/.aws/credentials`.

**Fix:**
- In `evaluateInvocation`, also call `isSensitiveSearchRoot` on each non-flag argument, or at least on those of a recursive-capable executable (`grep -r/-R`, `rg`, `find`, `tar`, `cp -r`, `zip -r`, `du`), and block on true.
- `~`-or-ancestor roots must block.

### CR-A-5: 8.3 short names of credential directories are not recognised

**Location:**
- `.pi/extensions/safety/paths.ts:243`: `SHORT_NAME_ALIAS` is tested on the basename only
- `paths.ts:296-298`

**Defect:** only the last segment is checked for the 8.3 shape. On this machine, `dir /x C:\Users\Admin` shows `AWS~1 → .aws`, `SSH~1 → .ssh` and `PIC454~1 → .pi`. Node's `fs.existsSync("C:/Users/Admin/SSH~1")` returns true, and so does Git Bash `ls -d ~/SSH~1`.

**Reproduced (allowed on both branches):**
- `read {path: "C:/Users/tester/AWS~1/credentials"}`
- `cat ~/AWS~1/credentials`
- `cat ~/SSH~1/id_rsa`

**Fix:**
- Test every segment against `SHORT_NAME_ALIAS`, not only the basename.
- Better, resolve the long name in `buildFacts` through an impure, injected `longPathOf` that uses `fs.realpathSync.native` (which expands 8.3 names on Windows), and classify both spellings. That also removes the need for the false-positive-prone regex (WR-A-1).

### CR-A-6: Bash writes are never path-classified, so every detonation target is writable from bash

**Location:**
- `.pi/extensions/safety/policy.ts:245-256`: bash args use `classifyPathRead` only
- `shell.ts:234`: only `<`, `<>` and `<&` targets are collected
- `paths.ts:341`: the comment claims "Applies to bash and the `write`/`edit` tools", which is false

**Reproduced (allowed on `feat`):**
- `echo 'git push origin feat:main' > .git/hooks/pre-commit` (the next allowed `git commit` runs it)
- `cp x.sh .git/hooks/pre-push`
- `echo x >> ~/.bashrc` (runs in the user's own terminal, holding live AWS SSO credentials)
- `echo x > .gitlab-ci.yml`
- `tee .pi/agents/x.md < y` (D-03 says agent-definition directories are protected paths)
- `echo x > /c/Windows/x` (outside the project)

**Why it matters:** this is a mistake a cheap model makes routinely. `echo 'export PATH=...' >> ~/.bashrc` is an everyday fix, and its effect outlives the session.

**Fix:**
- Collect `>`, `>>`, `>|`, `&>` and `<>` targets in `scanScript`, and classify them with `classifyPathWrite`.
- For the destination operand of `cp`, `mv`, `tee`, `install`, `ln`, `dd of=` and `sed -i`, at least run `DETONATION_TARGETS`.
- Correct the comment at `paths.ts:341`.

### CR-A-7: The guard does not protect its own code or the extension directories

**Location:**
- `.pi/extensions/safety/paths.ts:342-414`: `DETONATION_TARGETS` has no `.pi/extensions` row

**Reproduced (`write` tool, allowed on both branches):**
- `C:/repo/.pi/extensions/safety/policy.ts`
- `C:/repo/.pi/extensions/evil/index.ts`

**Defect:**

- In this checkout it is worse. The user-scope stub imports `<checkout>/.pi/extensions/safety/index.ts` by absolute path (`bin/bootstrap.sh:862`). So an agent session here can rewrite the guard that every repository on the machine loads.
- `~/.pi/agent/extensions/**` is also missing. That covers the stub itself and `subagent/config.json`, whose `worktreeSetupHook` is a program pi-subagents runs. Both are reachable whenever a session's projectRoot is `$HOME`.

**Fix:**
- Add detonation rows for:
  - `projectPath(".pi", "extensions")`
  - `projectPath(".pi", "npm")`
  - `homePath(".pi", "agent", "extensions")`
  - `homePath(".pi", "agent", "npm")`
  - `homePath(".pi", "agent", "models.json")`
- In this repo, edit the guard from outside Pi. If agent edits here are wanted, gate them behind a `confirm`, never an `allow`.

### CR-A-8: The user-scope safety stub fails open when the import or the factory throws

**Location:** `bin/bootstrap.sh:854-864` (the generated stub)

**Defect:**
- The stub blocks every tool call only when the target file is **missing**.
- If `await import(...)` or `mod.default(pi)` throws, the throw escapes the factory. Pi 1.1.0 `loadExtension` turns that into `{ extension: null, error }` and discards the half-registered load (`dist/core/extensions/loader.js:515-538`). The session then continues with no guard.
- Triggers include a syntax error mid-edit in the checkout, a `git checkout` of a ref with a different API, `unbash` missing after `npm ci`, and CR-A-7.
- Because the stub is the single, machine-wide delivery path, every repository on the machine loses the guard at once. Headless modes show nothing.

**Fix:**
```ts
export default async function (pi) {
  let failure = existsSync(TARGET) ? undefined : "missing";
  if (failure === undefined) {
    try { const mod = await import(TARGET); await mod.default(pi); }
    catch (e) { failure = e instanceof Error ? e.message : String(e); }
  }
  if (failure !== undefined) {
    pi.on("tool_call", () => ({ block: true, reason: `ky-safety failed to load (${failure}); every tool call is blocked` }));
  }
}
```
Add a `bootstrap-safety-stub` test that points the stub at a target that throws.

## Warning

### WR-A-1: `HEAD~N` and every `name~N` argument are refused as 8.3 short names

**Location:** `.pi/extensions/safety/paths.ts:243, 296-298`, which reaches every bash argument through `policy.ts:247-256`

**Reproduced (blocked on both branches):**
- `git log HEAD~1`
- `git diff HEAD~3 --stat`
- `git show main~2`
- `git rebase -i HEAD~3`
- `git checkout HEAD~1 -- file.ts`

`notes~1.md` and `file~2` also match.

**Defect:** these are some of the most common commands a coding agent runs. A cheap model then either loops on the block or learns `HEAD^^^`. The rule mostly blocks things that are not paths.

**Fix:**
- Skip the short-name rule for an argument that has no `/` and no `.` extension and matches git revision syntax (`^[\w./-]+~\d*$`, `@~N`).
- Better, use the realpath long-name expansion from CR-A-5 and apply the rule only to paths that exist.

### WR-A-2: Regex pattern arguments are glob-classified as file names

**Location:** `.pi/extensions/safety/policy.ts:184, 251`; `paths.ts:504-511`

**Reproduced (blocked on both branches):**
- `rg '.e*' src`
- `grep -rn '.*env' .`

By the probe-name logic, `rg 'id_*'`, `rg 'credential*'` and `grep 'auth*'` also block, because they match `id_rsa`, `credentials` and `auth.json`.

**Defect:**
- The first positional of `grep`/`rg`/`ag`/`sed`/`awk` is a pattern, not a path, yet any `*`, `?` or `[` makes it a glob.
- Related: `~/x.sh` is refused as `non-literal-command-name`, while `bash ~/x.sh` is allowed. That teaches the model the wrapper form.

**Fix:**
- For known search tools, skip glob classification of the pattern operand (the first non-flag argument, or the value of `-e`/`--regexp`), while still classifying the path operands.
- Expand a leading `~/` in command position before the non-literal check.

### WR-A-3: Exported `GIT_*` variables bypass the git environment check

**Location:**
- `.pi/extensions/safety/policy.ts:181-182, 210-213`: only prefix and wrapper assignments are seen
- `shell.ts:467`

**Reproduced (allowed):**
- `export GIT_DIR=/c/mainrepo/.git; git commit -am x` on `feat` commits into another repository's checked-out `main`, while the branch check reads the cwd's `feat`.
- `export GIT_CONFIG_PARAMETERS="'core.fsmonitor'='sh x.sh'"; git status` (both branches) runs a program.
- `export GIT_CONFIG_GLOBAL=/tmp/evil; git status` and `declare -x GIT_WORK_TREE=/x; git status` (both branches).

**Fix:** when any git invocation is present, treat these as a non-formatting git assignment (block):
- `export`, `declare -x`, `typeset -x`, `readonly -x` or `local -x` of a `GIT_*` name
- `set -a` / `set -o allexport` followed by any `GIT_*=` assignment-only statement

### WR-A-4: The protected branch can be moved locally from a feature branch

**Location:** `.pi/extensions/safety/git.ts:150-158` (`fetch`/`branch` match all arguments) and `:529-531` (everything allowed off a protected HEAD)

**Reproduced:**

| Command | `feat` | `main` |
|---|---|---|
| `git branch -f main feat` | allow | allow |
| `git branch -M feat main` | allow | allow |
| `git fetch . feat:main` | allow | allow |
| `git switch main && git commit -am x` | allow (the branch is read once, before `switch` runs) | n/a |

`git fetch --update-head-ok . feat:main` is not in the probe, but the code path is the same.

**Defect:** the push rule still blocks `push :main`. However, the user's own later `git push` from `main` deploys whatever the agent placed there. The "no write while HEAD is protected" invariant is evaded by naming `main` instead of being on it.

**Fix:**
- Treat as writes to a protected branch:
  - a `branch`/`fetch`/`checkout -B`/`switch -C`/`update-ref` whose ref operand or refspec destination is protected
  - `branch -f/-M/-C/-D`
- Treat a `checkout`/`switch` followed by a write in the same command like `afterCd`: if it names a protected branch, refuse the later writes.

### WR-A-12: The approval dialog has no timeout and does not use `canConfirm`

**Location:** `.pi/extensions/safety/index.ts:279-285`

**Defect:**
- `approve_ky_command` calls `ctx.ui.select` with no `timeout`, and gates only on `ctx.hasUI`.
- In `rpc` mode with a front-end that never answers dialogs (a scripted RPC client), the agent hangs indefinitely.
- The push confirm and the management confirm use `canConfirm` plus `CONFIRM_TIMEOUT_MS`, so the three approval paths have inconsistent fail-closed semantics.

**Fix:** gate on `canConfirm(ctx)` and pass `{ timeout: CONFIRM_TIMEOUT_MS }` to `select`. A timeout should yield `undefined` and therefore a refusal.

### IN-A-1: A failed child-guard registration is silent

### IN-A-2: The management confirm truncates the definition shown to the human
