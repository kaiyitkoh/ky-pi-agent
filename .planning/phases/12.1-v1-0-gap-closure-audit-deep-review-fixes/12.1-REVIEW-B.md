# Phase 12.1: Code Review Report, Part B (workflows, quality, review)

**Reviewed:** 2026-10-13T08:12:51Z

## Summary

`agent_settled` is used correctly against Pi 1.1.0. It is declared as `{ type, aborted }` in `types.d.ts:777-781`, emitted once from the `finally` of `_runAgentPrompt` (`agent-session.js:1412`, `:684-691`), and handlers are awaited. The empty-commit reject, the fail-closed `currentSha`/`currentTree` in the `/quick` settle, and the aborted-run disarm all behave as described.

The D-01 gate still has holes:
- "Produced a commit" is never checked. Any HEAD movement passes, and a test locks that behaviour in.
- `/quick` gates the working tree, not the commit.
- The model can rewrite the "declared verification" for later `/execute` tasks during a run.
- The review stop order lets a classification override a surviving BLOCKER.

Several gate legs can also report PASS or "no changed file" when that is not true. The main triggers are a subdirectory cwd, ESLint-ignored files, and solution-style tsconfigs.

Tests were not run (CPU budget).

## Critical

### CR-B-01: The evidence gate accepts a HEAD move that made no commit

**File:** `.pi/extensions/workflows/evidence.ts:74-105` (`gateCompletion`). It also governs `.pi/extensions/workflows/settle.ts:48` and `.pi/extensions/execute/index.ts:156`.

**Defect:** D-01 says a task passes only when it "produced a commit". The predicate checks only three things:
- `headSha !== baseSha`
- `headTree !== baseTree`
- some record exists at the new HEAD

It never checks that `baseSha` is an ancestor of HEAD, or that HEAD is a new commit. The safety layer allows `git checkout`, `git switch` and `git reset --hard <sha>` on a feature branch, because `GIT_WRITE_SUBCOMMANDS` only blocks on protected branches. Any of them moves HEAD to an existing commit with a different tree. The tool call that moves HEAD is recorded at the new SHA, so the "evidence at HEAD" condition is met by the same call.

`tests/integration/quick-workflow.test.ts:1067-1150` ("case 9") asserts `verdict === "accept"` for `git checkout --detach HEAD^`, so this behaviour is locked in by a test.

**Scenario:**
1. `/quick fix X` runs on `feature/a`, which already has commits.
2. The cheap model gets stuck and runs `git reset --hard HEAD~1`, or `git checkout HEAD^`.
3. HEAD moved and the tree changed, so the run is ACCEPTED.
4. The `/quick` settle then gates `base..HEAD`, which is a diff of the *reverted* commit. It is read from disk, which now matches HEAD~1, so the gate passes. Nothing was committed.

In `/execute` the same move to an earlier task's commit is accepted for a later task. The drift check sees only allowed files, and the verification command passes at the old commit. PROGRESS then records T00N at T00(N-1)'s SHA.

**Fix:** In `endRun`, or in both settle callers before `gateCompletion`, require that `base` is a strict ancestor of HEAD:
```ts
const anc = spawnSync("git", ["merge-base", "--is-ancestor", baseSha, headSha], { cwd, shell: false });
const ahead = spawnSync("git", ["rev-list", "--count", `${baseSha}..${headSha}`], { cwd, encoding: "utf-8", shell: false });
if (anc.status !== 0 || Number(ahead.stdout.trim()) < 1)
  return { ok: false, reason: `HEAD ${headSha} is not a new commit on top of ${baseSha} -- a checkout/reset is not a commit` };
```
Pass the result into `gateCompletion` as a boolean so the function stays pure. Flip case 9 to expect `reject`.

### CR-B-02: `/quick` gates the uncommitted working tree, not the commit

**File:** `.pi/extensions/workflows/settle.ts:51-60`. The cause is in `.pi/extensions/quality/index.ts:214, 223, 234-235`.

**Defect:** `runChangeGateStage` reads every changed file from disk (`existsSync`/`readFileSync(join(cwd, p))`), and runs `tsc --noEmit` and `eslint` on the working tree. `/execute` refuses a dirty tree before it gates (`execute/index.ts:169-170`). `/review` does the same (`review/index.ts:227-228`). `settleQuickRun` has no such check. `docs/WORKFLOWS.md:222` and `:305` claim the `/quick` gate runs "on `base..HEAD`", which is not true.

**Scenario:**
1. The model commits `a.ts` with a type error.
2. It then fixes `a.ts` on disk and does not amend the commit.
3. At settle, `changed = [a.ts]`, and tsc, lint and the anti-pattern scan all read the fixed file. The result is PASS.

The run is accepted with "HEAD moved ... with a changed tree", but the committed tree fails typecheck. The reverse also happens: an uncommitted half-edit makes a correct commit fail. This is the "accept work that was never committed" case asked about in the review brief.

**Fix:** In `settleQuickRun`, before calling `runChangeGateStage`, reject when `uncommittedPaths(cwd) !== ""`, as `/execute` does:
```ts
const dirty = uncommittedPaths(cwd);
if (dirty !== "") { writeEvidenceRow(cwd, { verdict: "reject", reason: `working tree is not the commit (${dirty})`, ... }); return input.notify(...); }
```
A better long-term fix is to make `runChangeGateStage` read sources via `git show <head>:<path>`. Also correct both lines in `docs/WORKFLOWS.md`.

### CR-B-03: The model can rewrite the "declared verification command" of later `/execute` tasks during a run

**File:** `.pi/extensions/execute/index.ts:62, 88-89, 125`; `.pi/extensions/execute/ledger.ts:18-21`.

**Defect:** Every `/execute` re-reads `PLAN.md` from `.pi/work/<slug>/` and takes `task.verificationCommand` from it. The signed ledger pins only the *file allowance* (the `base` row's `allowance`). It does not pin the task list or the verification commands. `.pi/work/` is not a protected path (`safety/paths.ts` protects `kypi-ledger` and the agent directories only). It is git-excluded by `ensureHarnessIgnored`, so edits there never show up in `changedFiles` or the drift check.

**Scenario:**
1. During the run for T001, the executor model edits `.pi/work/<slug>/PLAN.md` and sets T002's verification to `true` (or `echo ok`, or `npm test -- -t nothing`).
2. `validatePlan` still passes on the next `/execute`. The allowance is unchanged, so no `--rebase-base` prompt appears.
3. T002 is accepted once `true` exits 0.

The model can also delete tasks that are not yet recorded. `historyMismatch` only checks the tasks still present in `plan.plan.tasks`. This defeats D-01's "declared verification passes" without touching any committed file.

**Fix:** At the first `/execute`, pin a hash of the validated PLAN task list (id, path, verificationCommand) in the signed `base` row. Refuse any later mismatch the same way an allowance change is refused (`execute/index.ts:84-86`), unless the user re-pins with `--rebase-base` and sees a diff. Alternatively, make `.pi/work/*/{SPEC,PLAN}.md` write-protected while an `/execute` run is armed.

### CR-B-04: A "symptomatic" or "workaround" classification turns a surviving BLOCKER into an approvable stop and hides it

**File:** `.pi/extensions/quality/verdict.ts:30-58` (`decideWorkflowStop`); the effect lands at `.pi/extensions/review/index.ts:285-292`.

**Defect:** The classification checks (1) and (2) return `needsApproval: true` *before* the surviving-BLOCKER check (3). When the reviewer returns `classification: "workaround"` together with BLOCKER findings that survived refutation:
- the stop is approvable;
- `stop.reason` names only the classification, so the `ctx.ui.confirm("Open the MR anyway?")` text never mentions the BLOCKERs.

`docs/WORKFLOWS.md:307` says "a surviving BLOCKER still stops without approval", which is false. The comment on rule (3) only explains why classification must fire when there are *no* BLOCKERs. That does not require BLOCKERs to lose priority.

**Scenario:** A cheap reviewer often labels a fix "workaround". It also reports a BLOCKER (for example, an unhandled null on the main path), and refutation upholds it. The user is asked "Open the MR anyway?" with only the workaround justification shown, approves, and the MR opens with a known BLOCKER.

**Fix:** Evaluate surviving BLOCKERs first, and keep the classification stops for the no-BLOCKER case:
```ts
const surviving = review.findings.filter((f) => f.severity === "BLOCKER");
if (surviving.length > 0) return { stop: true, needsApproval: false, reason: ... };
if (review.classification === "symptomatic") ...
if (review.classification === "workaround") ...
```
Add a test with classification `workaround` plus one upheld BLOCKER that expects `needsApproval: false`.

## Warning

### WR-B-01: An unreadable HEAD at the `/execute` settle leaves the shared evidence run armed until restart

**File:** `.pi/extensions/execute/index.ts:152-156`

**Defect:** `disarmExecuteRun()` runs first. Then `currentSha(cwd)` and `currentTree(cwd)` run inside the `try`. Both throw by design. On a throw, `endRun` is never called, so the `__kypiQuickRun` slot stays armed.

From then on:
- the workflows `tool_execution_end` handler keeps recording every ordinary tool call;
- every later `/quick` and `/execute` is refused with "a turn is already in flight", because `isRunArmed()` is true;
- the workflows settle no longer disarms it, because the settle key is unset. Only `session_start` clears it.

`/quick` handles the same case correctly (`settle.ts:41-48`), and `docs/WORKFLOWS.md:94-98` promises "never leave ... permanently armed".

**Scenario:** A transient `index.lock`, or the model running `rm -rf .git/refs/...`. After that, both workflows are dead for the rest of the session with a misleading message.

**Fix:** Use `headShaOrEmpty(cwd)` plus a tree helper that does not throw, as `/quick` does. Or put `disarmRun()` in a `finally` whenever `endRun` was not reached.

### WR-B-02: A prompt that never starts leaves `/quick` and `/execute` armed, and the next unrelated turn settles them

**File:** `.pi/extensions/workflows/index.ts:46-48`; `.pi/extensions/execute/index.ts:123-126`

**Defect:** `pi.sendUserMessage` is fire-and-forget (`agent-session.js:2712-2719` catches the rejection and only emits an error). `prompt()` can return or throw *before* `_runAgentPrompt`, and then `agent_settled` is never emitted (`agent-session.js:1517-1631`). This happens when:
- no model is set;
- auth is missing or expired ("Authentication failed ... Run '/login'"). With Bedrock SSO this is routine.
- compaction is in progress;
- an `input` handler returns `handled`.

Both runs stay armed. The next ordinary turn's `agent_settled` then settles the `/quick` or `/execute` run with that turn's commits and tool results. That turn was never routed through the executor check, and it is exactly what the `isIdle` guard comment at `workflows/index.ts:39` / `docs/WORKFLOWS.md:61-69` is meant to prevent. `execute/index.ts:133` states this invariant ("must not settle some later turn") but only enforces it at `session_start`.

**Scenario:**
1. The SSO token has expired.
2. `/execute` arms the run, and the prompt throws.
3. The user runs `/login` and types "hi, what's the status".
4. That turn settles T003. If the model happened to commit and run the verification command, T003 is recorded.

**Fix:** Arm from a `before_agent_start` / `agent_start` handler keyed on a pending-arm token that the command sets. Or add a `turn_start` check that the first turn after arming carries the `/quick`/`/execute` text, and disarm otherwise. At minimum, have the settle refuse a run whose recorded `agent_start` count is zero.

### WR-B-03: Paths relative to the repo root are joined to a subdirectory cwd, so legs report "no changed file" and the reviewer sees every file as deleted

**File:** `.pi/extensions/quality/index.ts:214, 223`; `.pi/extensions/review/scope-drift.ts:81-82`; `.pi/extensions/execute/progress.ts:325-338`

**Defect:** `changedFiles` uses `git diff --name-only` without `--relative`, so the paths are relative to the git top-level. `runChangeGateStage` filters with `existsSync(join(cwd, p))`, and `readTouchedFiles` uses `join(cwd, path)`. When Pi is started in a subdirectory (common on the user's multi-stack monorepos, for example `services/api/`):
- every code file is filtered out;
- the anti-pattern and lint legs report UNAVAILABLE "no changed TypeScript/JavaScript file", although TS files did change;
- `/review` sends the reviewer `(deleted in this change)` for every touched file;
- the import graph is built from those placeholders.

The typecheck leg uses the unfiltered list, so the report contradicts itself.

**Scenario:** Run `/quick` from `apps/web` in a monorepo, with the change in `apps/web/src/x.ts`. The anti-pattern leg says nothing changed. In `/review`, the model is told all files were deleted and reviews blind.

**Fix:** Resolve paths against `git rev-parse --show-toplevel` (`join(top, p)`) in `runChangeGateStage`, `readTouchedFiles` and `showAt`'s callers. Alternatively, pass `--relative` and keep everything cwd-relative. Also look for the ESLint config from the top-level, not only in cwd (`quality/index.ts:161`).

### WR-B-04: The evidence log says "accept" for runs that were rejected or never gated

**File:** `.pi/extensions/workflows/evidence.ts:160-178`; `.pi/extensions/workflows/settle.ts:48-63`; `.pi/extensions/execute/index.ts:156-158`

**Defect:** `endRun` writes an `accept` row as soon as the SHA/tree predicate passes. Several later rejections then leave that row as the only or first record:
- `/execute` rejecting on `checkVerification` (the verification failed, or ran at the wrong SHA): the only evidence row is `accept`.
- `/execute` rejecting on dirty tree, drift HALT or gate failure: the only evidence row is `accept`.
- `/quick` with a throwing gate (`settle.ts:61-62`): the only row is `accept`.
- `/quick` with a failing gate: `accept` followed by `reject`.

Anyone auditing `evidence-*.jsonl` sees accepts for runs whose declared verification failed.

**Fix:** Split `endRun` into a pure "compute verdict and disarm" step and a single `writeEvidenceRow` call made by the caller *after* all checks (verification, dirty, drift, gate). Write exactly one row per run with the final verdict.

### WR-B-05: `/quick` accepts with no verification at all when no gate leg applies

**File:** `.pi/extensions/workflows/settle.ts:59-60`

**Defect:** For a Terraform, Python or docs change, every leg is UNAVAILABLE. The run is still ACCEPTED with an `info` notice and an `accept` evidence row. `/execute` treats the same situation as requiring `ctx.ui.confirm` (`execute/index.ts:180-182`). D-01 requires that "the declared verification passes", but for `/quick` that becomes a check of nothing. The user's main workload (AWS/Terraform) hits this path every time.

**Fix:** When `!gate.ranAny`, mark the evidence row as something other than `accept` (for example `unverified`), and notify at `warning` level. Or require `ctx.ui.confirm` as `/execute` does.

### WR-B-06: The lint leg reports PASS when ESLint linted nothing

**File:** `.pi/extensions/quality/index.ts:143-175`

**Defect:** `eslint -- <files>` exits 0 with only a "File ignored because of a matching ignore pattern" or "no matching configuration" warning when every file it is given is ignored. Typical cases are `.tsx` without a TS config block, or files under `ignores`. That exit is mapped to `{ status: "pass" }`. Config detection also misses:
- `eslint.config.mts` and `eslint.config.cts` (supported by ESLint 9);
- `package.json#eslintConfig`;
- configs in ancestor directories.

Each of these misses gives a misleading UNAVAILABLE reason. Point 5 of the brief asked whether the legs are truthful; this one is not.

**Fix:** Run with `--format json`. Report `pass` only when at least one result has no `fatal`/ignored message and `errorCount === 0`. Map all-ignored results to `unavailable`. Add the missing config names, and walk up to the git top-level.

### WR-B-07: The typecheck leg reports a vacuous PASS on solution-style tsconfigs

**File:** `.pi/extensions/quality/gates.ts:73-87`; `.pi/extensions/quality/index.ts:123-141`

**Defect:** `hasTsconfig` only checks that a file exists. A root `tsconfig.json` with `"files": []` and `"references": [...]` makes `tsc --noEmit` check zero files and exit 0, which is reported as PASS. This is the default layout of the Vite React/Vue templates and of many monorepos. Real type errors in the change are reported as "typecheck: PASS".

**Fix:** When the resolved tsconfig has `references` and an empty `files`/`include`, either run `tsc -b --noEmit`, or report `unavailable` with that reason. At minimum, run `tsc --listFilesOnly` and treat zero listed project files as `unavailable`.

### WR-B-08: An error in the design pass aborts `/review` after the paid correctness review, which contradicts its own contract

**File:** `.pi/extensions/review/index.ts:267-272`; `.pi/extensions/quality/design-review.ts:107-141`

**Defect:** The `runDesignReview` docstring says "An unusable reply yields no findings and a notice: the correctness review already stands." In practice:
- `runSingleShotRole` can throw (guard refusal, provider error, timeout);
- the throw propagates to the outer `catch` in `/review` (`:302`);
- `REVIEW.md` is not written, and the correctness review and refutation are lost.

Separately, `parseFindings` drops the whole list when a single item is malformed. One bad `location` discards every valid design BLOCKER, and the only trace is a warning notice.

**Fix:** Wrap the call in `try/catch` and return `{ findings: [], notice: \`design pass failed: ${msg}\` }`. In `parseFindings`, drop and count individual malformed items instead of rejecting the list.

### WR-B-09: The MR audit row records a glab failure or timeout as `block`, including when the MR was actually created

**File:** `.pi/extensions/review/mr.ts:264-277`

**Defect:** `verdict = outcome.kind === "opened" ? "allow" : "block"`. A `failed` outcome is the classifier *allowing* the command and glab then running. That covers a non-zero exit and the `ETIMEDOUT` path, which `spawnExec` itself warns "may already have created the MR". Both are logged as a policy `block`. In the audit trail, an MR that may exist on GitLab shows up as a refused action.

**Fix:** Log the classifier verdict (`allow`) for anything past classification, and put the outcome in `reason`. Or add a distinct outcome field such as `exec_failed`/`timeout`. Keep `block` for `refused` only.

### WR-B-10: `/quick` leaves harness logs and pre-existing changes exposed to `git add -A` in the target repo

**File:** `.pi/extensions/workflows/index.ts:42-48`

**Defect:** `/execute`, `/grill` and `/review` call `ensureHarnessIgnored(ctx.cwd)`. `/quick` does not. Every `/quick` settle writes `<cwd>/.pi/logs/evidence-*.jsonl` into the work repo. The `/quick` brief also does not tell the model to stage explicit paths, while `/execute`'s brief does (`execute/index.ts:126`).

**Scenario:** On the next `/quick`, a cheap model runs `git add -A && git commit`. That sweeps in the harness logs, plus any uncommitted user work that was present at arm time. The result lands in a repo where `main` auto-deploys.

**Fix:** Call `ensureHarnessIgnored(ctx.cwd)` in the `/quick` handler before arming. Refuse to arm when the tree is dirty (which also supports CR-B-02). Add "stage only the files you changed (git add <path>...)" to the brief.

### WR-B-11: `localBin` runs `tsc`/`eslint` from any ancestor directory up to the filesystem root, outside the trusted project

**File:** `.pi/extensions/quality/index.ts:34-44`

**Defect:** The trust check (`resolveExec`) covers the project, but `localBin` walks past the git top-level up to `/`. The first `node_modules/.bin/tsc` it finds is spawned with `shell: true` on Windows. On a shared or temporary parent directory (for example `/tmp/node_modules/.bin/tsc` on macOS later, or a stale `~/node_modules`), a binary outside the trusted project is executed with the user's AWS session. `hasTsconfig` already stops at the git top-level, and `localBin` should apply the same limit.

**Fix:** Stop the walk at `git rev-parse --show-toplevel`, and use the same `stop` logic as `hasTsconfig`.

### IN-B-03: The design-signal parser loses track of the current file on quoted diff headers

**File:** `.pi/extensions/quality/design-review.ts:38`; `.pi/extensions/review/index.ts:252`

**Issue:** `git diff` runs without `-c core.quotePath=false`. A non-ASCII path, or a path with special characters, produces `diff --git "a/..." "b/..."`. The header regex does not match it, so `currentFile` stays on the previous file, and `publicInterfaceChanged` and loop-window resets are attributed to the wrong file.

**Fix:** Run the diff with `-c core.quotePath=false`, and handle the quoted header form.

### IN-B-04: Deleted, binary and truncated JS/TS files appear in the import graph as "(no declared imports)"

**File:** `.pi/extensions/review/index.ts:257`; `.pi/extensions/quality/reviewer.ts:97-105`

**Issue:** `buildImportGraph` is given `t.contents`, and for these files that is placeholder text such as `(deleted in this change)`. The rendered graph then claims a measured "no declared imports" for a file that was deleted or was never read.

**Fix:** Leave placeholder entries out of the graph input, or render them as "(not read: deleted/binary/truncated)".

### IN-B-05: Aborted turns never use up the `/grill` and `/plan` budgets

**File:** `.pi/extensions/grill/index.ts:149-151`; `.pi/extensions/plan-ceremony/index.ts:128-130`

**Issue:** An aborted turn returns before `asked`/`turns` is incremented, so repeated Esc presses keep the workflow armed with no limit. The `before_agent_start` injection also stays active for every later turn. Edits to SPEC/PLAN made before the abort are re-gated on the next settle, so no gate is skipped. Only the budget is affected.

**Fix:** Count aborted turns toward the budget, or disarm after N consecutive aborts.
