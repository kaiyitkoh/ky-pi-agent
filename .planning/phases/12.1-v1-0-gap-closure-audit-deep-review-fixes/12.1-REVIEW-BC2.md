**Reviewed:** 2026-10-13T10:30:28Z
**Depth:** deep. Checked against the pinned Pi 1.1.0 sources: `agent-session.js` (`prompt`, `_runAgentPrompt`, `setModel`, `setThinkingLevel`), `extensions/runner.js` (`emitInput`) and `settings-manager.js`.

## Summary

Most iteration-1 findings are closed. These look correct:

- WR-B-02, the pending-run binding. Pi 1.1.0 emits `before_agent_start` only a few synchronous steps before `_runAgentPrompt`, and `agent_settled` fires from that function's `finally`. Once a run has "started", it will settle.
- CR-B-04, the BLOCKER-first stop order.
- CR-C-1, CR-C-2 and CR-C-3, the guard inputs and the Bedrock prefix.
- WR-B-01 and WR-B-04 to WR-B-11.

The fixes did introduce new defects:

- **Reviewer input corruption (CR-BC2-1).** The CR-C-5 shared secret table added a generic "credential-named assignment" rule. That rule now also runs over the reviewer's prompt, the design pass and the MR body, so ordinary source such as `const token = req.headers.authorization` reaches the reviewer redacted. The reviewer is blinded on exactly the auth code where it matters most.
- **Unguarded workflow prompts (WR-BC2-1).** The WR-C-4 fix lets every `source: "extension"` prompt bypass the guard. That includes `/grill`, `/plan` and any third-party extension, none of which run their own guard. The WR-B-02 pending-run binding already makes the bypass unnecessary.
- **Commit check too loose (WR-BC2-2).** The CR-B-01 ancestry check accepts any descendant of the base, such as a pull, a merge or a reset forward. The run is never checked for "exactly one commit".
- **Task-pin side effects (WR-BC2-3, WR-BC2-4).** The CR-B-03 task pin can only be moved with `--rebase-base`. Using it for a PLAN-only edit makes `/review` skip its ancestry check and tells the MR reader a rebase happened. The pin also leaves the task text and SPEC unpinned.
- **Pin ownership (WR-BC2-5).** Under the CR-C-4 owner-pid registry, a default-mode session silently inherits another session's pin, or a stale one. On Windows, pid reuse plus `EPERM` treated as "alive" can keep a stale owner alive indefinitely.

## Critical Issues

### CR-BC2-1: The shared credential table now redacts ordinary source code in the reviewer, design-review and MR inputs

**File:** `.pi/lib/secret-patterns.ts:34`. The impact lands at `.pi/extensions/quality/reviewer.ts:128`, `.pi/extensions/quality/design-review.ts:115` and `.pi/extensions/review/mr.ts:68`.

**Issue:** The CR-C-5 fix replaced the old narrow wire rule with a generic one. The old rule covered only `access_token`, `refresh_token`, `session_token`, `secret_access_key` and `client_secret`. The new rule is:

```
(?<keep>(?:password|passwd|secret|token|api[_-]?key|access[_-]?key|authorization|credential)[A-Za-z0-9_-]*["']?\s*[=:]\s*)(?:"[^"]*"|'[^']*'|[^\s"'&;]+)
```

`redactString` uses this table, and `redactString` also processes:
- the whole reviewer contract (diff plus the full contents of every touched file);
- the design-review prompt;
- the MR description that is published to GitLab.

In ordinary TypeScript and Terraform the rule rewrites:
- `const token = req.headers.authorization;` to `token = [redacted:25 chars]`;
- `password: string;` to `password: [redacted:7 chars]`;
- `if (token === undefined)` to `token = [redacted:2 chars] undefined)`;
- `secret: process.env.JWT_SECRET` and Terraform `password = var.db_password`.

The reviewer then reviews code it cannot see, and the refutation pass judges against the same mangled text. This hits the security-sensitive code (auth handlers, credential plumbing, IAM/Terraform) where a missed bug costs most. It defeats the core value ("DeepSeek Flash still misses bugs that Sonnet would catch"). Before this change, the reviewer saw these lines intact. The same rewrite also corrupts the MR body text, for example a finding that mentions `token: missing null check`.

**Fix:** Split the table by consumer:
- Keep the generic key-name rule for the wire log and the audit, where over-redaction is cheap.
- For prompts sent to a model, and for the MR body, use only the shape-based patterns (`sk-`, `AKIA`/`ASIA`, `ghp_`, `glpat-`, `ABSK`, JWT, PEM, URL userinfo, bearer).
- Alternatively, narrow the generic rule to values that look like credentials: env-style uppercase keys at line start, or quoted literals of at least 8 characters.

```ts
// secret-patterns.ts
export const SHAPE_PATTERNS: readonly RegExp[] = [/* every pattern except the generic key-name rule */];
export const SECRET_PATTERNS: readonly RegExp[] = [...SHAPE_PATTERNS, GENERIC_ASSIGNMENT];
export function maskSecretShapes(text: string, mask: (s: string) => string): string { /* SHAPE_PATTERNS only */ }
// diagnostics/redact.ts
export function redactForModel(value: string): string { return maskSecretShapes(value, (s) => redactionPlaceholder(s.length)); }
// reviewer.ts / design-review.ts / mr.ts -> redactForModel
```

Add a `buildReviewerContext` test whose touched file contains `const token = req.headers.authorization;` and assert that the line survives byte-for-byte.

## Warnings

### WR-BC2-1: The input backstop now lets every extension-sourced prompt through, including `/grill`, `/plan` and third-party prompts that nothing guarded

**File:** `.pi/extensions/routing/index.ts:359-360`; `docs/ROUTING.md` (the "Prompts a workflow command sends itself ... pass, because the command already guarded them" bullet)

**Issue:** `if (ctx.model === undefined || event.source === "extension") return;` exempts every `pi.sendUserMessage` prompt, not only the `/quick` and `/execute` ones. `/grill` (`grill/index.ts:134`) and `/plan` (`plan-ceremony/index.ts:114`) run no guard at all; `grep guardRoute|planRoleCall|deriveNeed` finds nothing in either file. The same applies to plan-mode's refinement follow-up and diagnostics' prose-retry follow-up.

Scenario: a restored session, or a revert that failed (WR-C-2's own failure path), leaves the session on Bedrock R1 or on a thinking-dropping Bedrock model. `/grill` then runs a multi-turn tool loop on R1, which the guard exists to refuse.

The code comment ("A workflow prompt was routed and guarded by its command") and ROUTING.md both state something false.

The bypass is also no longer needed:
- WR-B-02 binds each run to its own prompt.
- If the backstop refuses that prompt, the run simply stays pending.
- A pending run records and settles nothing (`settle.ts:143`, `execute/index.ts:165`), and the next prompt disarms it.

So the leak WR-C-4 described can no longer happen. Pi 1.1.0 `runner.js:1217` stops at the first `handled`, but `execute/index.ts` loads before `routing/` and `workflows/` loads after it. In either order, the run stays pending, and the next accepted prompt clears it.

**Fix:** Remove the `source === "extension"` exemption, or narrow it to the armed run's own prompt:

```ts
if (ctx.model === undefined) return;
if (event.source === "extension" && isRunPending() && pendingPromptMatches(event.text)) return; // /quick, /execute pre-guarded
```

Fix the comment and the ROUTING.md bullet to match. Add a test where `/grill` is issued on an R1 session and assert "Prompt not sent".

### WR-BC2-2: The ancestry check accepts any descendant, so a pull, merge or reset forward still passes as "the run's commit"

**File:** `.pi/extensions/workflows/evidence.ts:50-54`, `:90-97`

**Issue:** `isStrictDescendant` requires only `merge-base --is-ancestor base head` and `head !== base`. It accepts all of these:
- `git pull` or `git merge origin/feature`: a fast-forward or merge onto someone else's commits;
- `git reset --hard <ref ahead of base>`;
- `git cherry-pick` of an existing commit.

Each one moves HEAD to a descendant with a changed tree, and the tool call that moved HEAD is recorded at the new SHA. Both briefs demand "exactly one atomic commit" (`workflows/index.ts:51`, `execute/index.ts:135`), but the commit count is never checked.

For `/quick` this means a `git pull` of a teammate's work is accepted as the task, and the gate runs on their diff. For `/execute`, the drift check is the only remaining line of defence. CR-B-01 asked for "HEAD is a new commit". Ancestry is necessary, but it is not sufficient.

**Fix:** In `endRun`, after the ancestry check, require one new non-merge commit created after arm time:

```ts
const n = spawnSync("git", ["rev-list", "--count", "--no-merges", `${base}..${head}`], { cwd, encoding: "utf-8", shell: false });
const merges = spawnSync("git", ["rev-list", "--count", "--merges", `${base}..${head}`], { cwd, encoding: "utf-8", shell: false });
const ct = Number(spawnSync("git", ["log", "-1", "--format=%ct", head], { cwd, encoding: "utf-8", shell: false }).stdout.trim());
const fresh = n.stdout.trim() === "1" && merges.stdout.trim() === "0" && ct * 1000 >= state.armedAt - 2000;
```

Store `armedAt` in `RunState`. Add rejection tests for `git pull --ff-only`, for a merge, and for two commits.

### WR-BC2-3: Re-pinning tasks after a legitimate PLAN edit is only possible through `--rebase-base`, which weakens `/review`'s history check and puts a false rebase note in the MR

**File:** `.pi/extensions/execute/index.ts:78-94`, `:132`; `.pi/extensions/execute/ledger.ts:359-366` (`latestRepin`); `.pi/extensions/review/index.ts:79-83`; `.pi/extensions/review/mr.ts:85-89`

**Issue:** The pin is written at arm time (`:132`), before the prompt has even started. After that, any PLAN edit by `/plan` is refused. This includes these cases:
- an edit after the first `/execute`'s prompt never started (expired SSO);
- fixing a wrong verification command for a task not yet run.

The only way past is `--rebase-base`, which appends a second `base` row. `latestRepin` treats every `base` row after the first as a rebase, which causes two problems:
- `historyMismatch` excludes every accepted entry recorded before it from the `merge-base --is-ancestor <sha> HEAD` check (`mr.ts:85`).
- `/review` appends "the entries above were verified on commits a rebase may have replaced" to the MR body.

So a plain PLAN edit, with no rebase, permanently turns off the off-history check for the earlier tasks, and tells the MR reader something false.

**Fix:**
- Give task re-pinning its own ledger row kind (for example `{ kind: "tasks", tasks, reason }`), appended by a `--repin-tasks` flag behind the same confirm, which shows both lists.
- Have `pinnedTasks` read the latest `base` or `tasks` row.
- Leave `ledgerBase` and `latestRepin` looking at `base` rows only.
- Also consider writing the first `base` row only once the run's prompt has started, from `before_agent_start`.

### WR-BC2-4: The task pin leaves the task text, requirement ids and SPEC unpinned, so the executor can still rewrite what a later task asks for

**File:** `.pi/extensions/execute/ledger.ts:237-242`, `:330-332`; `.pi/extensions/execute/index.ts:121`, `:125`

**Issue:** `PinnedTask` holds only `{id, path, verificationCommand}`. The brief for the next task is built from the live files:
- `buildHandoffPacket({ spec: spec.spec, task })` and `task.rawLine` come from the current PLAN.md;
- the SPEC requirements come from the current SPEC.md.

A model working on T001 can rewrite T002's description, for example from "implement rate limiting in api.ts" to "add a comment in api.ts". It can also change T002's requirement ids or SPEC's requirement text. Path and verification stay the same, so `/execute` raises no objection, and a weak verification command (`npm test -- api`) then passes the reduced task.

CR-B-03's remediation said to pin "the validated PLAN task list"; only three fields were pinned.

**Fix:** Pin `rawLine` and `requirementIds` in `tasksOf`, plus a SHA-256 of the gated SPEC requirements body, and compare all of them. `renderTasks` already shows lines, so the re-pin prompt stays readable.

### WR-BC2-5: The planner pin leaks into default-mode sessions, and on Windows a recycled pid can keep it alive indefinitely

**File:** `.pi/extensions/routing/index.ts:383-389`; `.pi/extensions/routing/agent-overrides.ts:150-158`, `:298-321`

**Issue:** There are three separate problems.

1. **A session that never pins inherits the pin.** At `session_start`, a session whose mode is `DEFAULT_MODE` (`cheap`) writes nothing (`index.ts:386`). If another session holds a `/max` pin, the cheap session's planner subagents run on Bedrock Sonnet, with no notice. Before CR-C-4, this session would have restored the pin. Now it silently uses the other session's model. ROUTING.md's "last writer wins" covers two sessions that pin, but not a session that never writes. `/mode` resolves the planner through `pickConfiguredCandidate` (`index.ts:233-237`), not through the effective `agentOverrides`, so it reports the cheap planner while the expensive one runs.
2. **On Windows, a stale owner can stay alive.** Closing the console window usually kills node without `session_shutdown`, so markers left behind by crashes are normal. Windows recycles pids quickly. `processAlive` also counts `EPERM` as alive, and `EPERM` is what `OpenProcess` returns for SYSTEM and service processes. Once a stale owner pid is reused by such a process, `restorePlannerPin` never restores. The pin then stays in the user's global settings for every later default-mode session. The cost concern is the project's core value. ROUTING.md says this lasts "until that process exits", but a service process may not exit for days.
3. **Updates are not atomic across processes.** `writeAgentOverrides` and `restorePlannerPin` read, modify and write `settings.json` without a lock. Two processes starting or exiting together can lose an owner entry, which brings back the original CR-C-4 symptom.

**Fix:**
- At `session_start`, when a marker exists, always write this session's own mode's pins, including `DEFAULT_MODE`, so a session never runs on someone else's pin.
- Record owners as `{ pid, startedAt }`, and expire entries older than a TTL (for example 24 h), refreshed on each `session_start` or mode switch. Do not trust a bare pid on Windows.
- Make `/mode` print the effective `subagents.agentOverrides.planner` when it differs from the route.

### WR-BC2-6: The generic credential rule backtracks quadratically, and it now runs synchronously on file contents in `before_provider_request`

**File:** `.pi/lib/secret-patterns.ts:2-3`, `:34`

**Issue:** The header claims "Each pattern is a single quantifier over a character class ... against ReDoS". The generic rule breaks that claim: it is a keyword alternation followed by `[A-Za-z0-9_-]*["']?\s*[=:]`. On a long `[A-Za-z0-9_-]` run that contains the keyword many times, every keyword position scans to the end of the run and then backtracks. That is O(n²).

Measured with the exact regex on node 24:

| Input (`"token".repeat(n)`) | Time |
|---|---|
| 10 KB | 7 ms |
| 40 KB | 107 ms |
| 160 KB | 1,718 ms |

Extrapolated, 1 MB takes about a minute. Before CR-C-5 this rule ran only on audited command lines. It now runs on:
- every string leaf of the wire payload, synchronously in `before_provider_request`, which stalls the turn;
- the reviewer contract.

A crafted or generated file (minified identifiers, base64-url blobs) in a work repo is enough to trigger it. The fix report's "1 MB in under 2 s" fixture does not exercise this rule.

**Fix:** Bound the run and anchor the keyword so each start position is O(1):

```ts
/(?<keep>(?<![A-Za-z0-9])(?:password|passwd|secret|token|api[_-]?key|access[_-]?key|authorization|credential)[A-Za-z0-9_-]{0,40}["']?[ \t]{0,8}[=:][ \t]{0,8})(?!\[(?:redacted|REDACTED)\b)(?:"[^"\n]{0,512}"|'[^'\n]{0,512}'|[^\s"'&;]{1,512})/gi
```

Add a ReDoS fixture of `"token".repeat(200_000)` with a time bound.

### IN-BC2-3: On a repository with no commit, `/quick` and `/execute` fail with raw git errors, and `/quick` has already retired `/grill` or `/plan`
