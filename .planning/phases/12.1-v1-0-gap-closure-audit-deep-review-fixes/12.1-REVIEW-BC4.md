## Summary

All five WR-BC3 Warnings are closed. So are IN-BC3-1, -2, -3, -5 and -6. IN-BC3-4 is deferred and IN-BC3-7 is accepted, both with reasons. The fixes introduce no new BLOCKER and no new WARNING. There are four small Info items.

Spot checks requested by the orchestrator:

- **Linear time.** Each rule was timed over every hostile input at 200 KB. The worst case was 28 ms, from the curl rule on `"-u=".repeat(n)`. The JWT, curl and name rules are no longer quadratic.
  - Every unbounded run either ends its rule or follows a literal anchor.
  - Bounded lookbehinds and quantifiers give per-start constants of at most 256.
  - The header claim in `secret-patterns.ts:3` and the DIAGNOSTICS.md wording are now accurate.
- **Name-rule coverage.** All of these are now masked whole:
  - a 600-character quoted value;
  - a 600-character unquoted value;
  - `password:\n  hunter2`;
  - `password=\r\n  pw`.

  Already-redacted text is left alone, on the same line and on the next one.
- **2-minute tolerance** (`evidence.ts:57,70`).
  - `startRun` arms with the current HEAD (`execute/index.ts:145`), not the ledger base. A commit from an earlier rejected attempt is therefore never inside `base..HEAD`. The window only admits a commit that was made in the two minutes before the arm and then fast-forwarded in.
  - WORKFLOWS.md §4 lists that residual.
  - The strict `COMMIT_ROW` parse fails closed on signature lines, merges, root commits and anything unparsable.
  - `-c log.showSignature=false` plus `--no-show-signature` is correct. `--no-color` and an explicit `--format` neutralise `color.ui` and `format.pretty`.
- **SPEC copy in the git common dir** (`ledger.ts:149-163`).
  - The path comes from `ledgerFile`, so it carries the same per-worktree hash suffix. Linked worktrees sharing one common dir cannot collide.
  - The name ends in `.SPEC.md`, not `.jsonl`, so `signingKey`'s lost-key check (`ledger.ts:62`) is not confused by it.
  - With no ledger: `pin` is undefined, `readPinnedSpec` returns undefined, and `--repin` / `--rebase-base` refuse with "nothing pinned yet" before any confirm.
  - With a pre-copy ledger, or a copy that no longer matches: the hash check returns undefined, so the confirm says the change cannot be shown and the refusal falls back to "restore it". A copy the model tampers with can never be presented as the pin.
  - The `kypi-ledger` segment guard (`safety/paths.ts:251,375`) covers the copy.
  - No `user_bash` hook exists in `.pi/extensions`, so the user's `!cp` really is unguarded.
  - A Windows backslash path inside bash double quotes survives as typed.
- **Checkbox backward compatibility** (`ledger.ts:126,137-139`).
  - `withoutCheckbox` uses exactly the prefix that `TASK_LINE_PATTERN` / `CHECKBOX_LINE_PATTERN` accept (`plan-schema.ts:19,22`).
  - Both sides of `pinMismatch` are normalised, so iteration-3 ledgers that pinned `- [ ] …` do not refuse.
  - The spread keeps the key order, so the `JSON.stringify` comparison stays stable.
  - Nothing selects tasks by checkbox: the next task comes from the ledger's `accepted` rows. Unpinning the box therefore opens no bypass.
- **AGENTS.md comments.** Every added comment is one or two lines and states a reason. None contains plan, phase, requirement or review IDs, history wording, or test or caller references. The `restoreModeFromBranch` JSDoc now gives the reason for the export instead of naming tests.

## Info

### IN-BC4-1: The JWT anchor leaves a token glued to `-`, `_` or an alphanumeric unmasked

**File:** `.pi/lib/secret-patterns.ts:25`

`(?<![A-Za-z0-9_-])eyJ…` buys linearity, but it changes coverage. The probe `cookie=session-eyJhbGciOiJIUzI1.eyJzdWIiOiIxMjM0.sig` now passes through both `redactString` and `redactForModel` unchanged. Before 1663116 it was masked. Most real JWTs follow `=`, `"`, `:`, a space or `Bearer `, and `Bearer ` has its own rule, so the impact is small. The trade-off is still undocumented. Loosening the lookbehind brings the quadratic case back (`"-eyJ".repeat(n)` gives one start per unit). The cheapest fix is to list this as a residual beside the linearity sentence in DIAGNOSTICS.md.

### IN-BC4-2: A line-ending-only SPEC change asks for approval of an empty diff

**File:** `.pi/extensions/execute/ledger.ts:198-200`

`specDigest` hashes the raw bytes, but the diff splits on `/\r?\n/`. A CRLF↔LF conversion (an editor, or `core.autocrlf`) therefore refuses `/execute` as "SPEC.md changed". The `--repin` confirm then shows `SPEC.md changes (- pinned, + now):` with nothing under it. Fix: when `specDiff.length === 0` and the hashes differ, print "line endings or whitespace only".

### IN-BC4-3: `lineDiff` prints `+` before `-` in a replaced block, against its own "- pinned, + now" header

**File:** `.pi/extensions/execute/ledger.ts:183-185`

The tie-break `>=` prefers insertions, so `["a","b","c"]→["a","x","c"]` renders as `+ x` then `- b`. The diff is correct; only the order reads backwards. Fix: test the deletion branch first with the mirrored tie-break, `i < a.length && (j === b.length || lcs[(i+1)*w+j] >= lcs[i*w+j+1])`.

### IN-BC4-4: `renderPinChanges` runs on every `/execute`, before the in-flight check and outside the flag branches

**File:** `.pi/extensions/execute/index.ts:79`

Only `--repin` and `--rebase-base` use `pinShown`. Every other `/execute` still pays for it:
- two `git rev-parse` spawns (through `ledgerFile`);
- a read of the copy;
- an LCS of up to 1,000,000 cells.

Any throw on that path, for example an unreadable copy, now refuses an ordinary run that never needed it. The in-flight refusal also does this work for nothing. Fix: compute it lazily inside the two flag branches, which adds no lines if it is inlined into the two `confirm` calls.

A separate cosmetic point in the same area: `restoreAdvice` wraps the copy path in double quotes (`ledger.ts:208`). On macOS, a `$` or a backtick in a home-directory name would expand there. Single quotes avoid that.
