# Phase 12.1 (part C): Code Review Report

**Reviewed:** 2026-10-13
**Depth:** deep. Call chains were traced into `quality/*`, `execute/*`, `workflows/*`, Pi 1.1.0 `dist/core/agent-session.js`, `dist/modes/interactive/interactive-mode.js`, pi-ai `transform-messages.js`, and the installed `pi-subagents@0.76.1`.
**Files reviewed:** 73
**Status:** issues_found
**Tests:** none were run, because of the CPU budget. Every finding comes from reading the code.

## Summary

The capability guard is now wired into production paths. The input it receives is wrong in two ways:

- `deriveNeed` derives every check from the whole main session.
- It feeds that session-wide input to nested single-shot roles, which do not carry the session.

Two consequences follow:

- After one image anywhere on the branch, the session can no longer be used on any DeepSeek executor, and none of `/cheap`, `/balanced`, `/max` or `/escalate` can recover it. Pi itself already downgrades images for text-only models.
- In long sessions, or ones that contain an image, the reviewer, advisor and refutation gates are refused.

The planner pin has two problems:

- It skips the new Bedrock prefix, so `/max` pins a bare Sonnet 4.5 id that Bedrock does not serve on demand.
- Any other Pi process undoes it, including the background subagent children that `/execute` launches.

The `model_select` revert does not undo a persisted default, so the refused model comes back at the next startup.

Redaction of the wire capture is weaker than the safety audit's own redactor. It has no GitLab PAT or generic `password=` / `api_key=` coverage, and the wire log is the stream that carries file contents.

**Secrets:** no credential, key-shaped literal, account id or hostname was found in the diff or in tracked non-markdown files. The AKIA and `sk-` strings in the tests are obvious fakes.

**`typescript` in `dependencies`:** this is correct. `quality/rules.ts` imports `typescript` at runtime, and Pi installs with `--omit=dev`. See IN-C-6 for a minor caveat.

## Critical

### CR-C-1: The image check bricks the session for every text-only executor, and still misses the image in the current prompt

**Location:**
- `.pi/extensions/routing/guard.ts:59-80`
- `.pi/extensions/routing/index.ts:53`, `:155`, `:311-314`, `:330-337`

**Defect:** `branchHasImage` scans every entry from root to leaf of `sessionManager.getBranch()`. That includes:
- tool-result images, for example `read` on a PNG;
- entries that compaction has already removed from context.

From then on, `image: true` is passed to every executor guard call. Pi already handles this case itself: pi-ai 1.1.0 `dist/api/transform-messages.js:1-20` replaces images with `"(image omitted: model does not support images)"` for any model whose `input` lacks `"image"`. The refusal therefore prevents nothing.

The check also never reads `event.images` in the `input` handler. A prompt that actually attaches an image to a text-only model is not refused. Only the prompts after it are.

**Scenario:**
1. The user is on DeepSeek Flash in `cheap` mode and asks the agent to read `screenshot.png`.
2. Every later prompt gets "Prompt not sent".
3. `/cheap`, `/balanced` and `/max` all resolve text-only executors (flash or pro), so `applyMode` refuses them too (`index.ts:53`). `/escalate` resolves pro and is refused (`:155`).
4. `docs/ROUTING.md` says "`/cheap`, `/balanced` and `/max` always remain available to recover". That is false here. The only way out is a new session.

This breaks the core value directly: the cheap daily driver stops working.

**Fix:**
- Base the image need on what the request will actually carry: `event.images?.length > 0` in `input`, and the images in the messages a nested role sends.
- Drop the branch scan, or limit it to user-message images after the last compaction entry, and only for roles that must see the image (`vision`).
- For the executor, consider leaving image handling to Pi's downgrade entirely.

```ts
// input backstop
deriveNeed(ctx, { usesToolLoop: true, promptChars: event.text.length, image: (event.images?.length ?? 0) > 0 })
// deriveNeed: image comes from `extra.image`, never from the whole branch
```

### CR-C-2: Session-scoped `deriveNeed` refuses nested reviewer, advisor, refutation and design-review calls

**Location:**
- `.pi/extensions/quality/reviewer.ts:196`
- `.pi/extensions/quality/advisor.ts:63`
- `.pi/extensions/quality/verdict.ts:193`
- `.pi/extensions/quality/design-review.ts:131`
- `.pi/extensions/routing/guard.ts:68-80`

**Defect:** these callers send a single-shot request that they build themselves: one user message plus a system prompt. The need they pass to the guard comes from the main session, though:

| Field | Value passed | Why it is wrong for a nested call |
|---|---|---|
| `estimatedInputTokens` | `getContextUsage().tokens + promptChars/4` | It includes the whole main conversation, which the nested call does not send. |
| `image` | Any image on the main branch | The nested call carries no images. |
| `thinkingRequested` | The main session's thinking level | The nested call's thinking comes from `route.reasoningEffort` via `buildNestedApiOptions`. |

**Scenario:**
1. In `balanced` mode the advisor is Bedrock Sonnet, with a 200k window.
2. The executor is DeepSeek-direct Flash, with a 1M window, and is 190k tokens into a session.
3. `consult_advisor` with a 50k-token context is refused: 190k + 50k > 200k.
4. In `cheap` mode, any image on the branch refuses the reviewer, which is text-only Flash. `runSingleShotRole` throws, and the quality gate fails, either closed or as an error, on sessions that are perfectly reviewable.
5. A future Bedrock non-Claude reasoning candidate for a call-model role would be refused or allowed according to the session's thinking toggle, which is unrelated to the call.

**Fix:** add a nested-call need builder that describes only the outgoing request. Use `deriveNeed` only for the executor.

```ts
export function nestedNeed(messages: Message[], systemPrompt: string, effort?: "high" | "max"): RoleNeed {
  const chars = systemPrompt.length + JSON.stringify(messages).length;
  return {
    estimatedInputTokens: Math.ceil(chars / 4),
    image: messages.some((m) => Array.isArray(m.content) && m.content.some((b) => b.type === "image")),
    thinkingRequested: effort !== undefined,
  };
}
```

### CR-C-3: The planner pin skips the Bedrock inference-profile prefix, so `/max` pins a bare id that Bedrock rejects

**Location:**
- `.pi/extensions/routing/agent-overrides.ts:86-101`
- `.pi/extensions/routing/index.ts:225-235`
- `.pi/extensions/routing/schema.ts:199-200`, `:228`

**Defect:** `ROLE_MAP.max.planner` is `VISION_CANDIDATES`, which is the bare `amazon-bedrock/anthropic.claude-sonnet-4-5-20250929-v1:0`. Only `pickConfiguredCandidate` adds `kyPiAgent.bedrockProfilePrefix` (`modes.ts:150-159`). `agentOverridesFor` writes `${candidate.provider}/${candidate.id}` unchanged.

Bedrock serves Sonnet 4.5 only through an inference profile. On-demand calls with the bare model id fail with a ValidationException asking for an inference-profile id or ARN.

`/mode` adds to the confusion. `reportMode` resolves the planner through `pickConfiguredCandidate`, so it shows `amazon-bedrock/apac.anthropic...`, which is not the value that was written.

**Scenario:**
1. The user runs `/max`.
2. Settings receive `subagents.agentOverrides.planner.model = "amazon-bedrock/anthropic.claude-sonnet-4-5-20250929-v1:0"`.
3. Every planner subagent run fails at the provider.
4. `/mode` reports the apac id, so the user sees no inconsistency.

D-04 is only half applied.

**Fix:** add the same prefix in `agentOverridesFor`. Factor `resolveRef(candidate)` out of `pickConfiguredCandidate` and use it in both places. If the prefix setting is invalid, refuse the pin (`ok: false`).

```ts
const ref = resolveBedrockRef(candidate); // shared with pickConfiguredCandidate
if (!ref.ok) { lastReason = ref.reason; continue; }
picked = `${ref.ref.provider}/${ref.ref.id}`;
```

### CR-C-4: Any other Pi process undoes the planner pin, including the background subagent children that `/execute` starts

**Location:**
- `.pi/extensions/routing/index.ts:345-354`, `:366-373`
- `.pi/extensions/routing/agent-overrides.ts:246-282`

**Defect:** the pin lives in the user-level `settings.json`, which every process shares. `restorePlannerPin()` runs unconditionally in `session_start` (unless `reason === "reload"`) and in `session_shutdown`, in every process that loads the routing extension.

pi-subagents 0.76.1 runs background or async children (`bg_wait`) with `host: "runner"`, in a separate process. It loads them with ambient extensions unless a capability ceiling denies extensions (`src/runs/shared/child-launch.js:199`). `planner.md` and `executor-handoff.md` declare no `extensions:` list. Nothing in `.pi/extensions` checks `PI_SUBAGENT_CHILD`.

**Scenario:**
1. The user runs `/balanced`, so the planner is pinned to DeepSeek Pro.
2. `/execute` dispatches `executor-handoff` with `bg_wait`.
3. The child loads routing (with the git package installed, or with project trust passed to the child). Its `session_start` restores the pre-pin value, and its `session_shutdown` does so again.
4. Every later planner run in the parent silently uses the default model.

The same thing happens with two terminals:
1. Session A runs `/max`.
2. Session B starts in another repo and erases A's pin at startup.
3. When A exits, its own shutdown wipes any pin B wrote.

**Fix:**
- Skip pin bookkeeping in subagent children: `if (process.env.PI_SUBAGENT_CHILD) return;`.
- Record an owner in the marker, for example `{ had, value, pid, sessionId }`. Restore at `session_start` only when the owning pid is no longer alive. Restore at `session_shutdown` only when this process is the owner.
- Better still, pass the model per spawn instead of through a global file, if pi-subagents supports that.

### CR-C-5: Wire-capture redaction misses common credential shapes, including GitLab PATs, `password=` and `api_key=`

**Location:**
- `.pi/extensions/diagnostics/redact.ts:45-68`, `:38`
- Compared with `.pi/extensions/safety/audit.ts:29-41`

**Defect:** the module docstring states the invariant: "a live key on disk is a breach the moment it is written". It also says the payload carries file contents such as a read `.env`. Even so, `SECRET_VALUE_PATTERNS` has none of these:

- `glpat-…` GitLab personal access tokens. The user's work GitLab auto-deploys `main`.
- Generic credential assignments: `PASSWORD=`, `DB_PASSWORD=`, `API_KEY=`, `SECRET_KEY=`, `token=`, `"password": "…"`. The assignment rule covers only `access/refresh/session_token`, `secret_access_key` and `client_secret`.
- `AWS_BEARER_TOKEN_BEDROCK=ABSK…` Bedrock API keys.
- Bearer tokens shorter than 20 characters.
- Credentials embedded in URLs, such as `postgres://user:pass@host`.

The safety audit's `redactSecrets` already covers `glpat-`, `xox[abprs]-`, `Bearer` with 8 or more characters, and a broad `(password|passwd|secret|token|api[_-]?key|access[_-]?key|authorization|credential)…[=:]` rule. The most exposed stream, the one carrying file bodies, has the weaker redactor.

`REDACTED_HEADER_KEY_RE` also needs a delimiter, so camelCase object keys such as `apiKey`, `accessToken` and `secretAccessKey` are not treated as credential keys.

**Scenario:**
1. The agent runs `read .env` in a work repo containing `DATABASE_PASSWORD=Pr0d!pass` and `GITLAB_TOKEN=glpat-xxxxxxxxxxxxxxxxxxxx`.
2. The next `before_provider_request` writes both values in plaintext to `.pi/logs/wire-<date>.jsonl`.

**Fix:**
- Move one pattern table into `.pi/lib/` and have both diagnostics and safety import it. That respects the rule that `safety/` must not import from `diagnostics/`.
- Add `glpat-[A-Za-z0-9_-]{20,}`, `ABSK[A-Za-z0-9+/=]{20,}` and a userinfo rule `://[^\s/:@]+:[^\s/@]+@`.
- Add the generic key-name assignment rule from `audit.ts`.
- Make the header-key regex match camelCase as well, for example by testing `key.replace(/([a-z])([A-Z])/g, "$1_$2")`.
- Add a redact test fixture for each new shape.

## Warning

### WR-C-1: The `model_select` revert leaves a persisted default and a widened model scope behind

**Location:** `.pi/extensions/routing/index.ts:307-328`. Pi side: `interactive-mode.js:4444-4452` and `agent-session.js:1946-1963`.

**Defect:** the `/model` picker's "set as default" action calls `session.setModel(model, { persist: true })`. That writes `defaultProvider` and `defaultModel` to settings, and `_addPersistedDefaultToNonEmptyScope` appends the model to `enabledModels`, all before `model_select` fires. The revert's `pi.setModel(previous)` does not persist. Afterwards the picker still shows the status `Default model: <refused id>`.

**Scenario:**
1. The user sets Bedrock R1 as the default.
2. The switch is reverted in the session, but settings still say R1.
3. The next `pi` startup boots on R1.
4. Every prompt is refused by the input backstop until the user switches models by hand.

**Fix:** in the revert path, compare `SettingsManager`'s default against `event.model`. The extension can read `<agent-dir>/settings.json`. If it matches, restore the previous default. A simpler fallback: notify the user explicitly that the persisted default still names the refused model and say how to change it.

### WR-C-2: A failed revert is silent, and the notification has already said "Reverting"

**Location:** `.pi/extensions/routing/index.ts:318-327`

**Defect:** the code notifies `Reverting to X` before calling `pi.setModel(previous)`. If that call returns `false` (the previous provider's auth is gone) or throws, the result is ignored, or swallowed by the outer `catch`.

The revert also does not restore the thinking level. `setModel` applies `_getThinkingLevelForModelSwitch(previous)`, which is the per-model or global default, not the level the user had (`agent-session.js:2101-2113`).

**Scenario:** the user's SSO session expires and they switch from Bedrock Claude to R1. The UI says "Reverting to Claude", but the model stays R1.

**Fix:** check the return value and notify `revert failed: …` when it is `false` or the call throws. Capture `ctx.thinkingLevel` before the switch is not possible, so call `pi.setThinkingLevel(...)` with the level recorded at the last `thinking_level_select`, or document the reset.

### WR-C-3: The thinking refusal cannot be followed, so Bedrock reasoning models outside Claude and `gpt-` cannot be selected at all

**Location:**
- `.pi/extensions/routing/index.ts:311`
- `.pi/extensions/routing/guard.ts:103-117`

**Defect:** Pi's `setModel` and `cycleModel` set the thinking level to the per-model or global default before `model_select` fires. The refusal tells the user to "Set thinking to off or pick another model". Setting thinking to `off` first makes no difference: the switch resets it to the default, for example `medium`, the guard refuses again, and the model is reverted.

**Scenario:** a Bedrock Qwen or DeepSeek V3 reasoning entry can never be chosen through `/model` unless the global default thinking level is `off`.

**Fix:** in `model_select`, when only the thinking block fails, call `pi.setThinkingLevel("off")` and notify, instead of reverting. Alternatively, change the message to name the per-model `thinkingLevel` setting.

### WR-C-4: The input backstop discards workflow prompts after the workflow has armed its run

**Location:**
- `.pi/extensions/routing/index.ts:330-340`
- `.pi/extensions/execute/index.ts:121-126`
- `.pi/extensions/workflows/index.ts:46-48`
- `.pi/extensions/diagnostics/index.ts:226`

**Defect:** `/execute` arms `startRun`, `armExecuteRun` and `claimWorkflow` before it calls `pi.sendUserMessage`. Pi routes that message through `input` with `source: "extension"`. If the guard fails, the backstop returns `handled`. No turn runs, so `agent_settled` never fires and the armed run leaks:
- `/quick` then refuses with "a turn is already in flight" (`isRunArmed`).
- The next ordinary prompt's `agent_settled` is consumed by the stale `/execute` settle (`execute/index.ts:147-160`), which then judges unrelated work.

`/execute` performs no guard pre-check of its own. CR-C-1 makes this easy to hit.

**Fix:** let `source === "extension"` messages through the backstop, because the workflows run their own `planRoleCall` checks, and add a pre-check to `/execute`. Otherwise, disarm in the backstop by emitting an event that the workflows listen for.

### WR-C-5: The context-window refusal gives the wrong remedy and blocks Pi's overflow recovery

**Location:** `.pi/extensions/routing/index.ts:333-336`

**Defect:** when `usage + prompt/4 > contextWindow`, the prompt is refused with "switch with /cheap, /balanced or /max". For a near-full session the real remedy is `/compact`. On DashScope (393k) the other modes do not have a larger window anyway. Without the backstop, Pi would have handled the overflow through its own auto-compaction and retry path.

**Fix:** for the context block, name `/compact`, or let the prompt through and rely on Pi's compaction. Keep the hard refusal for the image (CR-C-1), R1 and thinking checks.

### WR-C-6: The pin replaces the user's whole `agentOverrides` object, and the restore discards edits made during the session

**Location:**
- `.pi/extensions/routing/agent-overrides.ts:206-213`
- `.pi/extensions/routing/agent-overrides.ts:263-267`

**Defect:** `subagents.agentOverrides = overrides` replaces the whole object with `{ planner: … }`. Any override the user had for another agent, such as `executor-handoff`, `reviewer` or a pi-subagents builtin, disappears for the session. `restorePlannerPin` then writes back the snapshot taken at the first pin, so any override the user added during the session is also lost.

**Fix:** merge per key, `{ ...original, ...overrides }`, and record and restore only the keys that were pinned:

```ts
marker = { keys: { planner: original?.planner ?? null } }
```

### WR-C-7: Redacting before truncating spends the node budget on old messages and truncates the tail that is kept

**Location:**
- `.pi/extensions/diagnostics/wire.ts:275-289`, `:333`
- `.pi/extensions/diagnostics/call-model.ts:162`

**Defect:** `redactDeep(event.payload)` walks the full `messages` array under `MAX_NODES = 200_000`, and only then does `boundRequestPayload` keep the last 4 messages. In a long session the budget runs out partway through, so the newest messages, which are the ones kept, become `"[redacted:truncated]"`.

**Scenario:** this hits the long sessions where the wire inspector matters most. The recorded tail is placeholders.

**Fix:** slice first, then redact. Compute the hash over the full array with `JSON.stringify(messages)` before redaction, or over a redacted copy of each message one at a time.

```ts
const { payload, messageCount, messagesHash } = boundRequestPayload(event.payload);
record({ payload: redactDeep(payload), messageCount, messagesHash });
```

### WR-C-8: The remote Qoder session is cancelled only on user abort, never on timeout or stream failure

**Location:** `.pi/extensions/qoder/client.ts:517-592`, `:613-627`

**Defect:** `cancelRemoteSession` runs only when `signal?.aborted`. These paths all happen after the task was sent and all throw locally while the hosted agent keeps working with its own Read/Write/Bash tools in its environment, outside every control:
- the inactivity timeout (`:520-533`, `:548-561`);
- a network error while reading;
- a stream that closes early without an idle frame;
- a stop reason other than `end_turn`.

**Fix:** after the task POST succeeds, cancel the remote session on every exit path except `done && stopReason === "end_turn"`. Wrap the read loop in `try/finally` with a `succeeded` flag.

### WR-C-9: Qoder completion is not tied to the task that was sent, so an early idle frame returns an empty "success"

**Location:** `.pi/extensions/qoder/client.ts:288-295`, `:613-629`

**Defect:** `done` becomes true on any `session.status_idle` frame. The stream is opened before the task is sent (`:461-475`). A newly created session that reports its initial idle status, or a replayed status frame, therefore completes the fold before the agent has started. With no `stop_reason`, nothing throws, and `qoder_delegate` returns `""` as the delegated answer. `Accept: text/event-stream` is also never sent.

**Fix:**
- Accept `status_idle` only after a `session.status_running` frame, or after an `agent.message` event that follows the send.
- Treat empty `text` with `done` as an error.
- Send `Accept: text/event-stream`.
- Confirm the event order in the RUNBOOK live check.

### WR-C-10: Two processes rotating concurrently can overwrite a rotated file

**Location:** `.pi/lib/jsonl.ts:288-313`, `:377-394`

**Defect:** rotation uses `renameSync(src, dst)`, which replaces an existing `dst` on both Windows (MoveFileEx with REPLACE_EXISTING) and POSIX. Each process decides to rotate from its own cached size, which can be up to 1 s stale.

**Scenario:**
1. Process A shifts `.1`→`.2` and renames the live file to `.1`.
2. Process B, working from a stale `size > cap`, already passed its own shift. It then renames the new live file A just created onto `.1`, which destroys A's rotated file of up to 32 MB.
3. Separately, the extra rotations of tiny files use up `MAX_ROTATED_FILES` and push older history past the cap.

Subagent fan-out produces exactly this concurrency. The docstring's claim that "four concurrent appending processes lost no record" covers appends, not overlapping rotations.

**Fix:** make each rotated name unique, for example `<stem>.<epochMs>-<pid>.jsonl`, and prune by count. Alternatively, re-`stat` the live file just before renaming it and skip the rename if it is under the cap. Use `linkSync` plus `unlinkSync`, which fails with EEXIST, so a rename never overwrites.

### WR-C-11: The `implement` profile now costs as much as `full`. A loader was the better fix

**Location:**
- `.pi/extensions/routing/profiles.ts:35-39`
- `tests/integration/context-floor.test.ts:15-26`

**Defect:** review finding W1 was that `bg_*` and `questionnaire` had no enabler. The fix makes them active by default under `implement`:
- The floor goes from 2344 to 4179 tokens: +1835 per request, +78%, the same as `full`.
- The shell-policy prompt section is added to every turn.

The harness already has the sanctioned pattern for this: `web_enable` and `subagents_enable` loader tools, plus Pi's documented dynamic tool loading through `pi.setActiveTools`. A one-line `bg_enable` loader, about 60 tokens, would have kept the 2344 floor. The cheap-model context budget is the project's core value, and the `implement` profile no longer narrows anything that matters.

**Fix:** revert `questionnaire` and `bg_*` to `["full"]` and add a `bg_enable` loader, which activates `bg_run`, `bg_status`, `bg_logs` and `bg_kill` on demand, mirroring `web_enable`. Do the same for `questionnaire`, or fold it into the same loader. Restore the `implement < full` floor assertion.

### WR-C-12: The comment-rule scan skips `models-template.json`, which is full of IDs and phase references, and its header is stale
