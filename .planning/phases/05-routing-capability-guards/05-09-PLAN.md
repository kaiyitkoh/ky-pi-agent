Extend `.pi/extensions/routing/index.ts` with two more commands, both reusing the same
pre-flight → guard → `setModel` → persist path `applyMode` already owns. Do not fork a second
copy of that sequence; factor the shared part if needed.

`escalate` — invocation name `escalate`. With no argument (or `on`) it sets the escalated
flag, recording `escalatedFrom` as the current mode, and switches the executor to the
`ESCALATION_MODE` executor route resolved through `resolveRoute`. With the argument `off` it
clears the flag and switches the executor back to the current mode's own executor route.
Argument parsing is exact and unforgiving: anything other than empty/`on`/`off` is refused
with a message naming the accepted forms, never silently treated as `on`.

Both directions run the full sequence: `await ctx.waitForIdle()` first, candidate selection
with `hasConfiguredAuth`, the capability guard for the `executor` role, `pi.setModel` in a
`try/catch` with the boolean checked, and only then the state update, the `ky:mode` entry and
the `ROUTING_EVENT` emit. **If escalation cannot be applied, the state must not claim it was**
— set the flag only after `setModel` returned `true`.

`mode` — invocation name `mode`. Prints the current state through `ctx.ui`: mode name, whether
escalated and from which mode, the concrete `provider/id` currently serving the executor, and
the model each of the other five roles would use right now. This is criterion 2's "visible"
half in the only surface Phase 5 owns; Phase 11 renders the statusline from `ROUTING_EVENT`.

Write a durable record for every escalation change: append a row through the existing
diagnostics turns/JSONL machinery under a routing-owned base, carrying the previous and new
executor `provider/id`, the mode, the escalation flag and a timestamp. This is what makes a
cost spike explainable after the fact — the reason stickiness was chosen over auto-restore.
Keep it best-effort: a failed record write must never turn a successful switch into an error
(follow `safety/audit.ts`'s catch-and-return posture and say so in a comment).

Update the entry-point docstring's LAYOUT/commands list to include `escalate` and `mode`.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-32 | Repudiation | an unexplained expensive turn | mitigate | Every escalation change appends a record naming previous and new executor models, the mode and the flag; stickiness is deliberate so the state is always inspectable via `mode` |
| T-05-33 | Tampering | state claiming an escalation that never took effect | mitigate | The flag is set only after `pi.setModel` returns `true`; the refusal case asserts `escalated === false` alongside the unchanged model |
| T-05-34 | Elevation of Privilege | escalation silently widening beyond the executor | mitigate | `resolveRoute` lifts the executor only, and the test compares the other five roles' routes before and after |
| T-05-35 | Denial of Service | a failed record write breaking a successful switch | accept | The record write is best-effort and catches its own failure, mirroring `safety/audit.ts`; the residual risk (an unexplained spike if the write fails) is stated in the SUMMARY |
