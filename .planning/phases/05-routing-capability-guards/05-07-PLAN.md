`applyMode` executes in this order, and the order is the requirement:
1. `await ctx.waitForIdle()` — FIRST, before anything is read or written. This is what removes the race (ROUTE-02); `waitForIdle` exists only on `ExtensionCommandContext`, which is why these are commands and not tools.
2. Resolve the executor route for the target mode and pick a configured candidate via `pickConfiguredCandidate(ctx.modelRegistry, ...)`. On refusal, `ctx.ui.notify(reason, "error")` and RETURN — the session stays on its current model and the user is told which candidates were tried and why each failed.
3. Run the capability guard for the `executor` role (`usesToolLoop: true`). On refusal, notify the guard's reason verbatim and return.
4. `pi.setModel(target)` inside a `try/catch`. A thrown error is reported as a refusal naming the model; a `false` return is reported as a refusal naming the model. Neither is swallowed and neither is retried with a different model — a substitution here is exactly the silent degradation criterion 3 forbids.
5. Only after a `true` return: update the module state (`setMode`), clear any escalation, `pi.appendEntry(MODE_ENTRY_TYPE, <KyModeData>)`, then derive the subagent pins with `agentOverridesFor(state)` and, **only when it returns `ok: true`**, call `writeAgentOverrides(result.overrides)`. `agentOverridesFor` returns a discriminated result because it runs the capability guard over each subagent role's candidates (plan 05); an `ok: false` here is a refusal with a reason, carried into step 6's message — it must NOT be unwrapped, coerced to `{}`, or written anyway.
6. Report the outcome through `ctx.ui.notify`, naming the mode and the concrete `provider/id` that now serves the executor. If step 5's settings write returned a refusal, say so in the SAME message — "mode switched; subagent pins unchanged because <reason>" — rather than failing the whole switch or reporting an unqualified success.

The `ky:mode` payload is exactly `KyModeData` (mode name, escalation flag, `escalatedFrom`,
timestamp). It carries no model id: Pi already persists the executor model natively through
its own `model_change` entry (`session-manager.js:790-801`, restored by
`getSessionContextSettings`, `:146-161`). Re-persisting it here would create a second source
of truth that can disagree with Pi's own resume path. Put that sentence in the file.
