  <action>
Create `.pi/extensions/routing/modes.ts`. Named exports only, no default export.

**State.** Mode and escalation live in ONE process-wide slot keyed on `globalThis`, using the
pattern documented at `.pi/extensions/diagnostics/index.ts:192-224` and citing it in a
comment. Phase 2 observed this for real: two jiti module instances each started their own
counter and silently stamped the same correlation id. Two instances each holding "the current
mode" would let `/max` appear to take effect while a later read reports `cheap`.
Export `getModeState(): KyModeData`, `setMode(mode)`, `setEscalated(escalated, from?)`. The
initial state is `{ mode: DEFAULT_MODE, escalated: false, at: <now> }`.

**Resolution.** `resolveRoute(role, state)` returns the `RoleRoute` that applies right now:
`ROLE_MAP[state.mode][role]`, except that when `state.escalated` is true and the role is
`executor`, it returns `ROLE_MAP[ESCALATION_MODE].executor`. Escalation lifts the executor
only — that is ROUTE-03's "pulls a stronger model", not a whole-mode switch, and it is why
`KyModeData` carries `escalatedFrom`.

**Candidate selection.** `pickConfiguredCandidate(registry, candidates)` takes a MINIMAL
STRUCTURAL interface — `{ find(provider, id): Model<Api> | undefined; hasConfiguredAuth(model): boolean }`
— not an `ExtensionContext`. `ctx.modelRegistry` satisfies it structurally, and a plain object
satisfies it in a unit test, so this is testable with no session. It walks the candidates in
order and returns the first that both resolves AND has configured auth; otherwise it returns
a refusal whose reason names EVERY candidate tried and states which failed to resolve versus
which had no configured auth. `find`, `hasConfiguredAuth`, `getAvailable`,
`getProviderAuthStatus` are the sanctioned lookups (`chokepoint-lint.test.ts:99-104` names
this exact set as Phase 5's); `complete`/`completeSimple`/`stream`/`streamSimple`/`getProvider`
must not appear anywhere in this file, including comments.

**Planning.** `planRoleCall(registry, { role, state, need })` returns
`{ ok: true; model; mechanism; reasoningEffort? }` or `{ ok: false; reason }`. Order is
binding: resolve the route → pick a configured candidate → run `guardRoute(model, role, need)`
→ only then report a mechanism. `need.usesToolLoop` is derived from `ROLE_MECHANISM` via the
exported `usesToolLoop(role)` helper (`true` for `set-model` and `subagent` roles) so ROUTE-08's
deny-list scope is decided in one place. A guard refusal is returned verbatim as the plan's
reason — never rewritten, never downgraded to a warning, never followed by a substituted model.

**Dispatch.** `runSingleShotRole(ctx, { role, messages, systemPrompt, need })` is the impure
half and is used only by roles whose mechanism is `call-model`. It calls `planRoleCall` with
`ctx.modelRegistry`; on refusal it throws an `Error` carrying the reason (the caller is a
command or a tool that reports it — a refusal must never be swallowed into a `undefined`
result). On success it calls:
- `callWithFallback(ctx, {role, systemPrompt, messages, api})` when `usesFallbackChain(ref)`
  is true — i.e. the chosen `{provider,id}` is a member of `CHAIN` imported from
  `providers/schema.ts`. Reuse the real constant; a second hand-written list is how the two
  drift apart;
- `callModel(ctx, {role, model, systemPrompt, messages, api})` otherwise — a Bedrock-pinned
  role has no hop in `CHAIN` by design (`providers/schema.ts:340-347`).
`api` carries `{ reasoningEffort }` when the route declares one and is omitted entirely
otherwise — this is ROUTE-04's "per-call reasoning effort". Pass `role` through unchanged as
the join key. **Do not pass `signal`**: `callModel` defaults it to `ctx.signal`, so Esc
cancels nested work for free. **Never touch `ctx.model`, never call `pi.setModel`, never
append a session entry from this path** — ROUTE-04 is explicitly "not by mutating session
state", and `tests/integration/single-shot-roles.test.ts` (plan 06) asserts it.

Export `usesFallbackChain(ref): boolean` and `usesToolLoop(role): boolean` as pure functions
so both are unit-testable without a session.

Docstring: PURPOSE, the THREE MECHANISMS and which roles take which, the plan/dispatch split
and why, the state-slot hazard with its citation, the "escalation lifts the executor only"
rule, and a note that the fallback CHAIN is fixed and not parametrized by mode (RESEARCH A.4)
— so nobody later tries to give `max` its own chain.
