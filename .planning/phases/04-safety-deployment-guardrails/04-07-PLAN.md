<objective>
Compose the four classifiers into one decision function whose DEFAULT BRANCH IS DENY, and
build the approval store that makes "block → approve → re-issue" safe against approving a
different command than the one that was blocked.

Purpose: `noOpUIContext.confirm` returns `false` and `select` returns `undefined`, and
`hasUI()` is an object-identity check, not a mode string. A guard written as "allow unless a
check says no" therefore permits everything under `--mode json`. Writing the deny as the
default branch is what makes fail-closed a property of the code's shape rather than of a
test that might be deleted.
Output: `.pi/extensions/safety/policy.ts`, `.pi/extensions/safety/approvals.ts` and their
unit tests.
</objective>

Create `.pi/extensions/safety/policy.ts` exporting `evaluate(toolName, input, facts)` and the
`Verdict` type: `{kind:"allow"} | {kind:"confirm", reason, requestKey} | {kind:"block",
reason}`. `facts` carries `{ cwd, projectRoot, home, currentBranchFor(cwd), protectedBranches,
kubeconfigEnv? }` — every environmental fact is supplied by the caller, keeping this module
pure and fixture-drivable. `currentBranchFor` is a function so the composer can resolve the
branch of the invocation's `cwdOverride` lazily and only when a git invocation is actually
present.

Write EVERY decision as "start from deny, promote to allow on an explicit positive match".
Concretely: initialise the verdict variable to a block, and let each classifier upgrade it;
never initialise to allow and let classifiers downgrade. That inversion is the whole
difference between fail-closed and fail-open under `noOpUIContext`, and RESEARCH.md Pattern 4
documents the exact anti-pattern (`if (ctx.hasUI && !ok) block`) that must not appear
anywhere in this file. Add a comment stating the rule so a later reader does not "simplify"
it back.

Evaluation order for `bash`, stated in a comment and pinned by a fixture:
1. `canonicalise` — a refusal here terminates immediately (SAFE-03 fail-closed);
2. for each canonical invocation, in order: git/glab classification (needs
   `currentBranchFor(invocation.cwdOverride ?? facts.cwd)`), infra classification, then
   path classification over every argument that canonicalises to a path;
3. the STRONGEST verdict across all invocations and all classifiers wins — a block anywhere
   in a multi-segment command blocks the whole command. `cd /tmp && git push` must not be
   allowed because segment one is harmless.

For `read`, apply `classifyPathRead` to the `path` parameter. For `write` and `edit`, apply
`classifyPathWrite`. Handle a missing, empty or non-string parameter as a block naming the
malformed shape — Pi performs no re-validation after a `tool_call` mutation, so a malformed
input reaching the wrapper is exactly the case where the guard must not fall through.

`requestKey` on a confirm verdict is a stable fingerprint of `{toolName, exact input string,
cwd}` — Plan 08's approval flow keys the one-shot grant on it, and it must be derivable
identically at the hook and at the wrapper so a grant issued at one is consumable at the
other.

Create `tests/unit/policy-compose.test.ts` as a table over raw inputs covering every row in

Hold both maps in a `globalThis`-keyed slot, following the pattern documented at
`.pi/extensions/diagnostics/index.ts:192-224` and citing it. This is not defensive
programming — the `tool_call` hook and the wrapped tool `execute()` in Plan 08 reach this

every approved command is blocked forever with no error. Phase 2 already hit exactly this
with the correlation counter.

`validate` checks all three of id, command and reason. That triple is what prevents the model
from approving an EDITED command against a legitimate blocked request — the exact
vulnerability CONTEXT.md decision 5 names, where a later handler mutates `event.input` after
approval. Keying the GRANT on `requestKey` rather than on the request id is the other half:
the same command re-issued through a different tool call still consumes the grant, and a
different command does not.

`APPROVAL_TTL_MS` is `10 * 60 * 1000`, carried from the reference implementation. Take an
injectable `now` on every function that reads time so `tests/unit/approvals.test.ts` proves

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model-supplied approval arguments → grant store | The model chooses the request id, command and reason it submits to the approval tool; none of it is trusted |
| hook decision → wrapper decision | Two evaluation points in one process that must agree on the same grant, reached through different import paths |
| headless run (`--mode json`, `-p`, subagent) → confirmation | No UI is bound; `confirm()` is `false` and `select()` is `undefined` by construction |

| T-04-09 | Spoofing | approval laundering | mitigate | `validate` requires request id AND byte-for-byte command AND reason; the GRANT is keyed on `requestKey` (tool + exact input + cwd), so a grant for command A cannot be consumed by command B |
| T-04-37 | Elevation of Privilege | stale grant reuse | mitigate | One-shot `consume` plus a 10-minute TTL on both the pending entry and the grant, proven with an injected clock |
| T-04-38 | Elevation of Privilege | malformed `tool_call` input | mitigate | Missing, empty or non-string `command`/`path` is a BLOCK naming the malformed shape — Pi performs no re-validation after a hook mutation, so a malformed input reaching the wrapper must not fall through |
