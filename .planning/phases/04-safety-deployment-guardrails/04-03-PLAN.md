<objective>
Build the phase's parser layer: a recursive walk of `unbash`'s AST that (a) refuses the
specific node kinds that make a command unclassifiable, and (b) resolves wrapper
executables so policy is later evaluated against `git push`, not `env`.

Purpose: this is the single most important design correction the research produced.
`unbash` is a TOLERANT parser — it returns `errors.length === 0` for `git $(echo push)`,
heredoc-to-script, `nohup git push &`, `sh -c "git push"`, `env -i git push` and
`git -C /other/repo push`. "Fail closed on parse error" would therefore ship a guard that
fails closed almost never. SAFE-03 must be implemented as a node-type presence check.
Output: `.pi/extensions/safety/shell.ts` plus two table-driven unit tests.
</objective>

    - `git status` → verdict `{ kind: "ok" }` with one canonical invocation `{ executable: "git", args: ["status"] }`
    - `git $(echo push)` → verdict `{ kind: "refused", cause: "command-substitution" }`
    - `git \`printf push\`` → refused, same cause (backticks lex to the same node kind)
    - `diff <(git log) <(git log origin/main)` → refused, cause `process-substitution`
    - `cat > /tmp/d.sh <<'EOF'\ngit push\nEOF` → refused, cause `heredoc`
    - `nohup git push &` → refused, cause `background`
    - `g=push; git $g origin main` → refused, cause `unresolved-expansion-in-command-position`
    - `echo "$HOME"` → NOT refused for the expansion alone (an unresolved expansion in pure argument position that no policy pattern inspects is not itself a cause)
    - `git $((1+1))` containing an arithmetic command expansion → refused
    - Any input for which `parse()` returns `errors.length > 0` → refused, cause `parse-error` (kept as a final catch-all, never as the primary mechanism)
    - `g"i"t p'u'sh` → NOT refused by this predicate: quoting is resolved by unbash into `Word.value === "git"`, so the canonical invocation is `git push` and the DENY is policy's job, not the parser's
  </behavior>

The refusal walk is recursive over the whole `Script`, not over the top level only —
a `$(...)` hides inside a `DoubleQuoted` word part, inside a pipeline element, inside an
and-or list, inside a subshell. Walk every `Word.parts[]` including nested quoted parts,
every `Redirect.operator`, and every `Statement.background`. Refuse if any of the six causes
in `<behavior>` is present anywhere.

The unresolved-expansion rule is POSITION-SENSITIVE and this is where it is easy to get
wrong in both directions. Refuse an expansion part (`SimpleExpansion` / `ParameterExpansion`
— use the exact spellings from `unbash-ast.test.ts`) when it appears in the **command-name
word**, because that is literally `g=push; git $g`. Do NOT refuse it for appearing in an
ordinary argument the policy never inspects; the over-broad form breaks `echo "$HOME"` and
every ordinary command a session runs, which trains reflexive approval — the same failure
mode Pitfall 4 names for `aws`. Argument-position expansions become relevant only when the
argument is compared against a path pattern, which Plan 04 handles in `paths.ts` by refusing
at comparison time.

Include `errors.length > 0` as a final catch-all cause `parse-error`, with a comment
stating plainly that it is NOT the primary mechanism and citing the executed finding.

Create `tests/unit/shell-deny-list.test.ts` as a table of `{ input, expected, why }` rows
covering every row in `<behavior>`, plus at least one row per PITFALLS.md bypass class that
this predicate is supposed to catch. Each row's `why` names the requirement or bypass class.
Add a liveness guard in this repo's established style: assert the table is non-empty before
looping, and prove each `cause` value is reachable by at least one row — a cause no fixture
produces is a branch no test exercises.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model-emitted `bash.command` string → guard | Fully untrusted input; a confused cheap model produces obfuscated forms without adversarial intent |
| parsed AST → policy layer | The canonical invocation is what every later policy decision trusts; a wrong resolution is a silent allow |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Tampering | `canonicalise()` in `shell.ts` | mitigate | Recursive node-type deny-list over the full `unbash` AST (command substitution, process substitution, arithmetic command expansion, heredoc redirect operators, `Statement.background`, unresolved expansion in command position), NOT an `errors.length` check — the executed finding in `tests/unit/unbash-ast.test.ts` shows all seven adversarial inputs parse with zero errors |
| T-04-16 | Elevation of Privilege | wrapper resolution | mitigate | Tabulated `env`/`sudo` option grammars with a fixture per value-taking flag; `sudo -u root git push` asserted to resolve to `git`, closing Pitfall 2 |
| T-04-17 | Elevation of Privilege | nested shell (`sh -c`, `xargs`, `bash -lc`) | mitigate | Resolved-executable membership in `SHELL_RUNNERS` combined with `GUARDED_VERB_PATTERN` over the raw segment text → refuse outright. Accepted over-block documented as Assumption A3 |
| T-04-18 | Elevation of Privilege | `git -C /other/repo` | mitigate | `-C` / `--git-dir` captured as `cwdOverride` so the `HEAD == main` oracle in Plan 05 runs against the repository the command actually targets |
