<objective>
Wire the policy layer into Pi twice — once at the `tool_call` hook for UX and early
rejection, and once inside the wrapped tool's `execute()` as the actual last checkpoint —
and register the approval tool that turns a "requires confirmation" verdict into a
structured, re-issuable protocol instead of a blocking dialog.

Purpose: Pi's own extension types state that `event.input` is mutable, that later `tool_call`
handlers see earlier mutations, and that **no re-validation is performed after mutation**. A
hook-only guard is therefore defeated by any later-loaded extension. The wrapper is what
closes it, because it evaluates whatever input actually reaches execution.
Output: `.pi/extensions/safety/index.ts`, the allowlist edit that CONTRIBUTING.md requires in
the same commit, an entry-point shape test, and the double-enforcement integration proof.
</objective>

allows. Write an audit row for the exception before returning.

**Register the wrapped tools FIRST, before any hook registration**, and add a comment citing

if another extension registers a tool named `bash` before this one, the safety wrapper never
executes and there is no error anywhere. Use the exported factories

against the params it actually receives, consumes any matching one-shot grant, writes an
audit row, and on a non-allow verdict THROWS with the reason (a throw surfaces as
`isError: true` to the model, which is the behaviour we want).

**The `tool_call` hook** fires for `bash`, `read`, `write`, `edit`. It calls `evaluate()`,
writes an audit row for every verdict including allows, and:
- allow → return `undefined` (do not mutate `event.input`);
- block → return `{ block: true, reason }`;
- confirm → `createPending(...)` and return `{ block: true, reason }` where the reason embeds
  the request id and a literal instruction to call `approve_ky_command` with that id and the
  exact command. Do NOT set `terminate` — RESEARCH/CONTEXT both note it applies only to a
  blocked call and only stops the agent when every finalized result in the batch terminates,
  so it is not an enforcement mechanism.
Never call `ctx.ui.confirm()` or `ctx.ui.select()` from inside the hook.

**`approve_ky_command`** is the one registered tool that is not a wrapper. Parameter schema
via `Type.Object` from unscoped `typebox`, using `StringEnum` from `@earendil-works/pi-ai`
for any string-enum field (never `Type.Union`/`Type.Literal` — CLAUDE.md's "What NOT to Use"
says that breaks against Google's API). Fields, following the verified reference shape:
`request_id`, `command`, `reason`, `summary`, `blast_radius`. Its `execute()`:
1. `validate(request_id, command, reason)` — all three, byte-for-byte;
2. if `ctx.hasUI` is false, or `ctx.ui.select(...)` returns `undefined` or anything other
   than the explicit approve choice → refuse, write a block audit row, return an error. Write
   this as `approve only on an explicit affirmative`, never as `refuse only when the UI said
   no`;
3. on approval → `approve(...)`, write an audit row, and return text telling the model to
   re-issue the identical command.
Omit `promptSnippet` and `promptGuidelines` entirely — CONTRIBUTING.md's corollary says
prompt metadata rebuilds the system prompt and invalidates the provider cache prefix.

Call `pruneAuditLogs(ctx.cwd)` from `session_start`, mirroring how diagnostics prunes its own

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `tool_call` handler chain → tool execution | `event.input` is mutable in place, later handlers see earlier mutations, and Pi performs no re-validation (`types.d.ts:687-688`) |
| extension registration order → active tool set | Tool-name collisions resolve first-registration-wins (`runner.js:280-291`) — the opposite precedence from the mutation hazard, and equally load-order dependent |
| model → `approve_ky_command` | The model supplies every argument to the approval tool, including the command it claims was blocked |
| extension exception → Pi runtime | Pi swallows every exception a handler throws (`runner.js:861-870`), so an unhandled bug is silently an allow |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-02 | Tampering | post-approval `event.input` mutation | mitigate | Enforcement twice: `tool_call` hook for UX/early rejection AND wrapped tool `execute()` re-running `evaluate()` against the params that actually reach execution. Proven by `tests/integration/double-enforcement.test.ts` case 2, with the audit allow+block pair as the signature |
| T-04-08 | Tampering / Denial of Service | tool-name collision (another extension registers `bash` first) | mitigate + accept | Wrapped-tool registrations run first in `safety/index.ts` and `tests/unit/safety-entry.test.ts` pins that source order. Residual: an extension installed earlier in Pi's own load order could still win the name. Documented in `docs/SAFETY.md` (Plan 11) and compensated by SAFE-01 |
| T-04-03 | Elevation of Privilege | approval under `noOpUIContext` | mitigate | `approve_ky_command` approves only on an explicit affirmative from `ctx.ui.select`; `undefined` (the headless value) and `hasUI === false` both refuse. No `ctx.ui.confirm(` appears in the file, asserted by grep |
| T-04-09 | Spoofing | model-supplied approval arguments | mitigate | `validate(request_id, command, reason)` checks all three byte-for-byte before any UI is shown; the grant is one-shot and keyed on the request fingerprint |
| T-04-42 | Elevation of Privilege | guard exception → silent allow | mitigate | Local `guarded(...)` wrapper fails closed (`{block:true}` from the hook, rethrow from the wrapper) and writes an audit row before returning, because Pi swallows handler exceptions |

| T-04-43 | Information Disclosure | approval tool schema cost | mitigate | `promptSnippet`/`promptGuidelines` omitted so activation never rebuilds the system prompt; schema token cost MEASURED and recorded in the allowlist justification per CONTRIBUTING.md (b) |
