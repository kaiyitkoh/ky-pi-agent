### WR-02: The comment-only verifier silently passes added files, and it still never runs by default

**File:** `tests/unit/comment-only-diff.test.ts:63-66, 75-80, 86-89`; the `describe.skipIf(REF === "")` call.

**Issue:**
1. A path that is absent at the ref is pushed to `added` and only logged with `console.info`. No assertion fails.
   - `package.json` sets `pi.extensions: ["./.pi/extensions"]`, and Pi auto-discovers extension directories. A new `.pi/extensions/foo/index.ts` in a "comment-only" range therefore changes runtime behaviour without touching any compared file, and the verifier stays green.
   - The `COMMENT_DIFF_EXEMPT` sanity check makes this worse. It requires every exempt entry to be a *compared* pair, so an intentionally added file cannot be declared at all. The phase-base run passes only because `harness/comment-rules.ts` falls into the silent `added` bucket.
2. WR-04 item 1 from iteration 1 is still open. Without `COMMENT_BASE_REF` the whole equivalence block is skipped, so CI never proves anything. The fix report defers this.

**Fix:**
```ts
it("adds no file unless it is declared", () => {
	const undeclared = added.filter((p) => !EXEMPT.includes(p));
	expect(undeclared, "new authored files since the ref; list them in COMMENT_DIFF_EXEMPT").toEqual([]);
});
// and let the EXEMPT sanity check accept entries found in either `pairs` or `added`.
```
Then run the block in CI against `git merge-base HEAD origin/main`, or fail loudly when `CI` is set and the ref is empty.

### WR-03: The two citation gates can be bypassed by bare filenames and by any version string in the same comment

**File:** `tests/helpers/comment-scan.ts`, `LINE_CITATION`, `findRepoLineCitations` and `findUnversionedCitations`.

**Issue:** The two gates miss each other's cases:
- **Bare in-repo citations are treated as external.** `LINE_CITATION` requires at least one `dir/` segment. A bare in-repo citation such as `budget.ts:225` or `pinning.test.ts:253` (the form WR-01 found in `quality/gates.ts`) is never classified as in-repo. It falls through to the "external" gate.
- **One version anywhere exempts the whole comment.** `findUnversionedCitations` returns `[]` as soon as `\b\d+\.\d+\.\d+\b` matches anywhere in the comment.
  - A module header that names `pi 1.1.0` once, or contains `127.0.0.1` or `node 24.16.0`, exempts every other `file:N` in that block.
  - That includes stale in-repo line citations, and any `0.84.1`-era citation left unversioned beside a re-verified one (for example `safety/index.ts:339-343`, where the shared `pi 1.1.0` covers `agent-session.js:326-343`).

The gates are the ratchet that stops WR-01 and WR-02 from recurring, and both are silently bypassed by common shapes.

**Fix:**
- Classify a citation as in-repo when its basename matches any tracked file's basename. That allows `(?:[\w.-]+\/)*`.
- Require the version token to sit near each citation. For example, check the same line or the 40 characters before the citation (`/(?:pi(?:-ai)?|@)\s*\d+\.\d+\.\d+[^\n]{0,40}$/` on the prefix), rather than anywhere in the comment.
- Add self-tests for `"// pi 1.1.0 runner.js:410; see budget.ts:225"` (expect a hit) and `"// 127.0.0.1 runner.js:410"` (expect a hit).

### IN-01: Edge cases in the heading matcher that cause double or missed delivery

**File:** `.pi/extensions/harness/comment-rules.ts:18-19`

**Issue:** None of the following are handled:
- `## Code comments ##`, a valid ATX heading with closing hashes;
- a heading indented 1-3 spaces;
- an unclosed fence, which CommonMark treats as code to end-of-file, but where the regex still scans the remainder;
- a fence closed with more backticks than it opened with (```` ```` ```` closing ```` ``` ````), which fails to match and so extends the "fence" to a later one, hiding a real heading.

**Fix:** Use `/^ {0,3}##[ \t]+code comments(?:[ \t]+#+)?[ \t]*\r?$/im`, and handle an unclosed fence by stripping to end-of-file.

### IN-02: Forced-prompt delivery is undocumented, and only one ordering is tested

**File:** `docs/EXTENSIONS.md:756-762`; `tests/unit/comment-rules-delivery.test.ts` (`forcedSource`)

**Issue:**
- The docs section describes only the `sections` mechanism and the skip rule. It does not say that a non-empty forced prompt gets the rules appended, that an empty one is left alone, or that a forcer which runs *after* the harness with literal text drops the rules.
- The test covers only the case where the forcer registers before the harness.
- When a context file has the heading, the harness returns early, so a forced prompt that omits project context then carries no rules at all.

**Fix:**
- Add these three behaviours to the docs bullet list.
- Add a test with the harness first and a forcer returning `event.systemPrompt + "X"`. It should assert that the rules appear exactly once.

### IN-03: The widened ID pattern has likely false positives

**File:** `tests/helpers/comment-scan.ts:60-74`

**Issue:** The `#\d{3,}` branch matches all-digit hex colours (`#000000`, `#123`). The 4-digit branch `[A-Z][A-Z0-9]{0,5}-\d{1,4}` matches legitimate external standards citations (`RFC-9110`, `ISO-8859`, `ES-2022`). `\d{2}\.\d-\d{2}` matches numeric ranges such as `12.5-15`. Only `CVE-\d{4}` is allowlisted. None of these occur today, so the gate passes.

**Fix:** Add self-tests for `#000000` and `RFC-9110` and decide on each one. Prefer a narrow lookbehind such as `(?<![\w&])#\d{3,}(?![0-9a-fA-F])` plus an `RFC-\d+` allowlist entry.
