**Install** — two paths, stated as alternatives rather than a sequence. Path A is `pi install https://github.com/kaiyitkoh/ky-pi-agent`. Path B is clone then `sh bin/bootstrap.sh`. **Supply chain — what is protected and what is not.** This is ROADMAP success criterion 1's README obligation and it must be honest rather than reassuring. Open with the asymmetry that justifies the whole phase: `pi install` executes npm lifecycle scripts with no `--ignore-scripts` on any code path, while Pi installs *itself* with `--ignore-scripts`. Then state coverage as a list. Covered by the committed root `.npmrc`: the developer's own `npm install` in this repo, and the `npm install --omit=dev` Pi runs inside a clone of this repo. Covered after bootstrap by `~/.pi/agent/npm/.npmrc`: every `pi install npm:*` at user scope. Covered by the committed `.pi/npm/.npmrc`: project-scope `pi install -l`. **Not covered:** third-party *git* packages, whose clone directory is created fresh by `git clone` so no file can be pre-placed in it; and any `pi install` run on a machine where bootstrap has never been run. For the uncovered cases give the one-shot ritual `npm_config_ignore_scripts=true pi install <url>`, and warn against setting that variable persistently — Pi passes the inherited environment to everything it spawns, including the `bash` tool, so a persistent setting would silently skip legitimate native builds inside a session.

**Second machine / macOS setup** — a short numbered list: install Node ≥ 22.19.0 and Git (Git Bash on Windows); clone the repo; run `sh bin/bootstrap.sh`; verify with `sh bin/bootstrap.sh --assert-hardening`, which exits non-zero if any npm scope still permits lifecycle scripts. State that the repo-scoped `.npmrc` travels with the clone but the user-scope control does not — it is machine state, and bootstrap is how each machine acquires it. Mention `--check-only` as the non-mutating variant CI runs.

**Session sharing** — one short paragraph. `/share` uploads the full session transcript to a GitHub gist and cannot be blocked by any extension, because built-in slash commands are dispatched before extension commands and before the `input` event. `gh auth status` exiting non-zero is the only control. Run `sh scripts/check-gh-unauthenticated.sh` to check the current state and `gh auth logout` to apply it, noting that on a machine using git-over-HTTPS this removes your git credential too.
