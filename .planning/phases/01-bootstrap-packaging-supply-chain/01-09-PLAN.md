<objective>
Write the house rule that governs every later phase's capability decisions, ground it in the three source facts that make it economic rather than aesthetic, and prove Phase 1 does not break it in the commit that writes it.

Purpose: A tool's name, description and complete JSON Schema are serialised into `tools[]` on **every** provider request (`pi-ai/src/api/openai-completions.ts:1337-1370`). A command costs zero — commands are never rendered into the system prompt (`pi/src/core/system-prompt.ts` contains no reference to registered commands). With DeepSeek cache reads roughly 50× cheaper than fresh input, activating a tool that carries `promptGuidelines` rebuilds the prefix and invalidates the cache. That is an economic cost, and it is the whole reason this project exists.

Output: `CONTRIBUTING.md` and a test that makes BOOT-10 a gate.
</objective>

Create `CONTRIBUTING.md`. Keep it short and load-bearing — this is a personal harness with one contributor, so no code of conduct, no PR templates, no issue triage process, no team structures.

Section **Boundary rule** — the BOOT-10 requirement, stated so a grep can find it. A new capability is a **command** or a **skill** unless you can state why it must be a tool. Give the three source-cited facts: a tool's `name`, `description` and complete JSON Schema ride in `tools[]` on every provider request (`pi-ai/src/api/openai-completions.ts:1337`); a command costs zero because commands are never rendered into the system prompt (`pi/src/core/system-prompt.ts`); a skill costs roughly 40–60 tokens for name, description and path, with its body loading only when read. Then give the three questions a tool registration must answer: (a) must the *model* call this mid-turn, or is the *user* the initiator — an unanswered (a) is an automatic no; (b) what is the measured token cost of its schema; (c) why can a skill not carry this as a procedure. Add the corollary: lazily-loaded tools omit `promptSnippet` and `promptGuidelines`, because activating a tool that carries them rebuilds the system prompt and invalidates the provider cache prefix.

Section **Dependency policy** — every third-party dependency is pinned to an exact version with a committed lockfile. Explain the apparent contradiction before someone "fixes" it: the five entries in `peerDependencies` carry the range `"*"` because `docs/packages.md:171` mandates it — they are host-provided and jiti aliases every one of them to Pi's own bundled copies at `loader.ts:118-140`. The exact pin lives in `devDependencies` and in `package-lock.json`. Bundling any of them creates a second module instance and breaks type and instance identity across the boundary. Use unscoped `typebox`, never `@sinclair/typebox`. State the package-source rule: every third-party package source written into `settings.json` must carry a version or a git ref; this repo's own URL is the single documented exemption, because BOOT-02 mandates that literal unrefed command and reconciling to our own default branch is desired.

Section **Supply chain** — `ignore-scripts=true` is a committed control, not a preference. State the coverage honestly: the repo-root `.npmrc` covers the developer's own `npm install` and the `npm install --omit=dev` Pi runs inside a clone of this repo; `~/.pi/agent/npm/.npmrc` (written by `bin/bootstrap.sh`) covers `pi install npm:*`; `<repo>/.pi/npm/.npmrc` covers project-scope `pi install -l`. **Third-party git packages remain uncovered**, because their clone directory is created fresh by `git clone` and no file can be pre-placed there — for those, use the one-shot ritual `npm_config_ignore_scripts=true pi install <url>` or install and review. Never set that variable persistently: Pi passes `env: getEnv()` to everything it spawns, so it would silently break legitimate native builds inside the `bash` tool during a session.

Section **Repo rules** — no build step, ever (jiti loads `.ts`; a build breaks `/reload`). POSIX `sh` only; never PowerShell. Never place a `.gitignore` inside `.pi/extensions/` — the package-discovery path honours it and the project-local path does not, so it makes `pi install` silently lose the harness while dogfooding still works. `.pi/prompts/` discovery is flat, non-recursive. Match Pi's own TypeScript and vitest pins rather than latest.

Section **Verifying a change** — the quick command `npx vitest run tests/unit`, the full command `npx vitest run && npx tsc --noEmit`, and the note that CI additionally runs `shellcheck --shell=sh` on Ubuntu and executes `sh bin/bootstrap.sh --check-only` on Windows and macOS.
