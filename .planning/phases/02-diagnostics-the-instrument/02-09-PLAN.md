Extend the `message_end` handler in `.pi/extensions/diagnostics/index.ts` so that, after storing the finalized assistant message, it runs the prose check inside the same `safeHandler` wrapper.

Behaviour, in order:
- return early unless `event.message.role` is `"assistant"`;
- return early unless `isProseToolCall(event.message, pi.getActiveTools())` is true;
- record the verdict on the in-flight turn accumulator so the turn's own row carries `event: PROSE_EVENT` **alongside** its `stopReason`, not instead of it — RESEARCH §3.3 is explicit that the detector verdict is recorded next to the stop reason;
- append an immediate turns-log record carrying `event: PROSE_EVENT`, the matched tool name from `proseToolCallName`, the session id and the current correlation id, so the event is recorded even if the turn row is later lost;
- if the per-run retry counter has reached `MAX_PROSE_RETRIES`, append a record with `event: PROSE_EXHAUSTED_EVENT` and return without retrying — a second prose response is a signal, not something to keep paying for;
- otherwise increment the counter and call `pi.sendUserMessage(<the retry prompt>, { deliverAs: "followUp" })`. Add a comment stating that `deliverAs` is mandatory here because the agent is streaming inside `message_end`, and that `followUp` resumes the same run rather than starting a new one, so `/session` accounting stays coherent.

The retry prompt is a single sentence naming the failure and the remedy, in the shape: the previous message described a tool call in prose instead of emitting one; re-issue it as a real tool call. Export it as a named constant from `schema.ts` if a test needs to assert on it, rather than duplicating the literal.

Reset the retry counter on `agent_start`, registered through `safeHandler`.

The handler must still return nothing. A returned `{ message }` would replace the finalized message — that is the promotion path, and it is deliberately not built.

Add a flag-guarded, **default-off** `tool_choice` lever: a module constant `PROSE_RETRY_FORCES_TOOL_CHOICE = false` with a docstring recording that the mechanism exists (a second `before_provider_request` handler returning a payload with `tool_choice: "required"` for exactly one retry request, RESEARCH §1.2) but that its effect on the prose rate is UNVERIFIED, so it stays off until the detector has produced a baseline.
