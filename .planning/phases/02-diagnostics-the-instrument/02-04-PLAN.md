<objective>
Build the pure half of the prose-tool-call detector: the predicate that decides
whether a finalized assistant message described a tool call in prose instead of
emitting one.

Purpose: this is the leading root-cause candidate for "DeepSeek misses bugs Sonnet
would catch" (~11%, DeepSeek-V3 issue #1244, still open). A false positive here is
worse than a miss — it doubles cost and fabricates the rate Phase 10 will use to
discriminate between root causes. Keeping the predicate pure and separate from the
retry effect is what makes it testable without a session at all.

Output: `prose.ts` and a positive/negative table test with a ReDoS bound. The retry
effect and its integration test are plan 02-09.
</objective>

  <action>
Create `.pi/extensions/diagnostics/prose.ts` as a pure, dependency-free module (type-only imports permitted).

Export `escapeRegExpLiteral(value: string): string` escaping the regex metacharacters, so a tool name containing a dot or a dash cannot alter the pattern's meaning.

Export `buildProseToolCallPattern(activeToolNames: readonly string[]): RegExp | undefined`. It returns `undefined` when the name list is empty — an empty list means there is nothing a prose tool call could be *about*, and matching anything then would be a pure false positive. Otherwise it builds a single alternation of the escaped names, word-boundary anchored, followed by bounded optional whitespace (at most 8 characters, expressed as a counted quantifier rather than `\s*`) and then a literal `(` with bounded optional whitespace and a literal `{`. Add a comment naming ReDoS as the reason the whitespace runs are counted rather than unbounded.

Export `isProseToolCall(message: AssistantMessage, activeToolNames: readonly string[]): boolean` implementing exactly four gates in this order, each with an inline comment naming what it rules out: the message `stopReason` must be the literal `"stop"`; the message must contain no content block whose `type` is `"toolCall"`; the active-name list must be non-empty; and the concatenated text of the message's `text` content blocks must match the built pattern. Never require `rawStopReason` — record it elsewhere as optional enrichment, because `fauxAssistantMessage` does not populate it.

Export `proseToolCallName(message: AssistantMessage, activeToolNames: readonly string[]): string | undefined` returning the matched tool name, so the retry prompt and the JSONL row can name it without re-running the match.

Module docstring in the `win-quote.ts` shape covering: *Why any of this exists* — the measured ~11% failure mode where a model writes `finish_reason:"stop"` with `tool_calls:null` and a function call in `content`; *Why it is a predicate and not a handler* — the effect (`sendUserMessage` with `deliverAs: "followUp"`) lives in `index.ts` so the interesting half is testable with no session; *The rules it implements* — the four gates above; and *The false positive that matters* — "Use `read({...})` to open the file" written as an explanation to the user is not a failed tool call, which is why the pattern is anchored to registered names and requires an immediately-following brace.

The file must not contain the substring `registerTool`.
