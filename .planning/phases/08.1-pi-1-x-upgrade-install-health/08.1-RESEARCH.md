## Summary

The upgrade is far less invasive than 20 releases suggests. A single `tsc` run (2.6 s, against the unpacked 1.1.0 `.d.ts` files via path mapping, repo TypeScript 5.9.3, repo `tsconfig` flags) shows **all 67 distinct `@earendil-works/*` symbols the repo imports still resolve, every production file under `.pi/extensions/**` (including the untracked `execute/progress.ts`) type-checks clean, and the only type delta is 7 call sites in `tests/integration/qoder-tool.test.ts`** (a test passes `ExtensionCommandContext` where `tool.execute` now requires `ExtensionToolContext`, which adds `tools` and `executeTool`). The real breakage is *runtime-semantic and invisible to tsc*: the faux provider and every provider adapter now receive a `TranscriptContext` (`{ messages }` with the system prompt and tool declarations carried by a leading `role: "system"` message), so `tests/helpers/faux.ts` builders and four test files that read `context.systemPrompt` / `context.tools` will silently see `undefined`.

Safety (D-03) has a clear answer found at source: **codemode nested tool calls DO reach the `tool_call` event** (`agent-session.js:326-343` `_beforeToolCall(..., parentToolCallId)`, wired for nested calls at `:388-416`, driven by `extensions/codemode/execute.js:399` `ctx.executeTool`), and they execute the registry's tool objects, so this repo's wrapped `bash`/`read`/`write`/`edit` and the double-enforcement design still apply to them. The gap is not nesting - it is that `registerToolCallHook` (`safety/index.ts:640-651`) returns `undefined` for every tool name outside the seven built-ins (documented as EV-42). The new 1.x paths that fall into that hole are `powershell` (an unparseable-by-`unbash` shell, inactive by default), `mcp__*` tools (callable from codemode even when inactive), and - because Phase 8.1 vendors it - `bg_run` (a background shell taking a `command` string). Recommendation: keep the explicit decision small - a deny table in the existing hook (fail closed, audited), the four built-in extensions disabled in project settings as defence in depth, and a faux-session test with a stub tool proving a nested `executeTool("bash", {command:"git push ..."})` is blocked.

Composed-extension re-pinning has one policy collision the planner must resolve explicitly: **`pi-subagents` has shipped compiled JavaScript (tsc output, `.js` + `.d.ts` + `.js.map` without `sourcesContent`) since ~0.68**, so Phase 7's "source-reviewable `.ts`" criterion cannot be met by any Pi-1.x-compatible version; `pi-background-tasks@2.6.9` compiles clean against 1.1.0 under strict (one error, in the Anthropic-attribution file we should not vendor) and its fusion/delegate/attribution code is feature-flag gated by default-on `PI_BG_FEATURES`, so vendoring a process-only subset (~16k lines, no `turndown` dependency) is feasible.

**Primary recommendation:** Execute as six small sequential plans (pins/config -> faux+test migration -> safety D-03 -> re-pin composed -> vendor bg-tasks -> docs/RUNBOOK), keep TypeScript at 5.9.3, install Pi globally via the existing idempotent `sh bin/bootstrap.sh` as one explicit human/RUNBOOK checkpoint *before* any test that spawns `pi`, and run the full suite exactly once at verification.

### Pattern 1: Read system prompt / tools from a TranscriptContext (faux and provider-side code)
```typescript
// Source: pi-ai 1.1.0 dist/utils/transcript.d.ts (exported from index via `export * from "./utils/transcript.ts"`)
import { getCurrentSystemPrompt, getCurrentTools, type Message, type TranscriptContext } from "@earendil-works/pi-ai";

export function transcriptView(context: TranscriptContext) {
	return {
		systemPrompt: getCurrentSystemPrompt(context.messages), // "" when no system message
		tools: getCurrentTools(context.messages),
		// non-system messages only - the system message is no longer a separate field
		messages: context.messages.filter((m): m is Exclude<Message, { role: "system" }> => m.role !== "system"),
	};
}
```

### Pattern 2: Prove a nested call is guarded without codemode
```typescript
// A stub extension tool whose execute() issues a nested call exactly as codemode does
// (execute.js:399: ctx.executeTool(name, args, {signal})). Source: types.d.ts:269-281 ExtensionToolContext.
pi.registerTool({
	name: "nested_probe", label: "nested_probe", description: "test only",
	parameters: Type.Object({}),
	async execute(_id, _p, _s, _u, ctx) {
		const outcome = await ctx.executeTool("bash", { command: "git push origin main" });
		return { content: [{ type: "text", text: JSON.stringify({ isError: outcome.isError }) }], details: {} };
	},
});
// Assert: outcome.isError === true, audit row carries the "<parent>/1" tool call id, wrapper never ran git.
```

### Anti-Patterns to Avoid
- **Registering a stub `powershell` tool to "guard" it:** extension-registered tools are pushed into the *active* set at boot (`_refreshToolRegistry`), which would ACTIVATE powershell and add per-turn schema tokens (safety/index.ts WR-09 comment). Block it in the hook instead.
- **Treating tsc green as proof for the faux migration:** `TranscriptContext` is structurally assignable to the repo's `Context` parameter types (all `Context` fields are optional except `messages`), so the helper compiles and fails at runtime.
- **Updating all 326 `0.84.1` mentions:** see Pitfall 8.

|---------|-------------|-------------|-----|
| Reading prompt/tools from a transcript | Own system-message replay | `getCurrentSystemPrompt` / `getCurrentTools` from pi-ai | Later system messages patch `sections` and add/remove tools; replay order matters |
| Disabling built-in extensions | A custom extension that unregisters tools | `"extensions": ["-builtin:mcp", ...]` in settings (package-manager.js:738-748) | First-class, listed by `pi config` |
| Excluding tools per run | Wrapper scripts | `--exclude-tools 'mcp__*'`, `--no-mcp`, `defaultTools` `-name` | Documented in cli.md / settings.md |
| Pinning Pi's transitive deps | Hand-written dependency table | Committed `package-lock.json` + `npm ci`; `--before` for global install | Integrity hashes already in lockfile |
| Bash classification of new command-taking tools | A second parser | Reuse `evaluate("bash", { command })` (safety/policy.ts) | One chokepoint, one evasion corpus |
| Version pin drift detection | New test | Existing `extension-pins` / `tool-count-baseline` / `vendor-license-audit` registries | They already diff both directions |

**Key insight:** every concern in this phase already has a repo-local chokepoint (the safety hook, the four paper registries, `bootstrap.sh`, `faux.ts`). The work is updating those chokepoints, not adding mechanisms.

## D-03 Safety: traced at source

**Q1. Does a codemode nested call reach `tool_call`? Yes.**
- `dist/extensions/codemode/execute.js:399`: `const outcome = await ctx.executeTool(tool.name, args, { signal: callSignal });`
- `dist/core/agent-session.js:2783`: context `executeTool: (callerId, name, args, options) => this._executeNestedToolCall(...)` -> `:388-416` builds a `NestedToolCallRunner`; its `runToolCall` calls `runToolCall(toolCall, { tools: this._getCallableTools(), beforeToolCall: (context) => this._beforeToolCall(context, parentId), afterToolCall: ... })`.
- `:326-343` `_beforeToolCall` -> `runner.emitToolCall({ type: "tool_call", toolName, toolCallId, parentToolCallId, input })`. Nested ids are `<parentId>/<n>` (`nested-tool-calls.js`), `ToolCallEventBase.parentToolCallId` (`extensions/types.d.ts:907-917`).
- Callable set (`:1066-1150`, `_getCallableTools`): every registered tool with `codemode`/`deferred` exposure **plus** active `direct` tools; objects come from `_toolRegistry`, i.e. this repo's *wrapped* `bash`/`read`/`write`/`edit` (first registration wins) - so the second enforcement layer (wrapper `execute()` re-check) also applies. `hidden` tools are not callable.
- Consequence: **codemode does not need to be disabled for the four wrapped tools.** What it newly exposes is every *other* registered tool, notably MCP tools (default MCP exposure is `codemode`, `mcp-servers.js:135`) that the model can call without them being active.

**Q2. powershell event shape.** `PowerShellToolCallEvent { toolName: "powershell"; input: PowerShellToolInput }` (`extensions/types.d.ts:922-925`); input is `{ command, timeout }` (same shell-tool factory as bash, `core/tools/powershell.js`). `allToolNames` includes it (`tools/index.js:19-28`); the tool is **inactive by default** (`DEFAULT_TOOL_NAMES` excludes it) and per docs/windows.md is available only on native Windows. It becomes active via `defaultTools` `+powershell` (user or project settings), `--tools`, or any extension's `setActiveTools`. `unbash` parses POSIX shell only, so PowerShell commands cannot be classified - **deny rather than guard**.

**Q3. Disabling.** There is no `-builtin:` for powershell (it is a core tool, not a built-in extension). Controls: leave it out of `defaultTools` (already), `--exclude-tools powershell` (CLI), and the hook deny. Built-in extensions (`settings.md:160`): `builtin:mcp`, `builtin:llama.cpp`, `builtin:codemode`, `builtin:tool-search` "load by default; `-builtin:mcp` disables one"; project `extensions` array entries override user ones (`package-manager.js:738-748`: `applyAutoloadDisabledPatterns(... projectSettings.extensions ...)`, falling back to user settings). `docs/settings.md:44`: codemode and tool_search register **inactive**. llama.cpp registers provider models, not tools. Project-scope settings require project trust (headless untrusted runs ignore them), which is why the hook deny is the load-bearing control and the settings entries are defence in depth.

## Common Pitfalls

### Pitfall 1: Green tsc, red runtime (TranscriptContext)
**What goes wrong:** `buildOpenAiFixturePayload(model, context: Context, ...)` still compiles when handed a `TranscriptContext`; `context.systemPrompt` is just `undefined`, payloads lose their system message/tools, and assertions fail (or worse, pass vacuously - e.g. `systemPrompt.length > 0` guards will fail, but "tools undefined -> []" paths pass).
**How to avoid:** Change the helper signature to `TranscriptContext`, add a `transcriptView()` accessor, and add a unit assertion in `tests/unit/helpers.test.ts` that a captured context's `getCurrentSystemPrompt` is non-empty.
**Warning signs:** `providerPrompt` undefined in `budget.test.ts`; message counts off by one in `wire-capture.test.ts`.

### Pitfall 2: Tests that spawn the real global `pi` run against the wrong version
**What goes wrong:** `tests/helpers/pi.ts` shells out to `pi` on PATH; `load-paths`, `user-scope-load`, `headless-deny`, `subagent-block`, `helpers.test.ts` exercise whatever is installed (0.84.1 today) while `node_modules` is 1.1.0 - mixed-version false greens.
**How to avoid:** Make the global reinstall (`sh bin/bootstrap.sh`) a checkpoint *before* the first targeted test of those files, and assert `pi --version` = 1.1.0 at the start of verification.

### Pitfall 3: The four paper registries drift
**What goes wrong:** Re-pinning in `.pi/settings.json` alone fails `extension-pins`, `tool-count-baseline`, `subagent-capabilities` (every `pi-subagents` evidence row in `docs/EXTENSIONS.md` must name the pinned version and the file:line citations were for 0.49.0 source), `extension-composition`, `vendor-license-audit`, and the `docs/EXTENSIONS.md` tables.
**How to avoid:** One plan owns all of them together. The `subagent-capabilities` rows cite `src/agents/agents.ts:1155`, `src/extension/index.ts:578`, `schemas.ts:327` etc.; 0.77.0 is compiled JS with a different layout (`src/extension/index.js:596` registers `subagent`; `src/runs/background/wait-tool.js:41` registers **`bg_wait`**, not `subagent_wait`; new `subagents_enable` loader in `src/extension/tool-activation.js`) - citations and tool-name lists must be re-derived, not renamed. The test only enforces version strings and shape, so honest re-verification is on the executor.

### Pitfall 4: Dynamic tool loaders change the active set
**What goes wrong:** `pi-subagents@0.77.0` (`tool-activation.js`) and `pi-web-access@0.38.0` (`tool-activation.ts`) register loader tools (`subagents_enable`, `web_enable`) and call `pi.setActiveTools(...)`, in "auto" mode hiding `subagent`/web tools until the loader is called (eager only for an empty session without mid-convo tool additions). This interacts with the vendored plan-mode (`setActiveTools`) and with tests that read the active set. Pi hosts below 0.86 warn and fall back to eager.
**How to avoid:** Re-derive tool names for `tool-count-baseline` including the loaders; note both loaders carry `promptSnippet` (rebuilds the system prompt when activated - CLAUDE.md warning) and record the per-turn cost via `/budget` at verification; pi-subagents has a config mode `eager` (`registerSubagentToolActivation` returns early for `mode === "eager"`) if the loader behaviour proves hostile (decide in Phase 10, not here).

### Pitfall 5: Pi 1.x loads built-in extensions the repo never asked for
**What goes wrong:** `builtin:mcp`, `builtin:llama.cpp`, `builtin:codemode`, `builtin:tool-search` load by default, and `--tools` allowlists keep MCP tools unless an entry starts with `mcp__` (`agent-session.js:1103-1115`). Test sessions that pass `tools: [...]` are insulated by the allowlist, but real sessions are not.
**How to avoid:** Settings entries + hook deny (above). Do not assume the settings entries apply in an untrusted project.

### Pitfall 6: Subagent child processes
**What goes wrong:** pi-subagents children run real `pi` processes that load the user-scope stub and built-ins. The `subagent-block` topology test already encodes this; 0.77.0 changes how children are launched (`child-session.js`, `runner-peer-loader.mjs`) and changelog notes "a session that declined project trust no longer takes models, agents, or settings from that project".
**How to avoid:** Re-run `subagent-block`, `subagent-config-merge`, `user-scope-load` targeted after the re-pin; confirm `~/.pi/agent/extensions/subagent/config.json` + `worktreeSetupHook`/`worktreeSetupHookTimeoutMs` are still read (verified present: `src/extension/config.js:230`, `async-execution.js:1366-1367`).

### Pitfall 7: Shrinkwrap removal silently widens the install-time dependency set
See Supply chain.

### Pitfall 8: Citation churn
326 lines outside `.planning/` mention `0.84.1` (docstrings with `[VERIFIED: pi 0.84.1 ... file:line]`). Rewriting them all is high-effort and low-value, and line numbers will not match 1.1.0 anyway.
**How to avoid:** Rule for the plan: (a) change every *operative* value (pins, install commands, stub stdout, user-facing remedy text, `bootstrap.sh` constant); (b) re-verify and re-stamp citations only in files whose logic this phase touches or whose claim changed; (c) add one sentence to CONTRIBUTING.md: citations name the Pi version they were verified against and are not retroactively re-stamped. Sweep for operative strings with `grep -rn "0\.84\.1" bin .github tests/helpers tests/unit tests/integration CONTRIBUTING.md` and decide per hit.

## Open Questions

1. **Compiled-JS `pi-subagents` vs the Phase 7 "source-reviewable `.ts`" rule.**
   - Known: every Pi-1.x-compatible release ships tsc output (`src/**/*.js`, `.d.ts`, `.js.map` with no `sourcesContent`); unminified and readable; deps exact; no lifecycle scripts; 11.9 MB.
   - Unclear: whether the user accepts reading emitted JS (the same posture that excluded `cc-safety-net`, but that one was a prebuilt multi-harness bundle).
   - Recommendation: accept with an explicit entry in `docs/EXTENSIONS.md` ("compiled, unminified, reviewed as JS; sourcemaps point at unshipped `.ts`") and keep it out of the tool-execution allow path (pi-subagents spawns `pi` children, it does not run model-supplied shell). If the user declines, the alternative is pinning 0.49.0 unverified on 1.1.0.
2. **Should the guard cover `bg_run`?** Not strictly a "new 1.x path" but D-02 puts a background-shell tool into the active set, and EV-42 documents that extension tools shelling out are a known hole.
   - Recommendation: yes - map `bg_run.command` through `evaluate("bash", ...)` in the hook (single layer, no wrapper registration). It is ~10 lines and the only way D-02 does not widen the bypass surface.
3. **Retain `defaultTools`/CLI hygiene for powershell?** Recommend only the hook deny + RUNBOOK sentence; no settings entry needed (not default).
4. **`tuiMode`:** fullscreen is the 1.x default; the user may want `"regular"`. Not a harness requirement; mention in RUNBOOK.
