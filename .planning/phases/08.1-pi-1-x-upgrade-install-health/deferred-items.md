## Resolution (fix(08.1-02), unattended)

- **DeepSeek flash id: RESOLVED by rename.** Evidence at source: `pi-ai@1.1.0 dist/providers/data/deepseek.json` has `chat:deepseek-flash` (`name: "DeepSeek V4.1 Flash"`, baseUrl `https://api.deepseek.com`, `input:["text","image"]`, ctx 1,000,000, maxTokens 384,000) and `deepseek-v4-pro`. Pi passes `id` verbatim as the API model, so `deepseek-flash` is what hits api.deepseek.com. `pi-coding-agent` CHANGELOG: "advertise `deepseek-flash` for DeepSeek V4.1 Flash instead of retired Flash aliases" (#9423). No alias/migration code exists for `deepseek-v4-flash` (grep of pi-ai/pi-coding-agent dist outside data JSON: nothing). Decision: the daily driver follows the built-in id; every operative direct-side reference renamed (`deepseek/deepseek-flash`) in routing/providers schema, docs, tests. DashScope-side `dashscope/deepseek-v4-flash` is a user-defined id from models-template (Alibaba-documented) and is unchanged; the deliberate id collision with the built-in now remains only for `deepseek-v4-pro` (model-metadata invariant test gained a per-record `builtin` id). Note the built-in is V4.1 Flash with image input and cost 0.3/1.2; the capability guard reads `input`, so image routing may now consider it vision-capable.
- **R1 side effect:** built-in `deepseek-flash` now ships `thinkingLevelMap.low = "low"`, so Pi can select/send `low` without the modelOverrides unclamp; `tests/unit/r1-unclamp.test.ts` case 1 updated (cases 2-3 unchanged). RUNBOOK RB-03-04 prep step is now redundant for flash.
- **Q7 strict: RESOLVED by re-decision.** `convertTools` still writes `strict` only when `compat.supportsStrictMode !== false`; 1.1.0 `detectCompat` now defaults `supportsStrictMode: false`, so detection omits `strict`. Omission is fine for DashScope (field optional/unlisted). Template keeps explicit `supportsStrictMode:false`; case 4 control assertion changed to "never `strict: true`".
