## Critical Issues

### CR-01: bg_run is classified with the bash parser but executes under cmd.exe on Windows

**Status:** FIXED in 9c78149. The background-tasks shell policy now defaults to bash on win32 (PROVENANCE deviation 7); the guard denies bg_run when the effective shell is not bash/POSIX (explicit PI_BG_SHELL=cmd, fish). Regression: tests/unit/bg-run-guard.test.ts.

**File:** `.pi/extensions/safety/index.ts:738`, `.pi/extensions/background-tasks/src/core/common.ts:937-947`
**Issue:** The hook runs `classifyAtWrapper("bash", {command})`, which parses the command with unbash. The vendored shell policy defaults on `win32` (the project's primary platform) to `ComSpec` with `/d /s /c` and `windowsVerbatimArguments: true`, unless `PI_BG_SHELL=bash` is set. Nothing in the repo sets `PI_BG_SHELL`: a grep outside the vendored tree found no references. cmd syntax is therefore interpreted by unbash as bash. This lets the model bypass the git, infra and path rules. Examples are caret escapes (`g^it push origin main`), `%VAR%` expansion and cmd built-ins such as `del /s /q`. The same mismatch is what the deny table's powershell entry was meant to prevent. The load test only proves that bash-style commands get classified. It does not prove that the parsed dialect is the executed dialect.
**Fix:** Either deny `bg_run` outright and keep `bash` as the only shell path, or force the policy at load time. Setting `process.env.PI_BG_SHELL = "bash"` in the vendored index before the extension is activated is one way. Add a test that `resolveShellPolicy("win32", {})` yields the bash dialect. Denying `bg_run` is the safest choice, since it also removes WR-01.

## Warnings

### WR-01: bg_run has a single enforcement layer, with no wrapper re-check

**Status:** FIXED in 9c78149. guardBgRun runs in the hook and again inside bg_run execute() (PROVENANCE deviation 8).

**File:** `.pi/extensions/safety/index.ts:721-768`
**Issue:** Decision 5 of the safety design (the hook alone is defeated by `event.input` mutation, which Pi does not re-validate) is not honoured for `bg_run`. A later-loaded extension's `tool_call` handler can rewrite `input.command` after this hook allows it. The bash path is protected by the wrapper's `execute()`, but `bg_run` is registered by an unwrapped vendored tool.
**Fix:** Have the vendored `bg_run` `execute()` call the safety policy (or an exported `classifyAtWrapper`) on its final params, or deny `bg_run` as in CR-01.

### WR-02: bg_run with isAgent:true can launch an unguarded child pi

**Status:** FIXED in 9c78149. isAgent other than false is blocked.

**File:** `.pi/extensions/safety/index.ts:738`, `.pi/extensions/background-tasks/PROVENANCE.md` (deviation 6)
**Issue:** `bg_run isAgent:true` is meant to start `pi -p ...`. The hook only classifies the shell string, and the bash classifier is unlikely to block `pi`. The child's own guard depends on project trust. In headless mode trust resolves to false, so the child may start with the project-scoped safety extension not loaded (the CR-09 scenario described in this file). The child could then run unguarded bash. PROVENANCE notes that `pi-launch.ts:429` falls back to `process.cwd()` for an empty PATH entry.
**Fix:** Deny `isAgent: true` in the hook (`rec.isAgent !== false` leads to a block), or require the child to be launched with `-e <safety>`.

### WR-03: The deny table is name-based, so other extension tools remain outside the guard

**Status:** NOT FIXED, accepted and documented in docs/SAFETY.md (9c78149). lsp_fix writes edits through its own path, which the guard cannot see; this is the EV-42 class. Name-based denial only covers tools known today, and lsp_fix is not in the default active set. A tool-enumeration test was not added.

**File:** `.pi/extensions/safety/index.ts:600-622`, `.pi/settings.json:3-6`
**Issue:** Newly installed Pi 1.x packages are only covered by name. `pi-subagents` (which spawns child agents), `@narumitw/pi-lsp` (`lsp_fix` applies file edits that bypass write/edit path rules) and `pi-web-access` are unguarded under EV-42. This is documented, but the file edit path via `lsp_fix` is a real bypass of the path-detonation rules. The built-in `-builtin:mcp`, `-builtin:codemode` and `-builtin:tool-search` entries in settings are good defence in depth. The deny table is the only fallback if a user setting re-enables them.
**Fix:** Add `lsp_fix` (or route its target paths through `classifyPathWrite`) to the deny table, and add a test that enumerates the active tool names and fails on any unclassified name.

### WR-04: Raw command and input are persisted to the audit log, which can capture credentials

**Status:** FIXED in 9c78149. writeAuditRow redacts credential shapes (local redactSecrets, since safety/ may not import diagnostics/); denied tools without a command string log only input key names.

**File:** `.pi/extensions/safety/index.ts:705,712,730`
**Issue:** For denied tools without a `command` string, the whole `JSON.stringify(event.input)` (up to 2000 characters) is written to the audit log. This can include tokens or secrets in MCP or powershell arguments. The log lives under `.pi/logs`, which is gitignored, but the log is not redacted.
**Fix:** Record only the tool name and the input's top-level keys, or run a redaction pass on `raw`.

## Info

### IN-01: `KYPI_PI_PINNED` lets an environment variable override the Pi pin

**File:** `bin/bootstrap.sh:54`
**Issue:** `PI_PINNED="${KYPI_PI_PINNED:-1.1.0}"` allows an unvalidated version string into `npm install -g`. This is a deliberate escape hatch, but it conflicts with the exact-pin posture. CI hard-codes `@1.1.0`, so the two can drift.
**Fix:** Validate that the value matches `^[0-9]+\.[0-9]+\.[0-9]+$` before use, and log a warning when it differs from the default.
