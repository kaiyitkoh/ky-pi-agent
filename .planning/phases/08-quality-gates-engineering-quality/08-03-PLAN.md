<objective>
Build the REVIEW artifact's schema and its validator — the parser half of GATE-03/04/05 and QUAL-04/06.

These are *parser* requirements, not prompt requirements. If the harness would accept "LGTM", the requirement is
not met however good the reviewer's prompt is. The mechanism is a forced structured tool call (`submit_review`)
whose typebox schema IS the artifact shape, so Pi's own tool-call JSON-Schema validation rejects a bad `severity`
before this module's validator even runs — and this module's validator then enforces every cross-field rule a JSON
Schema cannot express (verdict coverage against the stated requirement ids, non-empty checked-and-cleared,
workaround-implies-proper-fix).

This module is PURE. It makes no model call, registers nothing, and reads no files.

Purpose: silence and vagueness become structurally impossible.
Output: `review-schema.ts` + its two-directional rejection table.
</objective>

  <action>
    Add to `review-schema.ts`:

    `export type ReviewValidation = { readonly ok: true; readonly review: ReviewArtifact } | { readonly ok: false; readonly reason: string };`

    `export function validateReview(raw: unknown, expectedRequirementIds: readonly string[]): ReviewValidation`
    — a first-match-wins predicate with a NUMBERED, BINDING-ORDER docstring in `gateCompletion`'s exact style:

      (1) `raw` is not an object, or `findings`/`verdicts` are not arrays → reject as malformed, naming the type
          that arrived.
      (2) ANY finding whose `severity` is not exactly one of BLOCKER/WARNING/NIT (including absent, empty string,
          lower-case, or an unknown token) → REJECT AS MALFORMED, naming the offending index and the value that
          arrived. This is GATE-05 and it is code, not wording.
      (3) `expectedRequirementIds` not fully covered by `verdicts` → reject, naming the missing ids. A verdict for
          an id NOT in the expected set is also a reject, naming the extra id — a reviewer inventing requirement
          ids is the same failure as omitting them.
      (4) ANY verdict whose `evidence` does not match a `file:line` shape (`<path>:<digits>`) → reject, naming the
          verdict's requirement id and the string that arrived.
      (5) `checkedAndCleared` absent, empty, or whitespace-only → reject. This is GATE-04: silence must be
          structurally impossible.
      (6) `classification` not exactly one of root-cause/symptomatic/workaround, or `classificationJustification`
          empty → reject. This is QUAL-04.
      (7) `classification === "workaround"` and either `properFix` or `deferralReason` is absent/empty → reject,
          naming which is missing. This is QUAL-06: an approved workaround is recorded with what the proper fix
          would be and why it was deferred, or it is not a valid review.
      (8) `findings.filter(f => f.severity === "NIT").length > NIT_CAP` → reject, naming the count and the cap.
      (9) otherwise → accept, carrying the normalised `ReviewArtifact`.

    Every reject reason is built from the received data, never from a caller-supplied string.

    Then create `tests/unit/quality-schema.test.ts`. Start from ONE valid baseline review object that passes, and
    derive every rejection case by mutating exactly one field of it — so each rejection is attributable to that
    field and nothing else. Cases, each with a `-t`-matchable name:
    - `"verdict"`: missing requirement id → reject naming it; extra invented id → reject; malformed `evidence`
      (`"src/x.ts"`, `"nowhere"`, `""`) → reject; valid `file:line` → accept
    - `"malformed"`: severity `"blocker"` (wrong case), `"CRITICAL"`, `""`, absent → all reject; the literal
      string `"LGTM"` as `raw` → reject; a review with zero findings and a non-empty `checkedAndCleared` → ACCEPT
      (a genuinely clean review must remain expressible, or the gate teaches the reviewer to invent findings)
    - `"checked and cleared"`: absent / `""` / `"   "` → reject; one sentence → accept
    - `"classification"`: absent, unknown token, empty justification → reject
    - `"workaround"`: `classification:"workaround"` with no `properFix` → reject naming `properFix`; with no
      `deferralReason` → reject naming `deferralReason`; with both → accept
    - NIT cap: `NIT_CAP + 1` NITs → reject naming the count and the cap; exactly `NIT_CAP` → accept

    Add a vacuity guard: assert the baseline object validates OK first. Without it every rejection case could be
    passing for the wrong reason.
