<objective>
Give the two templates a path into the directory Pi actually reads, without ever destroying a
credential the user already had.

Purpose: there is no project-scope `models.json` and no project-scope `auth.json` — both are
resolved only from `getAgentDir()` (RESEARCH §Q1.1). A file committed at `.pi/models.json` is
read by nothing. Success criterion 1 is therefore satisfied by templates **plus an installer**,
and the installer is the half where the worst outcome in the phase lives: clobbering a
`~/.pi/agent/auth.json` that holds the user's real credentials for every provider (Trap T7).

Output: `merge_models_json` / `merge_auth_json` in `bin/bootstrap.sh`, and the integration test
that drives them under a temp `PI_CODING_AGENT_DIR`.
</objective>

Add two functions to `bin/bootstrap.sh`, both in the `merge_settings` shape.

`merge_models_json` — reads `$REPO_ROOT/.pi/templates/models-template.json`, FATALs if the
template is missing; strips `//` comments before parsing (the template carries them
deliberately and `JSON.parse` will not); substitutes the base URL from
`KYPI_DASHSCOPE_BASE_URL` when that variable is set and non-empty, falling back to the
template's committed value; then merges into `$PI_AGENT_DIR/models.json` under the
`providers.dashscope` key **only**. Refuse to touch the target if it is not valid JSON or not
a JSON object, with the same FATAL wording style. Print "already current - unchanged" and exit
0 when the composed `providers.dashscope` value is identical to what is already there — that
no-op path is what makes the byte-identity test possible. Preserve every other key of the
target file untouched.

`merge_auth_json` — reads `$REPO_ROOT/.pi/templates/auth-template.json`, FATALs if missing,
and for each top-level provider key in the template writes it into `$PI_AGENT_DIR/auth.json`
**only when that key is absent**. An existing key is never modified, never merged into, never
reordered — this file may hold the user's real credentials for every provider. Same
invalid-JSON refusal. Same "already current - unchanged" no-op reporting when nothing was
added. Do not create the file with a permissive mode assumption: the `0600` note is already
recorded in `docs/RUNBOOK.md`'s Phase 1 machine-state section and must be referenced, not
restated — and on Windows it is a no-op against NTFS ACLs regardless, which is exactly why
the template holds no secret.

Wire both into `run_full` **after** `install_pi`, beside `merge_settings` and
`write_env_template`, under the existing `Configuration:` heading. Do not disturb the BOOT-01
ordering clause. Add neither to `--assert-hardening`; add neither to `--check-only`, which
mutates nothing and has a test asserting exactly that.

Add `KYPI_DASHSCOPE_BASE_URL` to the usage text's `Environment:` block with a one-line
description naming the workspace-dedicated form as its purpose and `RB-03-01` as the entry
that tells the user when to set it.

Strict POSIX `sh` throughout: no arrays, no `local`, no `[[`, no bash-4 parameter expansion,
no `sed`/`awk` on JSON, all JSON handled inside `node -e`, and every value crossing into that
`node -e` through a `KYPI_*` environment variable rather than shell interpolation into the JS

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| installer → `~/.pi/agent/auth.json` | The target file may hold live credentials for every provider the user has ever configured |
| installer → `~/.pi/agent/models.json` | The target file may hold the user's own providers, overrides and package-installed model entries |
| repo template → a public clone | Whatever the template carries is world-readable; whatever the installer substitutes is not |
| test process → the developer's real agent directory and global npm prefix | An integration test that forgot a seam would run the real installer against the real machine |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-06-01 | Tampering | the installer overwriting an existing `~/.pi/agent/auth.json` and destroying live credentials | mitigate | Merge-if-absent per provider key, never a whole-file rewrite; case 3 asserts both a foreign entry and an existing `dashscope` entry survive unchanged (Trap T7) |
| T-03-06-02 | Tampering | the installer overwriting an existing `models.json` holding the user's own providers | mitigate | Key-namespaced merge under `providers.dashscope` only, with every other key preserved; the invalid-JSON refusal copies `merge_settings`'s FATAL-rather-than-touch posture |
| T-03-06-03 | Information Disclosure | a workspace id or account id entering the public repo through the templated base URL | mitigate | The committed template carries the shared `dashscope-intl` form; the dedicated form arrives only through `KYPI_DASHSCOPE_BASE_URL` at install time. Case 5 asserts the committed template is unchanged after such a run |
| T-03-06-04 | Information Disclosure | a real credential pasted into a template or a test fixture and pushed | mitigate | Case 7's secret-shape scan over both committed templates, with a positive control; fixture credentials in the test are obviously synthetic and live only in a temp agent dir |
| T-03-06-05 | Tampering | the integration test running the real installer against the developer's machine or the global npm prefix | mitigate | Every run sets `PI_CODING_AGENT_DIR` to a fresh temp dir **and** `KYPI_SKIP_INSTALL=1`, with a stubbed `npm` whose invocation log is asserted — two independent guards, as the analog established |
| T-03-06-06 | Denial of Service | a `!command` reaching `models.json` through the installer and spawning a subprocess on every provider request | mitigate | The template forbids it (plan 03-02) and plan 03-07 makes it a standing scan; the installer performs no value transformation other than the base-URL substitution |
| T-03-06-07 | Repudiation | an `auth.json` written with a mode that is a no-op on Windows ACLs being mistaken for protection | mitigate | The installer writes no secret at all — the template holds `$ENV_VAR` references only — and the existing Phase 1 machine-state note in `docs/RUNBOOK.md` is referenced rather than restated (CONTEXT decision 10) |
| T-03-06-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs nothing and stubs `npm` in every test run; `tests/unit/pinning.test.ts` guards the dependency set |
</threat_model>
