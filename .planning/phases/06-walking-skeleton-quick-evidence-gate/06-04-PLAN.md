<decisions>
**D-12 — One inline user-scope extension composes the real entry points.** `createFauxSession`
accepts exactly one entry point, and project-scoped `.pi/extensions` resolves `trusted:false`
headless (a silently absent extension is a green run that proved nothing). So the fixture is an
`extensionSource` string that imports the REAL `safety/index.ts`, `workflows/index.ts` and — for case
4 — `diagnostics/index.ts` by absolute path and calls each default export in turn, exactly as
`double-enforcement.test.ts:150-172` does for the safety extension plus a second handler. No
re-implementation, no shim, no stub.

**D-13 — Every expected refusal string is READ from the real function inside the test.** The test
calls `planRoleCall` / `classifyGitInvocation` itself with the same inputs `/quick` uses and compares
the notification against that returned `reason`. A retyped literal would stay green against a `/quick`
that hardcoded the same literal — the precise weakness Phase 5's wire-proof test had.

**D-14 — A refusal must also cost zero provider requests.** `faux.state.callCount === 0` after a
refusal is what distinguishes "refused before prompting" from "prompted, then reported something".
Phase 5's `single-shot-roles.test.ts` established this assertion shape for a guard refusal.

**D-15 — Case 4 commits with `git commit --allow-empty`.** The atomic commit is what is being proved,
not the file edit; `--allow-empty` removes the `write`-tool path classifier as a variable from a test
whose subject is the route→guard→evidence→commit chain. If the executor prefers the richer shape, a
`write` tool call modifying a file the fixture already committed, followed by `git commit -am`, is an
acceptable substitute PROVIDED it is green on the first run — if the write tool is refused by
`safety/paths.ts` inside the temp cwd, record that as a finding in the SUMMARY and fall back, do not
weaken the path classifier.

**D-16 — A known and accepted property, to be recorded rather than discovered at review.** Because
evidence is bound to the SHA at capture time and compared against HEAD at claim time, a verification
command run BEFORE the commit is stale by construction once the commit lands. That is GATE-07's
stated rule ("evidence collected against SHA A must not satisfy a claim made at SHA B"), not a
defect. Any richer policy — re-running verification after the commit, or binding to a tree hash —
belongs to Phase 8's quality gates. State this in the test's header docstring and in the SUMMARY.
</decisions>
