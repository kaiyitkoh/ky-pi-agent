## Design decisions (Claude's discretion, recorded)

- D-P1 Selection: `pi.registerFlag("ky-profile", { type: "string", default: "implement" })` in routing; `/mode` model tiers are not overloaded. `resolveProfile` validates and falls back to `implement` on unknown input (the `isModeName` validate-then-default idiom). The user's cheap escape hatch `pi --tools read,bash` stays native.
- D-P2 Mechanism: narrowing REMOVES active names that are classified and not in the profile; it never adds; it preserves the relative order of the live active set; unclassified names are left active (fail-open on cost, and the completeness test turns that into a CI failure). This is the RESEARCH intersection with two refinements: (i) `PROFILE_NEUTRAL_TOOLS` = Pi's registered-but-inactive-by-default built-ins (`grep`, `find`, `ls`, plus any other the composed session shows registered and inactive, e.g. `powershell`) are never removed, because when they are active something chose them explicitly (plan mode, a subagent's `tools:` frontmatter); (ii) when the active set at `session_start` contains neither `edit` nor `write`, the loadout was already chosen read-only (plan mode restored or `--plan`, or a read-only subagent), and the profile leaves it untouched. Reason: `getFlag` is scoped to the registering extension (pi loader.js:295-300), so routing cannot read `--plan`; the loadout itself is the reliable signal, and plan-mode sorts before routing.
- D-P3 Membership (from RESEARCH "Profile design", extended for third-party names the repo already depends on):

| Tool(s) | recon | review | implement | full |
|---------|-------|--------|-----------|------|
| read, bash, approve_ky_command | yes | yes | yes | yes |
| edit, write, todo | no | no | yes | yes |
| consult_advisor | no | yes | yes | yes |
| lsp_diagnostics, lsp_fix (quality gate reads them, quality/gates.ts:32) | no | yes | yes | yes |
| subagent, bg_wait, subagent_supervisor, subagents_enable (/execute handoff dispatch, execute/handoff.ts:17) | no | yes | yes | yes |
| web_enable (loader only) | yes | yes | yes | yes |
| web_search, fetch_content, get_search_content, source_check | yes | no | no | yes |
| questionnaire | no | no | no | yes (plan mode re-adds it inside /plan) |
| bg_run, bg_status, bg_logs, bg_kill | no | no | no | yes |
| qoder_delegate | no | no | no | yes (still gated on configuration by qoder) |
| grep, find, ls (and other inactive-by-default Pi built-ins) | neutral | neutral | neutral | neutral |

  `full` applies no narrowing at all, preserving today's behaviour exactly. Third-party interaction (pi-subagents re-adding its loader each prompt, eager mode on DeepSeek, whether a subagent child loads routing) cannot be tested offline and is part of RB-10-03 (plan 10-07).
- D-P4 `tool_search` decision: option (a). `.pi/settings.json`, `docs/SAFETY.md`, the safety deny list and `tests/integration/new-tool-paths.test.ts` are NOT modified by this phase.

Output: profiles module, routing wiring, two test files, baseline cross-check, ratchet update.
