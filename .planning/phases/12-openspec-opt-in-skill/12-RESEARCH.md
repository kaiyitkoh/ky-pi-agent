**Pin `@fission-ai/openspec@1.13.2`** (published 2026-09-23, 20 days old; integrity `sha512-HzBaN9C1/ET+tgm/pxbWQYY4Kf+X9/1MSVEGQ8ZT3g4ZpdHn6v82CHkN+zmt9qv98Ghw0MDpmURasjJD2f90bg==`, shasum `ae88d3667eff76495e517399b3e0385d9d6af009`, SLSA provenance attestation present, published by GitHub Actions OIDC) `[VERIFIED: npm view @fission-ai/openspec@1.13.2]`. It has a first-class `pi` tool target, no install-time lifecycle scripts, 10 direct dependencies, `engines.node >=20.19.0`, bin `openspec -> bin/openspec.js`. The Pi adapter, telemetry opt-out, skill generator and profile code are byte-identical in 1.14.1 `[VERIFIED: diff of unpacked tarballs]`, so there is no reason to go newer; 1.14.0 (13 days) and 1.14.1 (8 days) fail the 14-day policy anyway.

Three facts reshape the CONTEXT assumptions and the planner must absorb them: (a) **`openspec init --tools pi` writes only project-level** (`<project>/.pi/skills/<name>/SKILL.md` and `<project>/.pi/prompts/opsx-*.md`); there is no user-level Pi target (only `minimax-code` has `globalSkillsDir`). User level is therefore reached by generating into a temp directory and copying into `$PI_CODING_AGENT_DIR` (default `~/.pi/agent`). (b) **There is no "expanded" profile name.** Profiles are `core` (6 workflows) and `custom`; "expanded" is `profile: "custom"` plus a `workflows` array holding all 12 ids, set in the global config file `config.json` under `$XDG_CONFIG_HOME/openspec/` (Windows fallback `%APPDATA%\openspec\`). (c) **The CLI does not emit `disable-model-invocation`**; the frontmatter it writes is `name`, `description`, `allowed-tools`, `license`, `compatibility`, `metadata`. A script must insert the key. In Pi 1.1.0 the key is honoured exactly as wanted: such skills are filtered out of the system-prompt index, and typed `/skill:<name>` still expands.

`openspec-pi@0.2.1` is rejected on source evidence: it registers a model-facing tool and appends `openspec context` output to the system prompt on every agent start. Separately, **the safety guard currently has no `openspec` rule**, so every `openspec` call is `allow` today (including `completion install`, which edits `~/.bashrc`, and `update`, which can offer an unpinned `npm install -g @latest`). The recommendation is a small explicit classifier plus table tests, not a path-rule change.

**Primary recommendation:** one POSIX `sh` script (`scripts/openspec-setup.sh`) that generates into an isolated temp project with an isolated `XDG_CONFIG_HOME`, patches the frontmatter, copies skills (and optionally prompts) into the Pi agent dir, and verifies; plus an `openspec` arm in `infra.ts`; plus a harness-level `process.env` telemetry default; plus an offline zero-cost test built on Pi's own `loadSkills`/`formatSkillsForPrompt`.

## Findings by research question

### 1. `@fission-ai/openspec` 1.13.2 at source `[VERIFIED: tarball dist/**]`

**1.1 Pi target.** `dist/core/config.js:56`: `{ name: 'Pi', value: 'pi', available: true, ..., skillsDir: '.pi' }`. Flag: `openspec init --tools pi` (`cli/index.js` `--tools <tools>`: "all", "none", or comma list; non-interactive). Also an `oh-my-pi` target (`.omp`) exists; do not confuse.

**1.2 Profile selection ("expanded").** `core/profiles.js`: `CORE_WORKFLOWS = [propose, explore, apply, update, sync, archive]`; `ALL_WORKFLOWS = [propose, explore, new, continue, apply, update, ff, sync, archive, bulk-archive, verify, onboard]` (12). `config-schema.js`: `profile` enum is `['core','custom']`; `workflows` is a string array honoured only when `profile === 'custom'`. `delivery` enum `both|skills|commands`, default `both`. `init --profile <core|custom>` overrides the profile only, not the workflow list. The grep for "expanded" in the package finds no profile of that name. Non-interactive way: write `config.json` directly:
```json
{"profile":"custom","delivery":"both","workflows":["propose","explore","new","continue","apply","update","ff","sync","archive","bulk-archive","verify","onboard"],"telemetry":{"enabled":false}}
```
`openspec config profile` is an interactive picker (only `core` preset shortcut exists, `commands/config.js:527-544`); do not use it. `openspec config set` exists but array handling was not verified; writing the file is simpler and testable.

**1.3 Config location.** `global-config.js`: `$XDG_CONFIG_HOME/openspec/config.json` if `XDG_CONFIG_HOME` set (all platforms); else `~/.config/openspec/` (Unix) or `%APPDATA%\openspec\` (Windows). Pointing `XDG_CONFIG_HOME` at a temp dir isolates generation from the user's real config. **Pitfall:** under Git Bash, a POSIX temp path handed to a native `node.exe` env var may or may not be auto-converted; use `cygpath -m` when available and verify in a RUNBOOK item.

**1.4 What init writes (project-level only).** Skills root is `path.join(projectRoot, tool.skillsDir, 'skills')` (`core/shared/skill-paths.js`); `globalSkillsDir` exists only for `minimax-code`. For `--tools pi` with `delivery: both` and 12 workflows, `init` in `<proj>` writes:
- `<proj>/openspec/{specs,changes,changes/archive}` with `.gitkeep` anchors, and `openspec/config.yaml` (`init.js:613-640`, `createConfig`)
- `<proj>/.pi/skills/<12 dirs>/SKILL.md` (`init.js:680-690`)
- `<proj>/.pi/prompts/opsx-<id>.md` x12 (Pi adapter `command-generation/adapters/pi.js`: path `.pi/prompts/opsx-<id>.md`, frontmatter `description` only)
No `.pi/skills/.openspec-target` marker for Pi (that is for shared `.agents` roots only).
Skill names (`OPENSPEC_SKILL_NAMES`, `core/config.js`): `openspec-explore`, `openspec-new-change`, `openspec-continue-change`, `openspec-apply-change`, `openspec-update-change`, `openspec-ff-change`, `openspec-sync-specs`, `openspec-archive-change`, `openspec-bulk-archive-change`, `openspec-verify-change`, `openspec-onboard`, `openspec-propose`.

**1.5 SKILL.md frontmatter emitted** (`core/shared/skill-generation.js:113-123`): `name`, `description`, `allowed-tools: Bash(openspec:*)`, `license: MIT`, `compatibility: Requires openspec CLI.`, `metadata: {author, version, generatedBy}`. **No `disable-model-invocation`.** The patch must be ours. Descriptions are 176-437 chars (< Pi's 1024 limit) and contain no `: ` or ` #` sequences that would break plain-scalar YAML `[VERIFIED: grep over core/templates/workflows/*.js]`. An executed `loadSkills` diagnostics-empty assertion on real generated output is still the right check (RB item).

**1.6 Cross-references in generated text (decision needed).** With `delivery: both` the Pi transformer rewrites in-skill references to `/opsx-<id>` (prompt-template names). With `delivery: skills` references become `/openspec-<name>`, which is not a Pi invocation (Pi's is `/skill:<name>`); only `kimi` and `codex` have a `SKILL_INVOCATION_PREFIX` (`utils/command-references.js:58-61`). Recommendation: **`delivery: both`, and copy the 12 `opsx-*.md` prompt templates to `$PI_AGENT_DIR/prompts/` as well.** Prompt templates are expanded only when the user types them (`agent-session.js` `expandPromptTemplate`), are not in the system prompt, and make the skill cross-references resolve. This is user-visible scope beyond the literal CONTEXT wording; record it as a Claude's-discretion choice (see Open Questions Q1).

**1.7 Telemetry implementation** (`telemetry/index.js`, `opt-out.js`): PostHog `POST https://edge.openspec.dev/batch/`, 1 s timeout, payload = command name + CLI version + random UUID (`anonymousId`), `$ip: null`. Disabled when, first match wins: `OPENSPEC_TELEMETRY` set to anything except `1/true/yes/on`; `DO_NOT_TRACK` set to anything except `''/0/false/no/off`; `CI` truthy; global config `telemetry.enabled === false`; global config unparseable. First-run notice on stderr. **So `OPENSPEC_TELEMETRY=0`, `DO_NOT_TRACK=1`, and `telemetry.enabled:false` each suffice; all three together is belt and braces.**

**1.8 Second network surface: the update check** (`core/version-check.js`). `GET <registry>/@fission-ai/openspec` (default `registry.npmjs.org`, 1.5 s timeout), run by `openspec update`. Disabled by `OPENSPEC_NO_UPDATE_CHECK` set to **any** value, by the telemetry opt-outs above, by CI, or `NODE_ENV=test`. In an interactive TTY it can then **offer to run `npm install -g @fission-ai/openspec@latest`** (`runGlobalUpgrade`, `version-check.js:578`; gated by `shouldOfferUpgrade`: interactive and stdout TTY). That is an unpinned self-upgrade, contrary to the pin policy. With the telemetry opt-outs present the check is skipped, which also removes the offer, but set `OPENSPEC_NO_UPDATE_CHECK=1` explicitly. Also set `OPENSPEC_NO_AUTO_CONFIG=1`: it stops `openspec completion install` from editing `~/.bashrc`/`~/.zshrc` (`completions/installers/bash-installer.js:127`).

**1.9 Other process spawns / writes outside target dirs** (grep of `child_process`/`cross-spawn`): `commands/feedback.js` (`execFileSync` for `gh`, files a GitHub issue), `commands/config.js` (`config edit` spawns `$EDITOR`/`$VISUAL`), `commands/workset.js` (`workset open` spawns an app), `version-check.js` (`npm install -g`), `core/store/git.js`, `core/store/operations.js` (`store` subcommands use git), `ui/welcome-screen.js`, `utils/shell-detection.js` (completions). Writes outside `openspec/` and the tool dirs: global config under the XDG/APPDATA dir, shell rc on `completion install`. Nothing else found.

**1.10 `archive`.** `openspec archive <change> [-y|--yes] [--skip-specs] [--no-validate] [--json] [--store <id>]`; implementation (`core/archive.js`) uses `fs.rename`/`mkdir`/`rm` within the planning home (`openspec/changes/` and `openspec/specs/`). **The generated `openspec-archive-change` skill does not call the CLI `archive`**: it runs `mkdir -p "<planningHome.changesDir>/archive"` and `mv "<changeRoot>" "<planningHome.changesDir>/archive/<target-name>"` (`templates/workflows/archive-change.js:157,167`, bulk variant at `:357,367`), and uses `openspec status|list --json|instructions|new change|validate` and `openspec --version`. No `$(...)`, heredocs, or git writes appear in any workflow template, so the guard's fail-closed shell predicates do not block the skills' own commands.

**1.11 Diff vs 1.14.x.** `diff -rq` of unpacked 1.13.2 and 1.14.1: identical `core/profiles.js`, `telemetry/opt-out.js`, `core/shared/skill-generation.js`, `adapters/pi.js`; differences are four new tool adapters, `cli/commands/` and `commands/workflow/default-schema.js`, changes in `archive.js`, `config.js`, `store`, `workset`, `doctor`, `context`, and `NATURAL_LANGUAGE_SKILL_TOOLS` gaining `gsd`. Nothing Pi-relevant.

### 4. Safety guard `[VERIFIED: .pi/extensions/safety/*.ts, docs/SAFETY.md]`

How a bash command is classified (`policy.ts` `evaluateBash`): `canonicalise()` (unbash AST, fail-closed predicates for substitution, heredocs, backgrounding, nested-shell-with-guarded-verb) -> per `CanonicalInvocation`: git/glab classifiers, `classifyInfraInvocation` (aws/terraform/kubectl only; anything else `not-applicable`), then **every arg** through `classifyPathRead` (sensitive-READ patterns only: `.env` family, `~/.aws/{credentials,config}`, kubeconfig, `*.tfstate`, harness ledger). **Bash writes are not path-classified at all**; `classifyPathWrite` / `DETONATION_TARGETS` (`.git/hooks`, `.git/config`, `~/.bashrc`, `~/.bash_profile`, `~/.profile`, `~/.gitconfig`, `.github/workflows/*.yml`, `.gitlab-ci.yml`) and the project-root containment check apply only to the `write` and `edit` tools (`evaluateWrite`). `grep -ri openspec` over `.pi/extensions/safety`, `docs`, `tests` returns nothing.

Verdict today for the commands in question (all `allow`):

| Command | Today | Why |
|---------|-------|-----|
| `openspec list/show/view/validate/status/instructions/--help/--version` | allow | executable not infra; args are not sensitive paths |
| `openspec archive <change> -y` | allow | writes only under `openspec/`; no protected-path rule can fire on bash writes anyway |
| `mkdir -p openspec/changes/archive`, `mv openspec/changes/x openspec/changes/archive/x` (what the archive skill actually runs) | allow | no rule |
| `openspec init`, `openspec update` | allow | write `.pi/`, `.claude/`, etc.; the guard cannot see bash writes |
| `openspec completion install` | allow | edits `~/.bashrc` (a `DETONATION_TARGETS` entry the write tool would block) |
| `openspec update` interactive | allow | may offer unpinned `npm install -g @latest` (1.8) |
| `openspec feedback ...` | allow | files a GitHub issue via `gh` |

**Recommendation (minimal, house style):** add an `openspec` arm to `classifyInfraInvocation` in `infra.ts` (same family and posture as terraform/kubectl; `infra.ts` header comment lists the invariants to follow, and `policy.ts` already routes `confirm` through `fromInfraVerdict`, so no `policy.ts` edit is needed). Explicit allow set, explicit confirm set, unknown subcommand -> `confirm` (matching terraform/kubectl "add a table row rather than widening a default"):
- **allow:** `list`, `view`, `show`, `validate`, `status`, `instructions`, `archive`, `new`, `change`, `spec`, `schema`, `schemas`, `templates`, `context`, `doctor`, `--help`, `-h`, `--version`, `-V`, `config` with `get|list|path` (the `config` first-arg), `store list|doctor`, `workset list`, `__complete`.
- **confirm (reason text required, must say why):** `init` and `update` (write agent-config dirs; `update` may self-upgrade), `completion` (install edits shell rc), `feedback` (posts to GitHub), `config set|unset|reset|edit|profile`, `workset create|open|remove`, `store setup|register|unregister|remove`.
- Bare `openspec` with no subcommand -> `confirm` (fail closed, like terraform).
`archive` must be a **named allow row** with a `why` citing "writes only inside openspec/", so a future path-write classifier cannot silently regress it. Whether to treat `init --tools none` as allow is optional; keep it confirm (single rule, fewer branches).

Test locations to extend (existing, table-driven; each has a vacuous-pass guard that asserts table length and that every table key is exercised):
- `tests/unit/infra-policy.test.ts`: add `openspec` rows to `ROWS`, add exported `OPENSPEC_ALLOW_SUBCOMMANDS`/`OPENSPEC_CONFIRM_SUBCOMMANDS` sets and extend the liveness describe (`:220-257`) so every set entry has a row; raise the `>= 45` row-count floor by the number added (this is a guard on the table, not a budget).
- `tests/unit/policy-compose.test.ts`: full `evaluate("bash", {command}, facts)` rows: `openspec archive add-foo -y` -> allow; `openspec init --tools pi` -> confirm; `mv openspec/changes/x openspec/changes/archive/x` -> allow; `env OPENSPEC_TELEMETRY=0 openspec update` -> confirm (wrapper resolution reaches the verb); a negative control that deleting the `openspec` arm turns the confirm rows red.
- Docs: `docs/SAFETY.md` "What the guard does catch" gets a short `openspec` paragraph and "Known bypasses" gets: `npx @fission-ai/openspec ...` (executable `npx`, unclassified), and bash writes are not path-classified, so the archive `mv` is allow by absence of a rule, not by an exemption.
Do not add `openspec` handling to `paths.ts`; nothing about archive trips protected-path rules, and adding exemptions would create the attack surface the phase wants to avoid.

### 6. Telemetry persistence, bootstrap and RUNBOOK conventions

**6.1 Pi bash children inherit the environment.** `getShellEnv()` (`dist/utils/shell.js:115-126`) returns `{ ...process.env, [pathKey]: updatedPath }`, so a `process.env` assignment made by any extension at load reaches `bash` tool children (and `pi-subagents` child processes spawned from the same process tree).

**6.2 Recommended layering (belt and braces):**
1. *Durable, covers terminal use:* the setup script runs `openspec config set telemetry.enabled false` under `OPENSPEC_TELEMETRY=0` against the user's **real** config dir (not the isolated one), or writes the key idempotently. Verify afterwards with `openspec config get telemetry.enabled` (expect `false`) and check no `anonymousId` was created.
2. *Pi sessions:* a few lines in the existing `.pi/extensions/harness/index.ts` factory assigning `process.env.OPENSPEC_TELEMETRY = "0"`, `DO_NOT_TRACK = "1"`, `OPENSPEC_NO_UPDATE_CHECK = "1"`, `OPENSPEC_NO_AUTO_CONFIG = "1"`. Use the existing extension rather than a new entry point: a new `.pi/extensions/<name>/index.ts` is picked up by `listEntryPoints()` and would disturb extension-layout/context-floor/tool-count expectations. Force-assign rather than default-if-unset (an inherited `OPENSPEC_TELEMETRY=1` would otherwise re-enable it). Test pitfall: this mutates the worker's `process.env`; the test must save and restore, and `tests/helpers/harness-session.ts` `PINNED_ENV` handling is the pattern. Add a unit test importing the factory with a fake `pi` and asserting the four values, plus a negative control that fails when the assignment lines are removed. Note the harness is project-scope; it applies in work repos only where the package is installed.
3. *Do not* write the user's `~/.bashrc`/`.profile` from scripts: those are `DETONATION_TARGETS` and a surprising place for a script to write. Document `export OPENSPEC_TELEMETRY=0 DO_NOT_TRACK=1` in the RUNBOOK as an optional manual step for terminal use; layer 1 already covers it.

**6.3 Bootstrap and RUNBOOK.** `bin/bootstrap.sh` (1,281 lines, POSIX sh, modes `--check-only`, `--assert-hardening`, `--check-version`, full) runs `run_full` for core setup; OpenSpec is opt-in, so **do not add it to `run_full`**. A separate `scripts/openspec-setup.sh` (modes e.g. `--install-cli`, default generate+install, `--check`, `--uninstall`) keeps bootstrap's contract ("which assertions ran") intact. `sanitise_npm_env`/`assert_ignore_scripts_for` in bootstrap are reference patterns. RUNBOOK conventions (`docs/RUNBOOK.md` header and `tests/unit/docs-policy.test.ts`): section `## Phase 12 — OpenSpec Opt-in Skill`; summary table `| ID | Check | Status |` with `OUTSTANDING`; each `### RB-12-nn — title` has `**Status:** OUTSTANDING`, exact commands, expected output, and an **offline proxy** test path (the test file must exist on disk; `PROXY_PATH_RE` scans for `tests/...test.ts`). **Registering new ids in `docs-policy.test.ts` is mandatory** or the "governs every entry" test fails: add `const PHASE_TWELVE_IDS = [...]`, append to `ALL_IDS`, and add an `ENTRY_COMMANDS["RB-12-nn"]` row per id whose strings occur verbatim in the runbook (the pattern: recorded line `echo "RB-12-01 ... $(date -u +%FT%TZ)" >> RB-12-01-RESULT.md`). Mind PHASE_NINE-style "occurs exactly once" pins if copied.

## Architecture Patterns

### System flow
```
operator

  |-- sh scripts/openspec-setup.sh
        |-- mktemp project dir + isolated XDG_CONFIG_HOME (config.json: custom/12 workflows/telemetry off)

        |-- openspec init --tools pi --profile custom <tmpproj>     writes <tmp>/.pi/skills/*, <tmp>/.pi/prompts/*, <tmp>/openspec/
        |-- patch each SKILL.md: insert disable-model-invocation: true (idempotent)
        |-- verify: 12 skills, each flag present, names match OPENSPEC_SKILL_NAMES
        |-- copy skills -> $PI_CODING_AGENT_DIR/skills/, prompts -> $PI_CODING_AGENT_DIR/prompts/

        |-- rm -rf temp

  |-- loadSkills: <agentDir>/skills/openspec-* (flagged) -> NOT in system prompt (0 tokens)
  |-- user types /skill:openspec-propose  -> body injected as a user message

work repo: `openspec init --tools none` creates only openspec/ (no agent dirs); `openspec update` there reports "No configured tools found".
```

### Recommended structure
```

.pi/extensions/harness/index.ts  # +4 env assignments (existing file)
.pi/extensions/safety/infra.ts   # +openspec arm + exported sets
docs/WORKFLOWS.md                # short OpenSpec opt-in section (or docs/OPENSPEC.md)

```

### Frontmatter patch (idempotent, POSIX)
Insert after the `name:` line inside the first frontmatter block only; skip if a `disable-model-invocation:` line already exists in the frontmatter; rewrite to `true` if present with another value. Use awk (POSIX) with a state flag so body text containing the string is never touched. Write via temp file + `mv`, preserving LF.

### Anti-Patterns to Avoid
- **Running `openspec init` in `$HOME` or in this repo.** Pollutes both; use the temp project. A repo-level accident is caught by `/openspec/` ignore.
- **`openspec update` as the upgrade mechanism.** It operates on project dirs only; user-level skills are refreshed by re-running the setup script.
- **`openspec config profile`** (interactive picker, can apply changes to the cwd project at `config.js:690-695`).
- **Quoting the value** (`disable-model-invocation: "true"`): Pi requires boolean `true`.
- **Editing shell rc files** from scripts (guard treats them as detonation targets).
- **Adding a new extension entry point** just for env defaults.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Skill generation | Copy the templates by hand | `openspec init` in a temp dir | Official, version-stamped (`generatedBy`) |
| Skills-index measurement | Parse system prompts with regex | Pi `loadSkills` + `formatSkillsForPrompt`; `/budget` slicer | Same code path as production |
| Shell parsing in classifier | String matching | existing `unbash`-based `canonicalise()` | Indirection (`env X=1 openspec update`) already resolved |
| Git-ignore checks | Parse `.gitignore` | `tests/helpers/git.ts` `isIgnored` | House rule |
| Exec stubs | Real CLI in tests | `tests/helpers/stub-bin.ts` | Reproducible, offline |

## Common Pitfalls

1. **`delivery: skills` leaves dangling `/openspec-*` references** (not a Pi invocation). Use `both` and ship the prompts, or accept dead cross-references. (Q1)
2. **String `"true"` is not honoured** by Pi; only boolean `true`.
3. **`XDG_CONFIG_HOME` path form under Git Bash.** A `/tmp/...` value may reach `node.exe` unconverted; resolve with `cygpath -m` where available; the test stub should record the received value; RUNBOOK covers the real run.
4. **Update check + self-upgrade offer.** Needs `OPENSPEC_NO_UPDATE_CHECK` (any value); the telemetry opt-outs also suppress it.
5. **`completion install` rewrites `~/.bashrc`.** `OPENSPEC_NO_AUTO_CONFIG=1` plus the `completion -> confirm` rule.
6. **Process-env tests leak.** Save/restore the four variables in any test that loads the harness factory.
7. **Stale skills after upgrade.** If a later version renames or drops a skill, old dirs remain; the setup script should remove the known 12 names before copying and report any other `openspec-*` dir it did not create.
8. **docs-policy.test.ts** fails until the new RB ids are added to `ALL_IDS` and `ENTRY_COMMANDS`.
9. **`openspec-archive-change` runs `mv`**: it works only because bash writes are not path-classified. Do not "fix" this by adding path rules without an `openspec/` carve-out test.
10. **Skill body is injected on `/skill:`** and the model then follows instructions that include `openspec` commands: the guard is the control, hence the classifier work.

## Security Domain

### Applicable ASVS Categories
| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2/V3 Authentication, Session | no | n/a |
| V4 Access Control | yes | safety guard `confirm` for state-changing `openspec` verbs |
| V5 Input Validation | yes | `unbash` canonicalisation (existing); script quotes all expansions; pin validated against `^[0-9]+\.[0-9]+\.[0-9]+$` |
| V6 Cryptography | no | n/a (integrity strings are recorded, not hand-verified; npm checks them) |
| V10 Malicious code / supply chain | yes | exact pin, `--ignore-scripts`, provenance, no lifecycle scripts, human gate before install |
| V8 Data protection | yes | telemetry off in three layers; no credential leaves via the update check |

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Unpinned self-upgrade (`npm install -g @latest` offer) | Tampering | `OPENSPEC_NO_UPDATE_CHECK`, `update -> confirm` |
| Shell rc modification via `completion install` | Tampering/EoP | `OPENSPEC_NO_AUTO_CONFIG=1`, `completion -> confirm` |
| Model-visible skill body steering the agent into destructive CLI calls | Tampering | guard classifier; skills are opt-in (`/skill:`) |
| Wrapper that bypasses the guard (`openspec-pi` tool/`pi.exec`) | EoP | rejected; no new tool |
| Public-repo leak of `openspec/` content from work repos | Information disclosure | rooted `/openspec/` ignore + tracked-files test; `init --tools none` only in work repos |
| Stale or poisoned tarball | Tampering | exact version, integrity and shasum recorded in RUNBOOK, npm verifies |
| Telemetry exfiltration | Information disclosure | opt-out env + config; payload is command name, version, random id only |
